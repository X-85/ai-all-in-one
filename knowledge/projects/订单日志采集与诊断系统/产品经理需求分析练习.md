# 产品经理需求分析练习：订单日志采集与诊断系统

## 1. 练习目标

以“订单日志采集与诊断系统”为真实案例，练习从客户口语化诉求到可供研发评审的产品需求的完整过程。

本练习重点不是学习 PRD 模板，而是训练以下能力：

- 识别真实用户、使用场景和业务问题。
- 将模糊诉求拆分为可验证的产品目标。
- 提出会影响方案的关键问题。
- 管理范围、假设、风险和版本取舍。
- 将结论整理为研发可实现、可验收的需求。

## 2. 原始诉求

> 希望有个工具或者系统可以方便地拉取现场 A 系统中日志；输入订单号后，可以从日志中分析此订单的执行情况。

### 初步判断

- 这是现场问题定位需求，核心价值是缩短订单异常排查时间。
- “拉取日志”“分析订单”“现场 A 系统”都不够明确，不能直接交给研发。
- 需要先澄清用户、协作流程、部署位置、日志来源、订单关联方式、分析结论和数据安全边界。

## 3. 关键追问与设计影响

| 追问 | 确认结论 | 对产品设计的影响 |
| --- | --- | --- |
| 谁使用工具？ | 现场实施、技术支持、研发 | 明确三层问题升级流程和职责划分 |
| 用户如何交接问题？ | 现场实施 -> 技术支持 -> 研发 | V1 使用外部渠道交接日志包，不做工单流转 |
| 日志如何获取？ | 初期设想 SSH；后确认工具部署在平台同一服务器 | V1 改为本机读取日志，移除 SSH、堡垒机和凭据管理 |
| 模块是否在多台服务器？ | 实际可能分散；V1 假设同一服务器 | 跨服务器关联进入后续版本 |
| 如何关联订单链路？ | `addTask.orderId` 是订单号；`task_group.id` 是任务号 | 将 `orderId -> taskId -> 线程 ID/设备号/状态上报` 定为核心关联路径 |
| 订单分析要输出什么？ | 生命周期、失败可能原因、阶段耗时和总耗时 | 分析页面不能只展示原始日志 |
| 是否使用 AI Agent？ | 工厂网络受限，客户不允许配置模型，无本地模型 | V1 采用确定性规则和结构化页面，不依赖大模型 |
| 是否现场直接分析？ | V1 现场实施只采集，技术支持集中分析 | 拆分为采集脚本和公司内网分析系统 |
| 日志保存多久？ | 默认 30 天 | 分析系统需具备自动清理能力 |

## 4. 需求演进与取舍

### 保留在 V1 的能力

- Linux 交互式 Shell 采集脚本。
- 按时间、订单号、任务号、设备号采集日志。
- 支持多模块选择，默认全选。
- 原始日志上限 500 MB，压缩目标 100 MB。
- 公司内网 Web 系统上传、检索和分析日志包。
- 订单生命周期、失败原因和耗时分析。
- 基于协议、错误码和日志特征的确定性诊断规则。

### 延后到后续版本的能力

- SSH 远程采集、堡垒机和服务器凭据管理。
- 跨服务器日志关联。
- 现场实施在线分析。
- 日志包自动拆分。
- 工单、评论、状态流转和协同通知。
- 对接现有登录体系、细粒度角色权限。
- 大模型/Agent 问答和日志解释。
- 慢订单阈值、告警和性能基线对比。

## 5. 关键产品决策

### 5.1 采集与分析分离

现场脚本仅负责在客户环境收集证据，技术支持在公司内网分析。该拆分降低现场部署和培训成本，也使分析能力可集中迭代。

### 5.2 标准日志包是系统契约

采集脚本与分析系统通过统一日志包衔接。日志包包含原始日志和 `manifest` 元数据：查询条件、模块、时间范围、文件校验和、采集版本和关联结果。

### 5.3 规则优先于智能推断

订单状态和失败原因必须能回溯至接口协议、错误码或原始日志证据。V1 对未知问题应明确显示未命中规则，而非给出无法验证的结论。

## 6. 假设、风险与待确认项

| 类型 | 内容 | 后续动作 |
| --- | --- | --- |
| 假设 | `addTask` 相关日志可记录或解析出 `orderId` 与 `taskId` | 用真实日志样本验证 |
| 待确认 | 若日志未记录 `taskId`，是否允许只读查询 `task_group` 表 | 与研发、现场部署负责人确认 |
| 风险 | 日志包从客户现场流转到公司内部 | 在推广前确认客户数据外传、传输和留存要求 |
| 依赖 | 各模块日志格式、状态协议、错误码和已知问题规则稳定 | 研发提供脱敏样本和规则清单 |
| 范围风险 | 实际模块可能部署在多台服务器 | V1 明确只支持单服务器完整链路 |
