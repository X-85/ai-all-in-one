# 日志采集与订单诊断系统 PRD（V1）

## 1. 背景与目标

客户现场出现订单执行异常时，现场实施需从多个模块日志中收集材料，再交由技术支持和研发分析。当前过程依赖人工查找，效率低且材料容易不完整。

V1 目标：

- 现场实施可在客户 Linux 服务器上按条件快速生成标准日志包。
- 技术支持可在公司内网统一上传、检索和分析日志包。
- 系统自动还原订单生命周期，展示耗时，并基于规则提示可能失败原因。
- 研发可使用同一日志包结合代码继续定位根因。

V1 不包含 SSH 远程采集、跨服务器关联、现场人员在线分析、工单流转、角色权限和大模型能力。

## 2. 用户与流程

| 角色 | 职责 | 使用工具 |
| --- | --- | --- |
| 现场实施 | 收集日志、生成并转交日志包 | 客户现场交互式 Shell 脚本 |
| 技术支持 | 上传、检索、分析日志 | 公司内网 Web 分析系统 |
| 研发 | 根因定位、维护诊断规则 | 公司内网 Web 分析系统 |

```text
现场实施运行采集脚本
-> 生成日志包
-> 通过既定外部渠道交给技术支持
-> 技术支持上传至公司内网分析系统
-> 分析并关闭问题 / 将材料交给研发
```

## 3. 日志采集脚本

### 3.1 部署与范围

- 部署在客户提供的 Linux 服务器上。
- 仅读取本机日志，不使用 SSH。
- 模块日志路径固定：`/main/app/<模块名>/logs/`。
- V1 假设订单完整链路涉及的模块均位于同一服务器。

### 3.2 采集条件

用户通过交互菜单选择采集方式：

- 时间范围：默认最近 2 小时，最长 24 小时。
- 订单号 `orderId`。
- 任务号 `taskId`。
- 设备号。
- 模块：默认全部模块，支持多选。

脚本应展示命中的模块、日志文件及预估采集量，用户确认后生成日志包。

### 3.3 输出与限制

- 原始日志总量上限：500 MB。
- 优先压缩为单个日志包，目标不超过 100 MB。
- 若压缩后超过 100 MB，V1 提示用户缩小时间范围或减少模块后重新采集；V2 支持自动拆分多个包。
- 输出格式：`tar.gz` 或 `zip`。
- 脚本不分析日志、不输出订单结论。

### 3.4 异常处理

- 未找到匹配日志：提示采集条件和可调整方向。
- 超出采集量上限：禁止生成并提示缩小范围。
- 日志目录不存在、无读取权限、磁盘空间不足、压缩失败：明确输出失败原因。
- 订单号未能关联任务号：生成已命中的日志，但在日志包元数据中标记“任务号关联失败”。

## 4. 日志包规范

每个日志包必须包含：

- 按模块归档的原始日志片段。
- `manifest` 元数据文件，包含：
  - 采集工具版本、采集时间、现场/服务器标识。
  - 查询条件、实际日志时间范围、已选模块。
  - 每个文件的原始路径、大小、行数、校验和。
  - 订单号、任务号、设备号关联结果。
  - 采集异常和告警信息。
- 不包含服务器 IP、账号、密码或其他凭据。

## 5. 公司内网日志分析系统

### 5.1 基础能力

- 单独账号登录，限制公司内网访问。
- 上传符合规范的日志包，并校验包结构和文件完整性。
- 上传包、解析结果和关联日志默认保留 30 天，到期自动清理。
- 支持手动删除日志包及其分析结果。

### 5.2 检索能力

支持按以下维度检索和组合筛选：

- 订单号、任务号、设备号。
- 时间范围、模块、线程 ID、错误码、关键字。
- 查看命中日志及前后文日志。

### 5.3 订单生命周期分析

系统根据稳定的接口协议和日志规则关联订单链路：

```text
addTask(orderId)
-> taskId
-> 线程 ID / 设备号 / 状态上报
-> 开始执行
-> 执行中状态
-> 结束或失败
```

页面展示：

- 订单接收时间、开始执行时间、关键状态上报时间、结束/失败时间。
- 总耗时和各阶段耗时。
- 最终状态、关联模块和关联日志证据。
- 未找到节点或链路不完整时的明确提示。

V1 展示耗时数据，但不定义“慢订单”阈值或告警。

### 5.4 失败原因分析

- 依据错误码、状态协议和日志特征匹配已知诊断规则。
- 每项结果须展示：可能原因、命中规则、对应日志证据、日志位置和建议处理方向。
- 未命中规则时，显示“未匹配已知原因”，不得生成未经验证的结论。
- 规则由研发维护，随产品版本发布；现场实施和技术支持不在线编辑规则。

## 6. 验收标准

- 现场实施可在 Linux 服务器上完成多模块日志采集并生成标准日志包。
- 可按时间、订单号、任务号、设备号完成采集。
- 技术支持可成功上传并检索有效日志包。
- 对提供的成功、失败、慢订单样本，系统可正确还原已定义的生命周期节点和耗时。
- 对已配置错误码/日志特征，系统能展示正确的可能原因及原始日志证据。
- 上传日志及分析结果在 30 天后自动清理。
- 对日志过大、格式错误、缺失模块、解析失败等情况提供明确提示。

## 7. 假设与风险

- V1 假设 `addTask` 相关日志可解析出 `orderId` 与 `taskId` 的关联。
- 若日志中不记录 `taskId`，需后续确认是否允许使用只读数据库查询 `task_group` 表补全映射。
- V1 假设相关模块在同一服务器；跨服务器日志链路纳入后续版本。
- 日志将从客户现场传至公司内部，当前虽未提出客户限制，仍需记录为交付风险，并在推广前确认客户数据外传和留存要求。
- 研发需提供各模块的日志样本、状态协议、错误码定义和已知问题规则清单。
