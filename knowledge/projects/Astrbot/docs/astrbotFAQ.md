# AstrBot FAQ

> 本文整理 AstrBot 使用过程中关于人格和会话规则的常见问题。

## 一、AstrBot 中的人格如何设置？

### 1. 人格是什么

人格用于定义 AstrBot 的角色身份、工作目标、回答风格和行为边界。它主要通过系统提示词影响模型的行为。

人格本身不等于知识库、插件或业务 API。人格只能告诉 AI“应该如何工作”，不能自动赋予它读取钉钉文档、查询 GitHub 或 @同事的权限。后续还需要配置相应的知识库、工具或插件。

官方文档：

- [自定义规则](https://docs.astrbot.app/use/custom-rules.html)
- [AstrBot 配置文件](https://docs.astrbot.app/dev/astrbot-config.html)

### 2. 如何创建人格

进入 AstrBot WebUI：

```text
左侧菜单 -> 人格 -> 创建人格
```

也可以直接访问：

```text
http://你的服务器地址:6185/persona
```

创建人格时主要填写以下内容：

| 字段 | 作用 |
| --- | --- |
| 人格 ID | 人格的唯一标识，例如 `dingtalk_project_assistant` |
| 系统提示词 | 定义人格角色、工作目标、回答风格和行为约束 |
| 自定义报错回复 | LLM 请求失败时显示的提示，可选 |
| 人格能力 | 选择该人格可以使用的工具、MCP 和 Skills |
| 预设对话 | 使用示例对话帮助模型理解角色和表达方式 |

填写完成后点击“保存”。

### 3. 如何让人格生效

#### 设置为默认人格

进入：

```text
配置 -> 模型配置 -> 默认采用的人格
```

选择刚刚创建的人格，例如：

```text
dingtalk_project_assistant
```

这样，没有特殊规则的会话都会使用该人格。

#### 只给指定钉钉群使用

进入：

```text
自定义规则 -> 创建规则
```

选择对应的钉钉群会话，并配置：

```text
启用消息处理：是
启用 LLM：是
聊天模型：选择需要的模型
人格：dingtalk_project_assistant
```

这样可以让不同钉钉群使用不同人格，例如研发群使用“项目协作助手”，普通群使用默认人格。

### 4. 人格示例：研发项目协作助手

人格 ID：

```text
dingtalk_project_assistant
```

系统提示词：

```text
你是“研发项目协作助手”，服务于公司研发团队，主要工作场景是钉钉群聊。

你的主要职责：

1. 阅读和总结已经授权给你的项目文档、需求文档、技术方案和会议纪要。
2. 根据项目资料回答研发人员的问题。
3. 整理项目进度、风险、阻塞事项和下一步计划。
4. 协助生成周报、日报、会议纪要和任务清单。
5. 根据用户明确要求，提醒相关同事提交周报、更新任务或提交代码。
6. 如果已经接入 GitHub、GitLab、Jira 或其他项目系统，查询任务和代码状态。

回答要求：

1. 使用简洁、清晰、适合钉钉群聊的中文。
2. 总结项目资料时，优先使用以下结构：结论、已完成事项、未完成事项、风险和问题、下一步计划。
3. 不要编造文档中不存在的内容。
4. 如果没有读取到文档、没有访问权限或资料不完整，要明确说明。
5. 不要把“建议通知某人”说成“已经通知某人”。
6. 不要把“建议提交代码”说成“代码已经提交”。
7. 涉及通知同事、创建任务、修改项目数据或发送外部消息时，先说明将要执行的动作；如果系统要求确认，必须等待确认后再执行。
8. 不要泄露 API Key、密码、Access Token、内部链接或其他敏感信息。
9. 对不确定的信息标注“不确定”，并说明需要补充的资料。
```

在钉钉群中可以这样测试：

```text
@AstrBot 请根据项目文档总结当前订单系统的开发进度。
```

```text
@AstrBot 帮我生成本周订单项目周报，包含完成事项、风险、阻塞问题和下周计划。
```

### 5. 预设对话示例

创建人格时，可以添加一组用户消息和 AI 回答：

用户消息：

```text
请帮我整理订单项目周报。
```

AI 回答：

```text
好的，我会按照以下结构整理：

1. 本周已完成事项
2. 当前进行中的工作
3. 风险与阻塞问题
4. 下周计划
5. 需要其他同事配合的事项

如果资料不足，我会明确标注缺失内容，不会自行编造。
```

预设对话不是实际业务数据，只是帮助模型更稳定地理解角色和回答格式。

## 二、自定义规则和配置文件路由规则有什么区别？

两者都可以按 UMO 匹配消息会话，但作用层级不同：

```text
配置文件路由规则：决定会话使用哪一整套配置文件
自定义规则：在配置文件基础上，对指定会话进行更高优先级的局部覆盖
```

### 1. 配置文件路由规则

入口通常是：

```text
WebUI -> 机器人 -> 编辑机器人 -> 配置文件 -> 路由规则
```

路由规则把某个 UMO 映射到一个配置文件。

UMO 格式为：

```text
[平台ID]:[消息类型]:[会话ID]
```

例如：

```text
dingtalk:GroupMessage:研发群会话ID -> dingtalk_rd
```

含义是：该钉钉研发群先使用 `dingtalk_rd` 配置文件。

配置文件可以作为一套完整的基础配置，包含默认模型、默认人格、唤醒词、回复规则、限流、白名单和其他可配置项。默认配置文件是 `default`，通常位于：

```text
data/cmd_config.json
```

WebUI 新建的其他配置文件通常位于：

```text
data/config/abconf_*.json
```

适合使用配置文件路由的场景：

- 研发群、客服群、测试群需要不同的整套配置；
- 一批会话需要复用同一套模型、人格和工具配置；
- 希望将不同业务环境隔离成不同配置模板。

### 2. 自定义规则

入口通常是：

```text
WebUI -> 自定义规则 -> 创建规则
```

官方文档列出的自定义规则能力包括：

- 是否启用该会话的消息处理；
- 是否对该会话启用 LLM；
- 是否启用 TTS；
- 指定聊天模型、STT 模型和 TTS 模型；
- 指定该会话使用的人格。

适合使用自定义规则的场景：

- 只想给某一个群切换人格；
- 只想给某个群换模型；
- 暂时关闭某个群的 AI 回复；
- 在相同基础配置上，对个别会话做差异化设置。

自定义规则不需要复制一整份配置文件，适合做会话级微调。

### 3. 两者的优先级

官方文档说明：自定义规则的优先级高于配置文件。

例如，先配置路由：

```text
dingtalk:GroupMessage:研发群会话ID -> dingtalk_rd
```

再配置自定义规则：

```text
消息来源：该研发钉钉群
启用 LLM：是
聊天模型：指定研发模型
人格：dingtalk_project_assistant
```

最终效果是：

```text
钉钉群消息
  -> 路由规则选中 dingtalk_rd 配置文件
  -> 自定义规则覆盖该群的模型和人格
  -> 使用 dingtalk_project_assistant 回复
```

因此，`dingtalk_rd` 提供通用的研发环境配置，而自定义规则可以把某个具体项目群切换为专属人格。

### 4. 推荐的实际配置方式

可以按以下层次设计：

```text
default
  -> 所有普通会话

dingtalk_rd
  -> 钉钉研发群的通用模型、知识库和工具配置

配置文件路由
  -> 所有研发钉钉群使用 dingtalk_rd

自定义规则
  -> 订单项目群：订单项目助手人格
  -> 周报群：周报助手人格
  -> 测试通知群：关闭 LLM，仅用于通知
```

### 5. 路由规则的通配符注意事项

配置文件路由支持通配符，但重叠规则应当谨慎配置。建议把精确规则放在宽泛规则之前：

```text
dingtalk:GroupMessage:订单群ID -> order_project
dingtalk:: -> dingtalk_rd
```

不要优先放置宽泛规则：

```text
dingtalk:: -> dingtalk_rd
dingtalk:GroupMessage:订单群ID -> order_project
```

否则宽泛规则可能先匹配，导致精确规则无法按预期生效。

## 三、与钉钉研发协作场景的结合

推荐采用以下分层：

```text
人格
  -> 规定回答方式、角色和行为边界

配置文件路由
  -> 为研发群提供统一的模型、工具和基础能力

自定义规则
  -> 为具体项目群指定专属人格和模型

知识库或文档插件
  -> 提供项目文档和技术方案内容

GitHub/GitLab 插件
  -> 查询代码提交、Issue、PR 和任务状态

钉钉通知插件
  -> 发送群消息、私聊消息或真正 @成员
```

人格不会自动获得钉钉文档或代码仓库权限。要实现文档阅读、周报催交和代码状态查询，还需要配置知识库、工具或对应插件。

## 四、接入钉钉后，如何定时搜集群消息并在 17:00 总结？

### 1. 先理解消息获取边界

AstrBot 不能主动从钉钉拉取任意群的历史消息。它只能处理钉钉实际推送给机器人的消息。

通常可以处理的内容包括：

- 群成员 `@机器人` 的消息；
- 机器人被回复或互动产生的消息；
- 钉钉开放平台实际推送给机器人的事件。

通常不能直接获取：

- 机器人加入群之前的历史消息；
- 没有推送给机器人的全部普通群消息；
- 任意时间范围内的钉钉群聊历史记录。

因此，能否总结全量群聊，首先取决于钉钉是否会把未 `@机器人` 的普通群消息推送给该机器人。

### 2. 如何验证机器人能收到普通群消息

在测试群发送两条不 `@机器人` 的普通消息：

```text
今天完成了订单接口开发。
```

```text
测试环境还缺少支付配置。
```

然后查看 AstrBot 的 Docker 日志：

```bash
docker ps
docker logs -f <AstrBot容器名>
```

判断方式：

- 日志中能看到普通消息：可以继续实现消息采集和日报；
- 日志中看不到普通消息、只能看到 `@机器人` 的消息：AstrBot 无法仅靠配置获得完整群聊，应该改用工作记录收集或企业级消息归档方案。

### 3. 推荐方案：群消息日报插件

正式场景建议实现“消息采集插件 + 持久化存储 + 定时总结”，而不是只依赖临时群聊上下文。

```text
钉钉群消息事件
  -> AstrBot 接收到消息
  -> 插件判断是否为目标群
  -> 保存到 SQLite 或 Markdown
  -> 每工作日 17:00 读取当天记录
  -> LLM 分段总结
  -> 将日报发送回原钉钉群
```

插件配置示例：

```json
{
  "enabled_groups": [
    "dingtalk:GroupMessage:目标群会话ID"
  ],
  "timezone": "Asia/Shanghai",
  "summary_cron": "0 17 * * 1-5",
  "min_message_count": 8,
  "exclude_bot_messages": true,
  "retention_days": 30
}
```

`0 17 * * 1-5` 表示每个工作日 17:00；每天都执行则使用：

```text
0 17 * * *
```

采集时建议持久化以下字段，并以消息 ID 去重：

```text
群会话 ID、消息 ID、发送人 ID、发送人昵称、消息时间、文本内容、附件说明
```

AstrBot 内置群聊上下文主要是内存中的滚动记录，适合让机器人理解近期对话；它不适合作为正式日报的数据源，因为重启后可能丢失，且不利于审计和长期检索。

### 4. 17:00 总结提示词示例

```text
请根据以下“今日群聊记录”生成研发群日报。

要求：
1. 仅依据聊天记录，不要补充未出现的事实。
2. 输出：已完成事项、进行中事项、风险/阻塞、待确认事项、明日计划。
3. 如记录中没有某项，写“未提及”。
4. 不输出个人隐私、密码、Token、内部敏感链接。
5. 控制在 500 字以内，适合直接发钉钉群。
```

输出示例：

```text
【订单项目群日报｜8 月 11 日】

已完成
- 完成订单退款接口联调。
- 修复库存扣减并发问题。

进行中
- 支付回调异常重试方案评审中。

风险与阻塞
- 测试环境缺少第三方支付沙箱配置。

待确认
- 是否本周上线退款功能。

明日计划
- 完成支付回调测试。
- 补充退款接口压测报告。
```

### 5. 是否可以使用 AstrBot 内置“未来任务”

可以先用于验证定时推送。先在配置中启用：

```text
配置 -> 主动型 Agent -> 启用
```

然后在目标群对机器人说：

```text
@AstrBot 每个工作日 17:00 总结今天本群已收到的讨论，按完成事项、风险、待办和明日计划输出，并发送到本群。
```

AstrBot 会创建 Cron 任务，可在 WebUI 的“未来任务/定时任务”页面查看、编辑和删除。

需要注意：主动任务是实验性能力。官方主动 Agent 页面未将钉钉列入主动推送平台，但当前钉钉适配器文档和源码标记为支持主动消息推送，存在文档版本差异。正式使用前，应在测试群创建一个短时间任务验证。

如果内置定时任务无法向钉钉群主动发送消息，可以在插件中调用钉钉群消息接口：

```http
POST https://api.dingtalk.com/v1.0/robot/groupMessages/send
```

请求示例：

```json
{
  "robotCode": "你的钉钉应用 ClientID",
  "openConversationId": "目标群会话ID",
  "msgKey": "sampleMarkdown",
  "msgParam": "{\"title\":\"群日报\",\"text\":\"日报内容\"}"
}
```

请求头：

```text
x-acs-dingtalk-access-token: 应用访问令牌
Content-Type: application/json
```

### 6. 如何定时互动，提高成员对机器人的关注

推荐固定、低频的工作互动，而不是随机刷屏。

上午 10:30 可以发送：

```text
【项目进度快速同步】

请大家用一句话回复：
1. 今天计划完成什么？
2. 是否有阻塞需要协助？

机器人会在 17:00 汇总，不需要重复描述。
```

下午日报后可以发送：

```text
今日共识已整理。请相关负责人确认“待确认事项”是否需要转为任务。
```

AstrBot 还提供群聊随机主动回复能力，可对非 `@机器人` 的群消息按概率回应。该能力适合偶尔参与，不适合作为定时日报。

配置示例：

```json
{
  "provider_ltm_settings": {
    "active_reply": {
      "enable": true,
      "method": "possibility_reply",
      "possibility_reply": 0.02,
      "whitelist": [
        "dingtalk:GroupMessage:目标群会话ID"
      ]
    }
  }
}
```

建议从 `0.01`（约 1%）开始测试，并仅对白名单群启用。该设置应放入目标群使用的配置文件，再通过配置文件路由分配给该群。

### 7. 无法采集普通群消息时的替代方案

如果钉钉没有把普通群消息推送给机器人，可要求成员主动提交结构化工作记录：

```text
@AstrBot 工作记录

已完成：
- 完成订单退款接口开发。

进行中：
- 支付回调联调。

阻塞：
- 缺少测试环境配置。
```

机器人保存这些明确记录，并在 17:00 汇总。对于需要完整采集聊天记录的企业场景，应咨询钉钉管理员是否具备企业级消息归档能力，并同时满足员工告知、企业授权和数据合规要求。

## 五、群成员 @机器人后，能否读取钉钉群文档并回复总结？

可以实现，但需要增加“钉钉文档读取插件”；这不是 AstrBot 钉钉接入后的开箱即用能力。

### 1. 目标流程

```text
群成员 @机器人 + 文档链接
  -> 插件解析文档 ID
  -> 使用钉钉应用凭据调用文档读取接口
  -> 下载并提取文档正文
  -> LLM 总结
  -> 在原钉钉群回复总结
```

群成员可以这样发送：

```text
@AstrBot 请读取并总结这个文档，重点说明风险和待办：
https://docs.dingtalk.com/i/team-docs/xxxxxx
```

机器人可以在原群回复：

```text
文档总结：

1. 核心目标
- 完成订单退款能力上线。

2. 当前风险
- 测试环境支付沙箱尚未配置。
- 接口压测结果未完成。

3. 待办
- 张三：补充压测报告。
- 李四：完成测试环境配置。
```

### 2. 实现条件

#### 必须提供文档标识

成员需要发送文档链接、文档 ID 或上传文件。只说“读取群里的《订单方案》”通常不够，除非插件已经维护“文档名称 -> 文档 ID”的索引。

#### 钉钉应用必须拥有文档读取权限

机器人被加入群，不代表它自动拥有所有群文档的访问权限。文档需要允许对应钉钉应用访问，或由企业管理员在钉钉开放平台授予相应的文档、云盘或组织权限。

#### 插件应承担的职责

```text
解析文档链接
  -> 识别文档类型和文档 ID
  -> 校验调用人和目标群是否有权限
  -> 调用钉钉文档 API 获取内容
  -> 将内容转换为纯文本或 Markdown
  -> 对长文档分段总结
  -> 回复结果并记录审计日志
```

### 3. 能否在回复中真实 @ 发起人

当前 AstrBot 钉钉内置适配器可以在原群回复，但不能可靠地发送真正的钉钉成员 `@` 提醒。它可以识别用户发来的 `@`，但当前群消息发送实现没有启用成员 `@` 参数。

因此：

```text
当前内置能力：
群成员 @机器人 -> 机器人在原群回复总结
```

```text
需要额外扩展：
群成员 @机器人 -> 读取文档 -> 在群内真实 @ 发起人并回复总结
```

在没有扩展前，可以使用普通文本：

```text
张三，文档总结如下：……
```

若要触发真正的钉钉 `@张三` 通知，插件需要取得张三的钉钉用户 ID，并调用支持成员 `@` 的钉钉消息或互动卡片接口。

### 4. 推荐实施顺序

```text
第一步：@机器人 + 钉钉文档链接 -> 在原群生成总结
第二步：增加文档权限校验、长文档分段和知识库入库
第三步：增加真实 @ 发起人、任务创建和日报汇总
```

不要直接将文档全文或敏感附件发送回群。插件应限制可读取的群和文档范围，避免泄露内部资料、密码、Token 和敏感链接。

## 六、AstrBot 在私聊和群聊中可以做什么

推广 AstrBot 时，建议优先推广能够减少重复整理、查资料和同步进度的功能，而不是简单宣传“可以和 AI 聊天”。

### 1. 私聊中的功能

私聊适合个人效率场景，成员可以单独使用，不会打扰群聊。

#### 文档总结和知识库问答

```text
@AstrBot 总结这份需求文档，给我 5 条重点。
```

```text
@AstrBot 根据公司的研发规范，代码提交前需要检查什么？
```

#### 日报、周报和汇报材料

```text
@AstrBot 根据以下工作记录生成我的周报：……
```

#### 文案和沟通辅助

```text
@AstrBot 把这段通知改得更专业、简洁：……
```

也可以让机器人帮助生成邮件、公告、会议邀请、项目汇报和发布说明。

#### 编程与技术排障

```text
@AstrBot 解释这个 Python 报错，并给出排查步骤：……
```

```text
@AstrBot 根据这个需求拆分开发任务，并给出测试点。
```

#### 个人提醒和任务整理

```text
@AstrBot 明天上午 9 点提醒我检查订单项目测试结果。
```

定时任务属于实验性能力，使用钉钉主动推送前应先在测试会话验证。

### 2. 群聊中的功能

群聊适合项目协作、资料查询和团队同步。建议通过固定命令或 `@AstrBot` 触发，避免机器人随机刷屏。

#### 项目群日报

成员可以使用统一模板提交工作记录：

```text
@AstrBot 工作记录

已完成：
- 完成退款接口联调

进行中：
- 支付回调测试

阻塞：
- 缺少测试环境支付配置
```

机器人可以在每天 17:00 汇总为：已完成、进行中、风险阻塞、待确认和明日计划。

#### 会议纪要与行动项

```text
@AstrBot 总结刚才的讨论，输出决策、待办、负责人和截止时间。
```

#### 项目文档问答

```text
@AstrBot 根据项目文档回答：这个需求的验收标准是什么？
```

前提是文档已经进入 AstrBot 知识库，或已开发钉钉文档读取插件并配置了访问权限。

#### 代码仓库和研发通知

接入 GitHub、GitLab 或其他代码平台后，可以向群里推送：

- Pull Request 创建、合并和评审状态；
- Issue 创建、分配和关闭；
- main 分支构建失败；
- 版本发布和紧急修复；
- 某个项目长时间没有提交。

这类“状态通知”适合先推广，因为内容客观、自动化程度高。自动催促某位同事提交代码，则需要额外的人员身份、任务系统和消息 @能力。

#### 群内快速问答和任务整理

```text
@AstrBot 总结今天的项目讨论。
```

```text
@AstrBot 把这段需求转成开发任务和验收标准。
```

```text
@AstrBot 列出当前讨论中还没有明确负责人的事项。
```

### 3. 私聊和群聊功能对照

| 功能 | 私聊 | 群聊 |
| --- | --- | --- |
| 文档摘要 | 适合个人阅读 | 适合项目资料和会议材料共享 |
| 知识库问答 | 个人查询 | 团队统一查询规范和流程 |
| 周报/日报 | 生成个人汇报 | 汇总项目成员进度 |
| 会议纪要 | 整理个人笔记 | 输出团队决策和行动项 |
| 代码排障 | 个人技术助手 | 团队共享排障结论 |
| GitHub/GitLab 通知 | 个人订阅 | 项目群统一接收 |
| 定时提醒 | 个人任务提醒 | 项目节点、日报和发布提醒 |
| 任务分派 | 私人待办 | 需要额外的任务系统和权限 |

### 4. 推荐推广顺序

建议按照以下顺序在公司内推广：

```text
第一阶段：文档总结、知识库问答、会议纪要
第二阶段：日报/周报生成、代码仓库通知
第三阶段：定时收集、项目进度汇总、任务创建
第四阶段：真实 @成员、自动催办、业务系统联动
```

先从低风险、立即可见的功能开始，例如“总结会议”和“查询研发规范”。成员感受到实际节省时间后，再逐步增加自动催办和业务系统操作。

### 5. 推荐的群公告

```text
本群已接入 AstrBot，可用于：

1. @AstrBot 总结文档或会议讨论
2. @AstrBot 查询项目规范和内部资料
3. @AstrBot 生成日报、周报和测试用例
4. @AstrBot 解释报错、拆解需求、整理待办
5. 接收 GitHub/GitLab 的项目状态通知

请勿发送密码、Token、客户隐私和未授权内部资料。
```

### 6. 使用边界

AstrBot 的人格只负责定义角色和回答方式；知识库、插件和外部 API 才负责提供文档、代码仓库、任务系统和通知能力。当前钉钉适配器也不适合把“真实 @某位同事”作为默认能力，涉及人员通知、任务创建和敏感文档读取时，应增加权限校验、操作确认和审计日志。

## 七、Docker 部署 AstrBot 的基础概念

### 1. 镜像、容器和宿主机的关系

```text
宿主机：运行 Docker 的 Linux 服务器
  -> Docker 镜像：AstrBot 的只读软件模板
  -> Docker 容器：基于镜像实际启动的 AstrBot 运行实例
```

镜像名不是本地目录，而是远程软件包坐标。例如：

```text
m.daocloud.io/docker.io/soulter/astrbot:latest
```

可理解为：

```text
m.daocloud.io       镜像仓库或加速服务
docker.io            上游 Docker Hub
soulter              用户或组织
astrbot              镜像仓库名称
latest               镜像标签或版本
```

`docker run` 会先在本地查找这个镜像；找不到时从对应仓库拉取，然后基于它创建并启动一个新容器。

### 2. `docker run -itd --name astrbot` 的含义

```bash
docker run -itd --name astrbot ...
```

其中：

| 参数 | 含义 |
| --- | --- |
| `docker run` | 基于镜像创建并启动新容器 |
| `-i` | 保持标准输入打开 |
| `-t` | 分配虚拟终端 |
| `-d` | 后台运行容器 |
| `--name astrbot` | 将新容器命名为 `astrbot` |

对于 AstrBot 这类长期运行的 Web 服务，最关键的是 `-d`。`-i` 和 `-t` 通常不是必须，因此也可使用：

```bash
docker run -d --name astrbot ...
```

容器命名后可直接操作：

```bash
docker logs -f astrbot
docker restart astrbot
docker stop astrbot
docker start astrbot
```

### 3. 端口映射：`-p 6185:6185`

Docker 端口格式为：

```text
-p 宿主机端口:容器端口
```

因此：

```bash
-p 6185:6185
```

表示：

```text
Linux 服务器的 6185 端口
  -> AstrBot 容器内部的 6185 端口
```

所以可使用：

```text
http://服务器IP:6185
```

访问 AstrBot WebUI。

也可以改为：

```bash
-p 8080:6185
```

此时从服务器外部通过 `8080` 访问，但容器内 AstrBot 仍使用 `6185`。

`-p 6199:6199` 同理，通常与 OneBot v11 反向 WebSocket 能力相关；未使用该能力时，可按实际部署需求决定是否暴露该端口。

### 4. 目录挂载：`-v /opt/astrbot/data:/AstrBot/data`

Docker 目录挂载格式为：

```text
-v 宿主机目录:容器内目录[:权限模式]
```

因此：

```bash
-v /opt/astrbot/data:/AstrBot/data
```

表示：

```text
服务器真实目录 /opt/astrbot/data
  -> 映射为容器内目录 /AstrBot/data
```

AstrBot 在容器内读写 `/AstrBot/data`，实际数据保存在服务器的 `/opt/astrbot/data`。这通常包括：

```text
配置、数据库、插件、知识库、上传文件、工作区和任务数据
```

该挂载未声明权限时默认为 `rw`，即容器可以读写：

```text
-v /opt/astrbot/data:/AstrBot/data
等价于
-v /opt/astrbot/data:/AstrBot/data:rw
```

AstrBot 需要保存配置、安装插件和写入数据库，因此 `data` 目录不能设为只读。

### 5. `:ro` 与 `:rw`

`ro` 表示只读，`rw` 表示可读写，后者是默认值。

例如：

```bash
-v /opt/projects/order-system:/workspace/order-system:ro
```

容器内的 AstrBot 或 Agent 可以读取和分析 `/workspace/order-system`，但不能修改、删除、提交或推送宿主机的项目代码。

这里的“宿主机”指运行 Docker 的 Linux 服务器，不是 Docker 容器。

公司服务器上，如果只需让 Agent 分析代码，建议优先使用只读挂载：

```bash
-v /opt/projects/order-system:/workspace/order-system:ro
```

### 6. 两条时区挂载的含义

```bash
-v /etc/localtime:/etc/localtime:ro
-v /etc/timezone:/etc/timezone:ro
```

它们将宿主机 Linux 的时区规则和时区名称以只读方式提供给容器，影响日志时间、文件时间和定时任务触发时间。

建议同时在 AstrBot 配置中设置：

```text
timezone: Asia/Shanghai
```

### 7. 为什么首次启动参数很多，后续只需要重启

```bash
docker run ...
```

同时完成“创建容器”和“启动容器”。端口、目录挂载、重启策略、镜像和容器名都会保存到容器元数据中。

```bash
docker restart astrbot
```

只会按首次创建时保存的配置重启已有容器，不会重新拉取镜像或重新指定端口、目录挂载。

### 8. 修改创建参数时是否需要重建容器

大多数创建参数，例如镜像版本、端口映射、目录挂载和容器名，不能直接修改，需要重建容器：

```bash
docker stop astrbot
docker rm astrbot
docker run -d --name astrbot ...新的参数... 镜像名:标签
```

删除容器不等于删除挂载目录。只要保留：

```text
/opt/astrbot/data
```

AstrBot 的持久化数据通常仍会保留。重建前可使用下列命令查看当前容器配置：

```bash
docker inspect astrbot
```

## 八、Computer Use 与 Skills

### 1. `none`、`local` 和 `sandbox` 的区别

Computer Use Runtime 决定 Agent 是否可以执行代码、访问文件、调用 Shell 和使用电脑工具。

| 模式 | 实际能力 | 推荐使用场景 |
| --- | --- | --- |
| `none` | 不提供 Shell、Python、本地文件读写等电脑工具 | 普通群聊、知识库问答、文档总结、写作辅助 |
| `local` | 在 AstrBot 所在 Docker 容器中运行 Shell、Python 和文件工具 | 管理员维护、访问容器内文件或已挂载项目 |
| `sandbox` | 在隔离沙盒中运行 Shell、Python 和文件工具 | 多用户文件处理、生成 Excel/PDF、执行不完全信任的 Skill |

`none` 不是“不使用 Agent”，而是不给 Agent 不必要的本地执行权限。它仍可使用模型、人格、会话上下文、知识库和不依赖电脑运行时的工具。

### 2. 为什么要保留 `none`

很多场景只需要问答和检索：

```text
知识库问答、会议纪要、周报润色、需求拆解、流程查询、文档总结、代码解释
```

这些任务不需要让模型执行服务器命令。保持 `none` 可降低提示词注入诱导执行命令、读取敏感文件或误删数据的风险，也减少不必要的工具上下文和模型调用成本。

推荐原则：

```text
普通钉钉群：none
需要处理文件的专用机器人：sandbox
管理员维护场景：受限 local
```

### 3. Skills 是什么

Skill 是带有操作说明、脚本、模板和参考资料的任务包，不只是提示词。例如：

```text
skills/
└── weekly-report/
    ├── SKILL.md
    ├── scripts/
    ├── templates/
    └── references/
```

`SKILL.md` 告诉 Agent 如何完成任务；Computer Use Runtime 决定 Agent 是否真的能读取文件、运行脚本和生成结果。

上传本地 Skills 的入口：

```text
WebUI -> 插件 -> Skills
```

上传 `.zip` 后，每个 Skill 文件夹必须包含大小写完全一致的 `SKILL.md`。

### 4. Skills 的典型场景

| 场景 | 示例请求 | 解决的问题 |
| --- | --- | --- |
| 周报生成 | “根据今天工作记录生成 Excel 周报” | 手工汇总和格式不统一 |
| Word 文档处理 | “将需求文档转 Markdown，提取验收标准” | 文档格式杂乱、人工整理耗时 |
| PDF 分析 | “分析合同并列出风险条款” | 长 PDF 难以快速阅读 |
| 表格统计 | “汇总项目工时并生成图表” | 手工统计容易出错 |
| 代码审查 | “检查提交记录并给出风险” | 代码规范依赖人工记忆 |
| 发布说明 | “根据 Git 提交生成发布说明” | 发布内容容易遗漏 |

包含脚本、文件读写或 Python 的 Skill，需要使用 `local` 或 `sandbox`。对于公司多人使用场景，优先选择 `sandbox`。

### 5. `none` 能否实现知识库只读

`none` 能禁止 Agent 通过 Shell、Python 或文件工具直接修改容器文件，但不能单独保证知识库绝对只读。

原因是知识库写入还可能来自：

```text
WebUI 上传文件、知识库插件、MCP 工具、AstrBot HTTP API、第三方系统 API、自动归档插件
```

正确的只读控制应分层完成：

```text
Computer Use Runtime = none
  -> 禁止本地 Shell、Python 和文件操作

人格能力 / 工具选择
  -> 只启用知识库查询工具
  -> 禁止知识库导入、删除、写入类工具和 MCP

自定义规则
  -> 将只读人格绑定到普通钉钉群

管理员权限和 API Scope
  -> 仅管理员保留上传、删除和建库能力
```

系统提示词可补充“仅允许查询，不得写入或删除知识库”，但提示词不是安全边界，不能代替工具权限和 API 权限控制。

## 九、插件、MCP、指令和函数工具的作用

### 1. 概念速览

```text
插件：安装新的业务能力包
Skill：某类任务的标准操作流程
MCP：连接外部系统的标准协议
指令：用户明确输入的控制命令
函数工具：模型根据任务自动调用的具体能力
```

### 2. 插件

AstrBot 在 v3.4.0 后将插件命名为 Star。插件可扩展平台适配、指令、函数工具、配置页面、事件监听、业务逻辑和内置 Skills。

插件适合增加完整业务能力，例如：

```text
GitHub Webhook 通知、钉钉流式卡片、群消息归档、代码仓库监控、企业内部系统集成
```

### 3. MCP 的作用和场景

MCP（Model Context Protocol）让 AstrBot 以标准方式连接外部系统：

```text
AstrBot -> MCP Client -> MCP Server -> 外部系统
```

| MCP 场景 | Agent 能做什么 | 解决的问题 |
| --- | --- | --- |
| GitHub/GitLab | 查询提交、PR、Issue、分支和评审 | 不必反复切换代码平台查进度 |
| Jira/TAPD | 创建任务、查询负责人、更新状态 | 项目任务分散，状态同步靠人工 |
| 文档库 | 搜索技术方案、制度、会议纪要 | 内部资料难找、重复询问 |
| 数据库 | 查询订单、错误率、库存和日报指标 | 取数依赖数据人员 |
| CI/CD | 查询构建结果、部署状态和失败日志 | 构建失败定位和通知慢 |
| 工单系统 | 查询客户问题、创建工单、查看 SLA | 客服、产品和研发信息断层 |

如果 MCP Server 运行在远程服务上，AstrBot 只需通过网络调用它，通常不要求 Computer Use Runtime 设为 `local` 或 `sandbox`。

### 4. 指令

指令适合明确、可控的管理操作。用户必须主动输入。

| 指令 | 作用 | 典型场景 |
| --- | --- | --- |
| `/help` | 查看可用指令 | 新成员了解机器人 |
| `/sid` | 查看 UMO、用户 ID、群信息 | 配置管理员、白名单和路由规则 |
| `/name` | 为当前会话设置别名 | WebUI 中快速识别群聊 |
| `/reset` | 清空当前对话上下文 | 切换项目话题 |
| `/stop` | 停止当前 Agent 任务 | 终止错误或耗时任务 |
| `/stats` | 查看 Token 用量 | 控制模型成本 |
| `/provider` | 查看或切换模型服务 | 模型故障切换 |
| `/persona` | 查看或切换人格 | 在研发、周报等人格间切换 |

部分扩展指令依赖 `builtin_commands_extension` 插件。部分管理指令需要 AstrBot 管理员权限。

### 5. 函数工具

函数工具是模型可自动选择调用的具体能力。AstrBot 默认可提供网页搜索、待办提醒和代码执行器；插件和 MCP 也能注册函数工具。

| 场景 | 用户请求 | 模型自动动作 | 解决的问题 |
| --- | --- | --- | --- |
| 网页搜索 | “查最新 Python 版本信息” | 调用搜索工具并总结 | 模型知识过时 |
| 定时提醒 | “周五 17 点提醒我提交周报” | 创建 Cron 任务 | 固定事项容易遗忘 |
| 代码计算 | “计算这批订单异常率” | 调用 Python 工具计算 | 手工计算易错 |
| 项目查询 | “订单项目有哪些阻塞 Issue？” | 调用 Jira/GitLab 工具 | 手工查多个系统 |
| 文档总结 | “总结这份技术方案” | 调用文档检索工具 | 长文档阅读成本高 |
| 创建任务 | “把这三项待办建到 Jira” | 调用创建 Issue 工具 | 会议纪要需人工录入 |

### 6. 分享用总结

```text
插件解决“能加什么业务能力”；
Skill 解决“这类工作应该按什么流程做”；
MCP 解决“如何连接公司外部系统和真实数据”；
指令解决“用户如何明确控制机器人”；
函数工具解决“模型如何自动完成查询、计算、提醒和执行”。
```

对公司钉钉机器人的推荐组合：

```text
普通员工群：人格 + 知识库 + 只读 MCP + 指令，Runtime = none
研发/文档处理专用群：人格 + 文档/表格/PDF Skills + 只读 GitLab/Jira MCP，Runtime = sandbox
管理员私聊：管理指令 + 受限 local 或 sandbox + 项目维护工具
```

## 十、函数工具、Skills 与 Skill 脚本有什么区别？

可以按层级理解：

```text
函数工具：一个可直接调用的动作
Skill：完成一类任务的操作手册
Skill 中的脚本：操作手册里实际执行的程序
```

完整流程通常是：

```text
用户请求
  -> Agent 判断任务
  -> 需要时加载 Skill 操作说明
  -> 按说明调用函数工具或运行 Skill 脚本
  -> 返回结果
```

| 对比项 | 函数工具 | Skill | Skill 中的脚本/工具 |
| --- | --- | --- | --- |
| 本质 | 给模型调用的函数或 API | 任务流程说明包 | 实际执行处理的代码或命令 |
| 模型如何使用 | 直接发起 Tool Call | 先阅读 `SKILL.md`，再按流程执行 | 由 Shell、Python 或函数工具执行 |
| 参数形式 | 必须有明确 Schema，例如 `query`、`repo` | 不一定，主要是 Markdown 指令 | 由脚本参数或命令决定 |
| 是否需要运行环境 | 取决于工具实现 | 若只含说明则不一定；涉及脚本通常需要 | 通常需要 `local` 或 `sandbox` |
| 适合场景 | 单一步骤、查询或外部系统调用 | 多步骤、标准化和可复用流程 | 文件转换、统计、生成产物等具体计算 |

### 1. 周报生成示例

函数工具可以是：

```text
get_daily_records(date)
create_excel(template, data)
send_file(file_path)
```

模型可以直接完成：

```text
查询日报 -> 生成 Excel -> 发送文件
```

但当周报需要固定格式、数据去重、异常处理和校验时，应使用 Skill：

```text
weekly-report/
  SKILL.md
  templates/weekly-report.xlsx
  scripts/build_report.py
```

其中 `SKILL.md` 规定流程：

```text
1. 读取本周日报。
2. 排除重复记录。
3. 按“完成、进行中、风险、下周计划”分类。
4. 数据不足时标注“未提及”。
5. 使用指定 Excel 模板。
6. 生成后校验工作表和字段。
7. 再发送文件。
```

`scripts/build_report.py` 则是真正生成 Excel 的程序。

因此：

```text
函数工具 = “查日报”“发文件”等单个按钮
Skill = “生成周报应按哪些步骤、规则和模板完成”的 SOP
Skill 脚本 = “真正把 Excel 做出来”的执行程序
```

### 2. GitLab 发版检查示例

GitLab MCP 或函数工具可提供：

```text
list_merge_requests()
get_pipeline_status()
create_issue()
```

它们适合模型临时查询或执行单个操作。

一个 `release-check` Skill 则可定义完整发版检查流程：

```text
1. 查询 main 分支最近合并的 MR。
2. 检查 CI 是否全部成功。
3. 查找未关闭的 P0/P1 Issue。
4. 生成发布风险清单。
5. 存在阻塞时，不得输出“可发布”结论。
```

函数工具偏“能力原子”，Skill 偏“流程标准”。Skill 可以调用函数工具，也可以运行 Python、Shell 脚本；三者并不互斥。
