# 项目管控桌面应用技术选型清单

## 1. 选型目标与边界

本项目面向 AMR 搬运系统（RCS）项目的研发、交付与技术支持流程。由于大部分项目存在定制需求，应用需要将 WEOR 单、研发方案、定制代码、项目配置、现场发布和问题闭环关联起来。

第一期优先支持内网部署。协作服务管理项目流程和审计记录；桌面端在研发电脑上执行本地 Git、SSH、文件传输、本地 Skill 和现场发布操作。

现场发布优先支持可直接访问的 Linux 服务与 SSH 跳板机。只能通过浏览器操作的堡垒机保留人工执行和结果回填，不承诺自动化。

## 3. 关键架构约束

- 协作服务只管理流程、成员、消息、审计和同步；现场服务器连接与发布动作由用户桌面端执行。
- SSH 密码、私钥与模型密钥只保存在桌面端系统钥匙串，协作服务不保存客户现场凭据。
- 发布以版本化 YAML 清单驱动，支持多个 JAR 的依赖顺序、备份、健康检查和反向回滚。
- 远程发布不能做到数据库式原子事务，发布结果必须区分“成功”“已自动回滚”“回滚失败，需要人工处理”。
- 大模型只能生成建议、文档或待确认的发布计划；任何生产升级命令都必须由用户确认后执行。

## 4. 第一期开源项目参考优先级

1. [GitButler](https://github.com/gitbutlerapp/gitbutler)：桌面端主参考，覆盖 Tauri、Rust、TypeScript/React 与本地 Git 仓库管理。
2. [Mattermost](https://github.com/mattermost/mattermost)：协作服务主参考，覆盖 Go、PostgreSQL、用户权限、聊天和实时消息。
3. [Gitea](https://github.com/go-gitea/gitea)：Git 协作、用户权限、内网部署和 Docker Compose 的参考。
4. [OpenSSH](https://github.com/openssh/openssh-portable) 与 [Teleport](https://github.com/gravitational/teleport)：SSH、跳板机和安全访问的参考。

## 5. 暂缓项

- 浏览器堡垒机自动化：第一期仅支持人工执行发布任务，并回填执行结果与日志。
- Docker 现场发布：先预留服务管理适配器，后续再实现 Docker/Compose 发布。
- 公网 SaaS 多租户运营：数据模型预留 `tenant_id`，第一期优先内网部署。
- 自研 Git 或 SSH 协议栈：直接使用成熟的本机 Git CLI 与 OpenSSH，避免兼容性和安全成本。
- 让大模型直接执行生产升级：不允许模型绕过用户确认执行现场操作。
