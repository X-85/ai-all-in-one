# 钉钉项目问题收集沉淀机器人 MVP

> 本文定义项目问题收集沉淀机器人的最小可行产品（MVP），用于后续在 AstrBot 与钉钉机器人基础上开发。
> 核心原则：只要求人发起问题和确认关闭；中间讨论、关联、归纳和沉淀由机器人自动完成。

## 1. 目标

在钉钉项目群中，成员会持续提出问题并通过群聊共同排查、讨论和解决。但问题的原因、方案和结论经常散落在聊天记录中，后续难以查询、复盘和复用。

本 MVP 要解决的问题是：将一次自然发生的群聊问题讨论，自动沉淀为结构化的项目问题记录。

最终闭环：

```text
人发起问题
  -> 机器人无感收集相关群聊
  -> 机器人提炼过程、原因与方案
  -> 发起人确认是否解决
  -> 机器人保存可查询、可复盘的问题记录
```

## 2. 范围与非目标

### MVP 范围

1. 成员在钉钉项目群中通过 `@机器人` 发起问题。
2. 机器人自动记录问题，并在后台监听同一群的后续普通消息。
3. 机器人用 AI 判断消息与当前问题的相关性，并将相关消息加入问题时间线。
4. 机器人自动生成滚动摘要，包括现象、排查过程、候选根因、处理动作和后续建议。
5. 机器人检测到可能已解决的信号后，向问题发起人发送确认请求。
6. 发起人确认已解决后，机器人生成最终总结并保存问题记录。
7. 支持查看当前群未关闭问题，以及查询已关闭问题的最终总结。

### 明确不做

- 不要求回答者 `@机器人`、引用机器人消息、填写表单或输入问题编号。
- 不自动关闭问题，最终关闭必须由问题发起人确认。
- 不在 MVP 中做复杂的项目管理、工单分派、SLA、权限工作流或跨群关联。
- 不尝试追溯机器人启动或问题创建之前的历史聊天记录。
- 不要求机器人对每条群消息都回复，避免干扰正常沟通。

## 3. 用户交互

### 3.1 发起问题

成员在项目群中发送：

```text
@项目助手 测试环境无法登录，阻塞验收。
```

机器人创建问题并仅回复一次：

```text
已开始跟踪问题 #12：测试环境无法登录。
后续群聊中的相关讨论将自动归档；解决后请由发起人确认关闭。
```

创建时自动保存：问题文本、发起人、群 ID、发起消息 ID 和创建时间。

### 3.2 无感收集讨论

此后所有成员维持原有群聊习惯，无需操作机器人：

```text
Redis 好像连接数满了。
我看到了，maxclients 已到上限。
我先重启服务。
现在可以登录了。
建议增加连接数监控。
```

机器人在后台做以下工作：

1. 接收普通群消息事件。
2. 判断消息是否与当前未关闭问题相关。
3. 将相关消息记录到该问题的时间线。
4. 识别消息属于现象、排查、原因、处理、结果或建议中的哪一类。
5. 周期性更新内部摘要，不对每一条消息发送群回复。

### 3.3 请求确认

当机器人检测到“已恢复”“已修复”“可以访问”“问题解决”等可能已解决信号，或者指定时间内的讨论趋于稳定时，向问题发起人发出确认卡片或私聊提醒：

```text
问题 #12：测试环境无法登录

机器人整理的结论：
- 现象：测试环境无法正常登录，阻塞验收。
- 候选原因：Redis 连接数达到上限。
- 已执行处理：重启 Redis 服务后登录恢复。
- 后续建议：调整连接数上限并增加监控告警。

[确认已解决] [仍未解决] [补充说明]
```

只有问题发起人可以确认关闭；项目管理员可作为后续扩展的兜底确认人。

### 3.4 关闭与沉淀

发起人点击“确认已解决”后，机器人生成正式记录：

```text
问题 #12：测试环境无法登录
状态：已解决

现象：测试环境无法登录，阻塞验收。
原因：Redis 连接数达到上限。
处理：重启 Redis 服务，登录恢复。
预防：调整 maxclients，并增加连接数监控和告警。

发起人：张三
参与讨论：李四、王五
创建时间：2026-09-08 10:12
关闭时间：2026-09-08 10:35
```

机器人将最终总结和原始讨论索引保存到数据库，供后续查询、复盘和知识库导出。

## 4. 状态机

```text
                     发起人 @机器人 提出问题
                                  |
                                  v
                          OPEN（跟踪中）
                                  |
          机器人持续接收普通群消息、判定关联并更新摘要
                                  |
                                  v
             PENDING_CONFIRM（发现可能已解决，等待确认）
                        |                         |
               发起人确认已解决              发起人选择仍未解决
                        |                         |
                        v                         v
                RESOLVED（已沉淀）            OPEN（继续跟踪）
```

状态说明：

| 状态 | 含义 | 机器人行为 |
| --- | --- | --- |
| `open` | 问题正在讨论和排查 | 自动关联普通群消息，更新内部摘要。 |
| `pending_confirm` | 检测到可能已解决，等待发起人判断 | 发送确认卡片或私聊提醒，暂停重复提醒。 |
| `resolved` | 发起人确认解决 | 生成最终总结，保存记录，停止收集新消息。 |

## 5. 系统架构

```text
钉钉项目群
  |
  | 普通消息、@机器人消息、卡片动作
  v
AstrBot 钉钉适配器
  |
  v
项目问题沉淀插件
  |-- 问题状态机
  |-- 消息相关性判断
  |-- 解决信号检测
  |-- 摘要与结论生成
  |-- 钉钉消息/卡片发送
  |
  +--> SQLite（问题、时间线、总结、消息索引）
  |
  +--> AstrBot 配置的大模型（分类、关联、摘要）
```

### AstrBot 的职责

- 接入钉钉机器人并接收事件。
- 提供插件生命周期、消息事件监听、发送消息和调用大模型的能力。
- 承载 `astrbot_plugin_project_issues` 插件。

### 插件的职责

- 识别 `@机器人` 发起的问题。
- 查询同群的未关闭问题。
- 对普通消息做相关性分类和时间线归档。
- 维护每个问题的滚动摘要与状态。
- 向发起人请求关闭确认。
- 生成、保存和检索最终问题记录。

## 6. 最关键的技术前提

此 MVP 是否成立，取决于以下能力：

> AstrBot 接入的钉钉机器人必须能收到项目群内的普通消息事件，而不仅是 `@机器人` 的消息。

如果钉钉只向机器人下发 `@机器人` 消息，机器人无法无感收集自然讨论，本 MVP 的核心体验无法实现。

因此，开发的第一步不是数据库、AI 或卡片，而是进行消息可见性验证：

1. 将 AstrBot 钉钉机器人加入一个测试群。
2. 打开事件日志，分别发送普通消息、`@机器人` 消息、回复消息、图片和文件。
3. 检查 AstrBot 收到的事件是否包含群 ID、发送人、消息 ID、消息内容、时间和引用关系。
4. 确认普通文本消息能稳定进入插件事件流。

验证结论：

| 验证结果 | MVP 决策 |
| --- | --- |
| 可以接收普通群消息 | 按本文方案开发。 |
| 只能接收 `@机器人` 消息 | 无法实现无感收集；需要更换钉钉机器人接入类型，或调整为显式触发方案。 |

## 7. 消息关联策略

一个群可能同时有多个未关闭问题。MVP 需要尽量正确地将普通消息归到对应问题，但不能把 AI 判断当作绝对事实。

### 初版策略

1. 每个群默认只允许一个“活跃跟踪问题”。
2. 新问题创建后进入 `open` 状态，机器人主要围绕该问题收集后续消息。
3. 当该问题关闭后，机器人再切换到下一个问题。
4. 如果用户尝试在已有活跃问题时创建新问题，机器人提示：

```text
当前正在跟踪问题 #12「测试环境无法登录」。
请先确认该问题是否已结束；如确需并行跟踪，请由项目管理员启用多问题模式。
```

这个约束能显著降低第一版中的消息误关联问题。

### AI 判断规则

对每条普通文本消息，让模型输出结构化结果：

```json
{
  "relevant": true,
  "confidence": 0.92,
  "role": "investigation",
  "summary": "确认 Redis 连接数已到上限"
}
```

`role` 取值限定为：

- `symptom`：现象或影响
- `investigation`：排查过程
- `cause`：根因或候选原因
- `solution`：处理动作或解决方案
- `result`：修复结果或恢复确认
- `prevention`：后续预防建议
- `irrelevant`：与问题无关

只保存 `relevant=true` 且置信度达到设定阈值的消息；低置信度消息可仅保留原始索引，不进入最终总结。

## 8. 数据模型

MVP 使用 SQLite 即可，无需先引入远程数据库。

### `issues`

```text
id                  问题编号
group_id            钉钉群标识
creator_id          问题发起人标识
initial_message_id  发起消息标识
title               问题标题
description         原始问题描述
status              open / pending_confirm / resolved
current_summary     滚动摘要
final_summary       确认关闭后的最终总结
created_at          创建时间
confirm_requested_at 请求确认时间
resolved_at         关闭时间
```

### `issue_timeline`

```text
id                  时间线记录标识
issue_id            所属问题编号
message_id          钉钉原始消息标识
sender_id           发送人标识
content             原始文本内容
message_time        发送时间
relevance_score     AI 关联置信度
extracted_role      symptom / investigation / cause / solution / result / prevention
extracted_summary   对该消息的简短提炼
```

### `issue_confirmations`

```text
id                  确认记录标识
issue_id            所属问题编号
actor_id            操作人标识
action              resolved / still_open / supplement
content             补充说明（可选）
created_at          操作时间
```

## 9. 插件行为设计

### 9.1 发起问题

触发条件：群成员 `@机器人` 且消息不是关闭、查询等系统命令。

行为：

1. 从消息中提取问题描述。
2. 检查当前群是否已有 `open` 或 `pending_confirm` 问题。
3. 创建 `issues` 记录。
4. 在群内发送一次“已开始跟踪”的确认消息。

### 9.2 后台收集

触发条件：收到同一群普通文本消息，且存在 `open` 问题。

行为：

1. 过滤机器人自身消息、空消息、过长消息和明显无关的系统提示。
2. 调用 AI 判断相关性和消息角色。
3. 保存相关消息到 `issue_timeline`。
4. 每累计 N 条相关消息，或每隔 T 分钟，更新一次 `current_summary`。
5. 如果出现高置信度解决信号，进入确认候选流程。

### 9.3 解决信号与确认

候选解决信号包括：

- “已解决”“已修复”“恢复了”“可以了”“验证通过”；
- “重启后正常”“发布后正常”“现在能登录”；
- AI 从连续讨论中推断出已执行处理并获得成功结果。

机器人不能据此自动关闭，只能：

1. 生成当前结论草稿。
2. 将状态改为 `pending_confirm`。
3. 向发起人发送确认卡片或私聊提醒。
4. 收到发起人的操作后更新状态。

### 9.4 最终总结

发起人确认解决后，调用 AI 生成固定结构的总结：

```text
问题：
影响：
现象：
排查过程：
根因：
解决方案：
后续预防：
参与人：
```

模型只能基于问题原文和已归档时间线总结；对不确定内容标记“待确认”，不能编造根因或处理结果。

## 10. 验收标准

MVP 完成的最低标准：

1. 测试群中，成员可以通过 `@机器人 + 问题描述` 创建问题。
2. 机器人能接收同群后续普通文本消息。
3. 机器人能将至少 80% 的人工标注相关讨论正确归入当前唯一活跃问题。
4. 回答者无需使用问题编号、命令、表单或卡片。
5. 机器人不会自动关闭问题。
6. 发起人可以通过一个明确操作确认“已解决”或“仍未解决”。
7. 确认关闭后，系统能生成并保存包含问题、过程、原因、方案和预防建议的记录。
8. 已关闭问题可以按群和关键词查询并查看最终总结。

## 11. 开发顺序

1. **验证消息可见性**：确认 AstrBot 的钉钉适配器能收到普通群消息。
2. **建立最小插件**：实现 `@机器人` 创建问题和 SQLite 保存。
3. **建立时间线**：收集当前群唯一活跃问题期间的普通消息，先不引入 AI。
4. **接入 AI 分类**：过滤无关消息，为相关消息标记角色。
5. **实现滚动摘要**：生成内部摘要，暂不频繁群发。
6. **实现确认关闭**：以卡片或私聊让发起人确认。
7. **生成最终总结与查询**：保存并提供“未解决问题”“查询问题”能力。
8. **再评估增强功能**：多问题并行、互动卡片详情页、自动识别潜在问题、导出 Markdown、同步知识库等。

## 12. 风险与边界

| 风险 | 应对方式 |
| --- | --- |
| 机器人无法接收普通群消息 | 在开发前验证；若不支持，MVP 无法实现无感收集。 |
| 同时讨论多个问题导致误关联 | MVP 限制每群一个活跃问题；后续再做多问题分类。 |
| AI 将闲聊误判为相关内容 | 设置置信度阈值，保留原始消息索引，最终关闭由人确认。 |
| AI 编造原因或方案 | 仅基于时间线总结；不确定内容明确标记“待确认”。 |
| 机器人频繁打扰群 | 只在创建、请求确认、关闭时主动发消息；其他处理后台进行。 |
| 群聊包含敏感信息 | 明确采集范围和保存期限，限制机器人和数据库访问权限，避免把密钥、个人信息和无关聊天写入长期知识库。 |

## 13. 后续可扩展能力

在 MVP 验证后，再按需要增加：

- 多个并行问题的自动关联和人工纠偏；
- 项目负责人代替发起人关闭问题；
- 互动卡片中的问题详情、摘要和补充说明；
- 每周问题复盘报告、问题分类统计和高频根因分析；
- 导出 Markdown 到项目知识库；
- 相似历史问题检索和解决方案推荐；
- 与 GitLab、Jira、飞书文档、Confluence 或内部工单系统同步；
- 根据问题状态自动创建待办、告警或工单。

## 14. 一句话交接说明

> 基于 AstrBot 内置钉钉适配器开发“项目问题沉淀插件”：群成员只需 `@机器人` 发起问题，并在机器人提示后确认问题是否解决；机器人必须能够无感接收项目群普通消息，用 AI 自动关联讨论、提炼过程与解决方案，并在人工确认后将其沉淀为可查询、可复盘的问题记录。开发第一步是验证钉钉事件流能否将非 `@机器人` 的普通群消息传递给 AstrBot。
