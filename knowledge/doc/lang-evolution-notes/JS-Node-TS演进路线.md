# JS → Node → TS 演进路线

一句话版：**浏览器需要交互所以有了 JS，JS 要离开浏览器干活所以有了 Node，JS 工程变大难维护所以有了 TS。** 这不是三个孤立名词，是一条因果链，每一步都是下一步的原因。

配套速查（npm/tsc/tsgo 等工具命令）：[构建工具链速查](构建工具链速查.md)

## 一、JS 诞生（1995）：给网页加交互

网景公司为了"让网页能响应用户操作"（表单校验、按钮点击），让 Brendan Eich 花了十天设计了 JS（最初叫 Mocha，蹭 Java 热度改名 JavaScript）。

注意它的处境：**语言天生只有一个能跑的地方——浏览器**。浏览器负责执行 JS，并额外提供 `document`、`window` 这些网页能力。"JS 是前端脚本语言"这个印象由此而来——但准确说法是"当时唯一能跑 JS 的地方是浏览器"。

一个后续常见的词汇困惑在这里就能解决：微软很快反向工程出自己的实现 JScript，各家浏览器行为不一，于是 1997 年出台了统一标准 **ECMAScript**。所以教程里的 ES5、ES6 指的是标准版本号——**ES 是标准的名字，JS 是语言的俗名**，说的是同一门语言。

之后十年，Gmail、Google Maps 证明网页可以做成应用，JS 代码量开始膨胀；2008 年 Chrome 带来了高速的 V8 引擎——为下一步埋了伏笔。

## 二、Node 诞生（2009）：把 JS 拎出浏览器

出发点是两个：

1. **JS 出不了浏览器**：想在服务器、命令行里用 JS，没人提供文件、网络这些能力；
2. **服务器高并发难题**（C10K 问题）：Apache 那种"一个请求开一个线程"的模型，线程大部分时间阻塞在等数据库、等磁盘上，一万个并发连接内存就撑不住。

Ryan Dahl 的方案：**单线程事件循环 + 非阻塞 I/O**，所有 I/O 异步发起、回调排队，一个线程同时挂上万个连接。选 JS 不是因为 JS 好写后端，而是 JS 从出生就是"单线程 + 事件回调"文化（浏览器的 onclick 就是这么工作的），和这个模型天生匹配。

实现上，Node 做了三件事：

| 组成 | 作用 |
|------|------|
| V8 引擎 | 执行 JS 代码（和 Chrome 同款） |
| libuv | 事件循环 + 非阻塞 I/O 调度 |
| 标准库 | `fs`(文件)、`http`(网络)、`child_process`(子进程)、stdin/stdout(终端) |

关键意义：**浏览器给 JS 的是 `document` 和 `window`，Node 给 JS 的是 `fs` 和 `http`。语言没变，换的是周围的世界。** JS 从此能碰操作系统，后端服务器、CLI 工具、构建脚本全部解锁。

2010 年 **npm** 出现，生态开始滚雪球。npm 是随 Node 一起安装的**包管理器**：在 `package.json` 里声明项目依赖哪些别人写好的代码，一条 `npm install` 就从中央仓库（npm registry）自动下载齐全，放进 `node_modules` 目录。它把"复用别人的轮子"的成本压到一条命令——用轮子的人多了，写轮子的人也多了。

## 三、TS 诞生（2012）：给变大的 JS 加类型安全网

因果链的最后一环：Node 把 JS 从几十行的网页脚本变成了几十万行的工程项目，动态类型的维护成本爆炸——重构靠全局搜索，改个函数名全靠祈祷。

微软的 Anders Hejlsberg（C# 之父）给出方案：**TS = JS + 静态类型**。类型只在开发期做检查，运行前被剥掉，机器最终执行的仍是纯 JS。

所以 TS 不是新语言，是 JS 的"开发期安全网"——代码库越大，这张网越值钱。

再补一句：TS 不是第一个"给 JS 补类型"的尝试。CoffeeScript(2009)、Dart(2011) 都更早，但它们选择另造一套语法甚至另一门语言，再编译成 JS；TS 赢在克制——**做 JS 的超集，只加可擦除的类型**，存量 JS 代码和 npm 生态原封不动，迁移成本趋近于零。

## 四、路线没有停在 2012

主链到此讲完，但路线本身还在延伸，三个节点值得知道：

- **ES6/ES2015**：JS 语言自身的大升级（let/const、class、模块、Promise）。今天写的 JS 和 1995 年的 JS 观感已经完全不同，教程里的"ES6"就是这一年的标准。
- **Deno(2020) / Bun(2022)**：新的 JS 运行时出现，验证了"运行时可换"。Deno 的作者正是 Ryan Dahl 本人——Node 作者回来修正 Node 的遗憾。
- **Node 原生运行 TS（2024-2025）**：Node 加入了 type stripping，可以直接执行"可擦除语法"的 TS，不再需要先编译。因果链在此闭环：2012 年 TS 要靠编译器剥类型，如今运行时自己会剥了。

## 五、三个必要词汇

理清这条路线只需要分清三个词：

- **语言**：定义代码长什么样、有什么规则——JS、TS 都在这一层；
- **运行时**：代码在哪跑、能碰什么能力——浏览器是一种，Node 是另一种；
- **场景**：这套组合被拿去干什么——前端、后端、CLI 只是场景，不是语言的属性。

最常见的混淆就是拿场景给语言定性（"JS 是前端的"）。记住：同一门 JS，跑在浏览器里是前端，跑在 Node 里读文件、起进程就是后端或 CLI。

## 六、工程化：一个 JS/TS 项目怎么构建和运行

演进讲完，补一块实务：用这门语言从零到跑起来，标准动作是什么。几乎所有 JS/TS 项目——后端、CLI、前端——都遵循同一套流程：

```text
npm init        → 生成 package.json(项目清单:叫什么、依赖谁、有哪些命令)
npm install     → 按 package.json 装依赖,下载进 node_modules
写代码          → src/ 下的 .js 或 .ts 文件
npm run dev     → 开发时运行(具体命令定义在 package.json 的 scripts 字段)
npm run build   → 构建(可选,按场景,见下)
npm test        → 跑测试
```

三个关键认知：

1. **`package.json` 是项目的身份证兼总开关**。目录里看到它就知道这是个 Node 项目；里面的 `scripts` 字段定义所有命令的入口，`npm run xxx` 是一切操作的标准姿势。
2. **要不要"构建"，按场景分**。后端和 CLI 可以零构建——`node xxx.js` 直接执行，遵守可擦除语法的 TS 项目在新版 Node 上也能直接跑；前端必须构建——浏览器只认 HTML/CSS 和打包后的 JS，需要 esbuild/Vite 这类工具处理。**"构建步骤要不要存在"本身就是 JS 生态里一个真实的选型点**。
3. **TS 项目多一步**：传统流程要先用 `tsc`/`tsgo` 把 TS 编译成 JS 再运行；Node 支持原生 type stripping 后，这一步可以省（呼应第四节的"闭环"）。

记熟这套结构的原因很实际：**AI 生成 JS/TS 项目时，默认产出的就是 `package.json` + `src/` + `scripts` 这副骨架**。认识它，你就知道 AI 给了什么、去哪验收（`npm run dev` 能不能跑起来）、提修改意见怎么说到点上（"把启动命令加进 scripts"）。

## 七、因果链小结

```text
浏览器需要交互能力 → 有了 JS(1995)
JS 要离开浏览器干活 → 有了 Node(2009)
JS 工程变大难维护   → 有了 TS(2012)
```

## FAQ

约定：这里的问答随实际疑问追加，每条回答控制在几句话内；问题来自真实使用中的困惑，不预设。

**Q1：TS 运行前把类型剥掉了，那类型检查还有什么意义？**
类型检查发生在写代码和编译阶段，价值全是开发期的：编辑器即时报错、自动补全、重构时全局改名不出错。运行期本来就不需要它，机器只执行逻辑。

**Q2：学 TS 之前要先学 JS 吗？**
要。TS 是 JS 的超集，事件循环、异步、模块这些运行时知识全是 JS 的，TS 只是在上面加了类型标注规则。

**Q3：ES5、ES6、ES2015 这些词到底是什么？**
见第一节：ECMAScript 是 1997 年立的官方标准，ES5/ES6 是版本号；ES6 发布于 2015 年所以也叫 ES2015，之后标准一年一版，改用年份命名。

**Q4：Node 和浏览器执行 JS 用的是同一个引擎吗？**
都是 V8。差别在引擎之外的能力：浏览器配上 DOM/window 等网页能力，Node 配上 fs/http 等系统能力。也存在用别的引擎的运行时（如 Bun 用 JavaScriptCore）——这正是"运行时可换"的含义。

**Q5：为什么 Node 选 JS，而不是当时更成熟的语言？**
Node 的核心模型是"单线程事件循环 + 非阻塞 I/O"，而 JS 从出生就是事件回调文化（onclick），程序员不用换思维；何况 Ajax 浪潮下 JS 程序员正多。语言不是主角，模型匹配才是。

**Q6：为什么有些工具要求 Node ≥22，且只允许"可擦除语法"的 TS？**
Node 22.6 起引入 type stripping（后续版本默认开启），能直接运行不依赖编译特性的 TS（不用 enum、namespace 等）。代码遵守可擦除语法，整个编译步骤就省了——这正是第四节"闭环"的落地。

**Q7：Node 只是运行时，为什么能用它写常驻的代理服务？**
"运行时"不等于"跑一下就结束的脚本工具"，它指执行代码并提供能力的环境。程序退出还是常驻由代码决定：只写 `console.log` 就打印完退出；写上 `http.createServer(...).listen(3000)`，进程就挂在端口上等请求——这就是服务。`node xxx.js` 起服务、`python xxx.py` 起服务、`java -jar` 跑 Spring Boot 是同一个模式：命令只是启动入口，常驻是代码逻辑造成的。

**Q8：TS 和 JS 的核心区别在哪里？是解决"JS 臃肿"吗？**
核心区别是类型检查的时机：JS 运行时才知道类型对不对，TS 写代码时就报错。它解决的不是"臃肿"——字面上 TS 还让代码更长——而是"工程变大后动态类型的维护成本"：改名全靠祈祷变成编译器逐点报错，bug 到生产才炸变成编辑时画红线。注意 TS 不提升运行性能（类型运行前被剥掉），也不防逻辑错误。
