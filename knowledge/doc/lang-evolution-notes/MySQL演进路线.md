# MySQL 演进路线

一句话版：**个人网站买不起 Oracle，MySQL 用"够快、免费、好装"拿下整个 Web；真正让它从玩具变成主力库的，是被收购来的 InnoDB 引擎——事务与行级锁补上那口气之后，它陪着互联网从 LAMP 一路走到云时代，还给世界留下一个教训：接口兼容养大了整个"换内核"生态。**

## 一、买不起 Oracle 的 Web（1995）

九十年代的数据库市场是商业巨头的天下：Oracle、Sybase、DB2，按 CPU 和并发数收授权费——一台服务器几万到几十万美元。与此同时，Web 站点开始爆发：个人主页、论坛、中小网站，全都需要存数据，全都没有预算。

1995 年，芬兰程序员 Michael "Monty" Widenius 发布了自己攒了多年的数据库 MySQL——名字来自女儿 My。它的策略与巨头完全相反：**SQL 子集、极快的读、安装包五分钟跑起来**，2000 年起采用 GPL 开源。与 Linux、Apache、PHP 汇合后就是著名的 **LAMP 四件套**——整个 Web 1.0 时代的默认底座（PHP 与那段历史，见 Vue 篇开头）。WordPress、WikiMedia、Facebook 早期，全踩在 MySQL 上。

但它当年的"玩具"名声也不冤：默认引擎 MyISAM 只有**表级锁**——一张表同时只能一个写者，并发一上来就排队；**没有事务**——转账转一半断电，钱就真的少了一半；存储过程、视图、触发器一概没有（要到 5.0，2005 年才补齐）。它在互联网头十年能赢，赢在**最容易上车**，不是最强。

## 二、可插拔引擎与 InnoDB 接管（2000-2010）

Web 从"内容"变成"业务"，电商要支付、扣库存，没有事务就是事故。MySQL 的架构这时显出妙手：**SQL 层与存储引擎分离，引擎可插拔**——接口不变，存储层随便换。真正的答案来自芬兰同乡 Heikki Tuuri 的 **InnoDB**（2001 年起随 MySQL 附带）：事务（ACID）、**行级锁**、崩溃恢复、MVCC——见第五节。2010 年的 5.5 版起 InnoDB 成为默认引擎，MyISAM 时代结束。

这十年更精彩的是资本剧情，三年三步：

- **2005 年，Oracle 收购 Innobase**（InnoDB 的母公司）——数据库巨头买下了 MySQL 心脏的供应商；
- **2008 年，Sun 以 10 亿美元收购 MySQL AB**；
- **2010 年，Oracle 收购 Sun**——MySQL 落入死对头之手。

社区炸锅："Oracle 会饿死 MySQL 好卖自家 Oracle DB。"Monty 愤而 fork，2009 年出走创立 MariaDB（名字同样来自女儿 Maria——一个父亲给两个女儿各命名了一个数据库）。而后来的剧本出人意料：**Oracle 十几年持续投入 MySQL**——5.6、5.7 大幅进化，8.0（2018）补上现代 SQL（CTE、窗口函数、JSON），InnoDB 集群方案成型。对照 Redis 篇：**社区最怕的不是被收购，是失去兼容承诺的信誉；fork 是保险单，未必兑付，但必须存在**（MariaDB 至今活着，多数 Linux 发行版默认用它替代 MySQL）。

## 三、云时代：接口养出了整个替代生态（2010-2025）

云时代 MySQL 的角色变成了**接口本身**。AWS RDS 2009 年上线时第一个引擎就是 MySQL（全托管 MySQL 从此是各家云标配）；2014 年 AWS 发布 **Aurora**——保留 MySQL 协议与 SQL 接口，把存储层整个重做成"一写多读的共享存储"，性能数倍——"外壳不变，换内核"的教科书案例。这条路上站满了人：国内的 PolarDB、TiDB（兼容 MySQL 协议的分布式 NewSQL）、分库分表中间件 ShardingSphere……**MySQL 自己也许不是最强的数据库，但"兼容 MySQL"成了造数据库的默认起跑线**——这正是第一节"最容易上车"的胜利在二十年后的复利。

同期格局：PostgreSQL 在开发者口碑上反超（标准 SQL 完整、扩展性怪兽、PGVector 踩中 AI 向量检索），MySQL 守住 Web/云托管存量；8.0 之后迭代放缓的抱怨渐多，但"事实标准"的惯性以十年计。它自己也在补：HeatWave（2021）给 MySQL 加内存分析引擎，Oracle 终于开始把两个儿子的家当互通。

## 四、还债：字符集、复制与高可用（2005-2018）

1. **SQL 方言之债**：存储过程/视图迟到 2005（5.0），CTE 与窗口函数迟到 2018（8.0）——SQL 篇讲的"标准 SQL"，MySQL 花了二十年才基本交齐。8.0 同时把默认字符集改为 utf8mb4：此前的"utf8"是残缺的三字节实现，存不了 emoji——坑了十几年的默认值，一朝改正。
2. **复制与高可用之债**：主从复制很早就有，但默认异步——主库提交不等从库，主库宕机就有丢数据窗口。补课三级台阶：半同步复制（5.5，2010，至少一个从库确认）、GTID（5.6，2013，复制位点从"文件+偏移"变成全局事务号，运维不再数手指）、组复制 MGR（5.7.17，2016，多数派共识自动选主）——这条路和 Redis 篇"哨兵→Cluster"是同一个方向：**单机够用时没人管高可用，规模逼出来才有标准答案**。
3. **拆分之债**：单表几亿行后索引撑不住，互联网公司被迫自创分库分表（中间件时代），直到云托管与 NewSQL 把这件事收编回去——分布式不是 MySQL 的债，是它所在生态的债。

## 五、三个必要词汇

- **存储引擎**：MySQL 架构的灵魂——SQL 解析、优化在上层，存取由可插拔引擎负责（InnoDB 事务/行锁/MVCC，MyISAM 只读快但表锁）。这一层分离是 Aurora 们能"换内核不换接口"的结构前提。
- **MVCC（多版本并发控制）**：InnoDB 给每行留版本链，读走旧快照、写加行锁——**读不阻塞写，写不阻塞读**。数据库并发的高吞吐基本都靠它，思路与 Redis 篇"单线程免锁"殊途同归：都不让读和写互相踩脚，一个靠版本，一个靠排队。
- **主从复制与最终一致**：主库把变更写进 binlog，从库重放。默认异步意味着从库永远略旧——"刚写入查不到"的经典来源。读写分离省不掉这一课：哪些读必须走主库，是业务决策。

## 六、工程化：一个 MySQL 服务怎么跑起来和正确使用

```text
docker run -d --name mysql -p 3306:3306 -e MYSQL_ROOT_PASSWORD=xxx mysql:8 → 起服务(或 brew install mysql)
mysql -uroot -p → 进客户端
CREATE DATABASE shop CHARSET=utf8mb4; CREATE TABLE ... ENGINE=InnoDB → 建库建表(新版本默认即 utf8mb4+InnoDB,显式写明是习惯)
EXPLAIN SELECT ... → 看执行计划(慢查询第一现场:type/key/rows)
SHOW PROCESSLIST; SHOW ENGINE INNODB STATUS → 体检(正在跑什么、引擎内部状态)
mysqldump shop > shop.sql → 备份(能恢复的备份才算数,见认知 3)
```

三个关键认知：

1. **默认配置是"能跑"，不是"能上线"**——与 Redis 篇同一条铁律。上线前过一遍：连接数上限、InnoDB buffer pool（给数据用的内存，通常给到机器内存的一半上下）、显式 utf8mb4、慢查询日志开关。
2. **EXPLAIN 是第一工具**。慢了不猜，先 EXPLAIN：type 是否全表扫描（ALL）、key 有没有走上索引、rows 扫了多少。索引为 where/order by/join 而生——这一手正是 SQL 篇"优化器"的日常入口。
3. **备份与复制是两条命**。binlog + 定期备份 = 能恢复（"没有验证过恢复的备份等于没有备份"）；主从 = 能故障转移。生产库没有这两样，都属于裸奔。

AI 验收三连：连接、建表、插入、查询一条龙跑通；EXPLAIN 能看到 type/key；`mysqldump` 备份后能在一个新实例里恢复出同样的数据。

## 七、因果链小结

```text
Web 买不起 Oracle,要的是快/免费/好装              → MySQL(1995,LAMP 默认库,表锁无事务的"玩具")
Web 变成业务,要事务要并发,SQL 层与引擎分离         → InnoDB 接管(2001-2010,行锁+MVCC+事务)
心脏供应商与本体先后落入 Oracle,MariaDB 出走       → 兼容承诺守住信任(2005-2010),Oracle 持续投入换来反直觉结局
云要托管,生态要替代,接口即起跑线                  → RDS/Aurora/PolarDB(2009-),"兼容 MySQL"成了造库标准
```

## FAQ

约定：这里的问答随实际疑问追加，每条回答控制在几句话内；问题来自真实使用中的困惑，不预设。

**Q1：新项目选 MySQL 还是 PostgreSQL？**
都能打，选生态不选功能：团队栈、云托管成熟度、现成轮子（WordPress 等）偏 MySQL；标准 SQL 完整度、扩展（PostGIS、PGVector）、 License 偏 PostgreSQL。AI 应用要向量检索，PG 的 pgvector 目前更顺——但 MySQL 存量 Web 世界的地位十年内不会动摇。

**Q2：MariaDB 和 MySQL 什么关系，要换吗？**
2009 年 Monty 对 Oracle 收购的 fork，同源近亲、高度兼容。多年分叉后新特性已各有方向。国内新项目多直接用云托管 MySQL；用 Linux 发行版自带数据库时，装到的"mysql"常常就是 MariaDB——照常用即可。

**Q3：utf8 和 utf8mb4 差在哪？**
历史坑：MySQL 的"utf8"最多存 3 字节，遇到 emoji（4 字节）直接报错；utf8mb4 才是完整 UTF-8。8.0 起默认已改，但老库老表还在——接手存量库先查 `SHOW CREATE TABLE`。

**Q4：为什么刚写入的数据在另一个连接查不到？**
大概率在读从库：默认异步复制有延迟。强一致读（支付后立刻看订单）走主库， tolerate 延迟的读（报表、列表）走从库——读写分离省不掉这一条业务规则。

**Q5：Aurora 是 MySQL 吗？**
接口是（协议与 SQL 兼容），内核不是——存储层被 AWS 重做成一写多读共享存储，故障切换秒级。"兼容 MySQL、重写存储"这条路后来走的人越来越多，MySQL 用接口当了自己的护城河。
