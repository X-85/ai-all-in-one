# Docker-K8s 演进路线

一句话版：**"在我机器上是好的"困了工程师三十年——Docker 用 Linux 内核里沉睡多年的两项能力造出集装箱，把环境连同代码打进一个可分发的文件；等所有人都开始装箱，Google 把内部跑了十年的 Borg 经验开源成 Kubernetes，于是"服务器"变成了"集群"，运维变成了"声明期望状态"。**

## 一、PaaS 公司的副产品（2013）

部署之痛是行业的老病：依赖地狱（这个库要 Python 2、那个要 3）、环境漂移（测试环境与生产差一个补丁）、"在我机器上是好的"。虚拟机能隔离，但分钟级启动、GB 级体积、按台收费——用它打包一个应用像用货车运一封信。配置管理工具（Puppet、Chef）管住了配置，却管不住"整个环境作为一个整体搬运"。

转机藏在一个冷知识里：**Linux 内核早就有隔离能力**——namespace（2002 年起逐步合入，隔离进程的视图：网络、文件系统、进程号）和 cgroups（2008 年合入，限制与统计资源：CPU、内存）。它们在内核里睡了多年，只有少数玩 LXC 的系统管理员当宝贝。

2013 年 3 月，PaaS 创业公司 dotCloud 的创始人 Solomon Hykes 在 PyCon 上做了五分钟演示：把公司内部基于这些能力搭的交付工具开源，取名 Docker。PaaS 业务没成，副产品成了时代主角。Docker 做对的事是**把内核能力封装成开发者友好的抽象**——

| | 虚拟机 | Docker 容器 |
|------|------|------|
| 隔离层级 | 硬件级（Hypervisor 各装一套 OS） | 进程级（共享宿主内核） |
| 体积 / 启动 | GB 级 / 分钟级 | MB 级 / 秒级 |
| 交付单位 | 镜像文件（难分发） | **镜像：分层文件，推拉即分发** |

Dockerfile（几行声明"怎么装环境"）→ 镜像（分层构建、层可缓存）→ 容器（`docker run` 秒级拉起）。"Build once, run anywhere"——Java 篇当年用 JVM 在字节码层承诺的话，Docker 在整个环境层兑现了：**可分发单位从"代码+文档说明"变成了"镜像"**。

## 二、编排大战与 K8s 登基（2014-2017）

容器一多，新问题立刻上台：几百上千个容器跑在几十台机器上，谁调度、挂了谁重启、流量谁分发、扩缩容谁决定？容器是新的进程，缺一个新的"init"。

2014 年 6 月，Google 开源 **Kubernetes**（希腊语"舵手"，K 与 s 之间 8 个字母故缩写 K8s）——把内部跑了十年的 Borg 系统的经验，用 Go 重写成开源项目（Borg 论文在 papers-we-love 里能读到）。战争三年就打完了：

- **Mesos**（伯克利出品，Twitter 重度用户）：两级调度，强在批处理混部，Web 服务编排始终隔靴搔痒；
- **Docker Swarm**（Docker 自家，2015）：够简单，但生态与扩展性跟 不上；
- **Kubernetes**：胜在三件事——Google 十年经验的降维、**声明式 API**（说"我要 3 个副本"，不说"怎么做到"）、接口化拆解（CRI/CNI/CSI 把运行时、网络、存储留给生态）。

两个关键节点：**2015 年 7 月 K8s 1.0 发布，同日 Google 把它捐给新成立的 CNCF（Linux 基金会系）**——1.0 承诺 API 稳定，这份承诺的语气和 Go 1.0（2012）如出一辙，毕竟是同一家的孩子；**2017 年 10 月，Docker 官宣在自己的版面支持 K8s**——编排大战就此收官。CNCF 后来长成云原生百科全书（Prometheus、Helm、Envoy……），K8s 是它的内核。

## 三、从编排器到云的操作系统（2017-2025）

登基之后的剧情分两条线，都值得记。

**K8s 线**：它成了云的"操作系统内核"——GKE/EKS/AKS 等各家托管服务、混合云的统一底座；生态按接口疯长：Helm 管应用打包，Operator 把"运维知识"写成代码，Istio 管服务网格。AI 时代接着用：GPU 调度、训练任务（Job）、推理服务（Deployment+HPA）——Python 篇 AI 帝国的算力底座，大多跑在 K8s 上。债也明摆着：**复杂度**——YAML 山、概念多到劝退小团队，于是催生了 k3s（2019，轻量发行版）与 Nomad 这类"反卷"替代品。

**Docker 线**：Docker 公司没能兑现时代赋予的垄断位——PaaS 转型失败、融资烧尽、2019 年把企业版卖给 Mirantis，Desktop 转"个人免费/企业收费"。但最有远见的一步棋是 2017 年把核心运行时 **containerd 捐给 CNCF**：K8s 通过 CRI 接口直接用 containerd，2022 年 1.24 起彻底移除内置的 dockershim。结局很哲学：**Docker 公司的生意做小了，docker 却赢了——`docker build` 仍是每个开发者的肌肉记忆，只是底下跑的早已是 containerd**。"界面是 Docker 的，内核是社区的"。对照 Redis 篇的许可风波：一个把核心攥紧又放开，一个直接捐给中立基金会——**捐出去的反而赢得了整个生态**。

## 四、还债：标准化、拆分与瘦身（2015-2022）

1. **标准化让权（OCI，2015）**：容器爆火当年，Docker 联合 CoreOS 等成立开放容器倡议（OCI），把"镜像格式"与"运行时接口"定为行业标准。任何人都可以造容器——Docker 主动放弃了"格式私有"这条最深的护城河，换来的是容器成为行业公器。这是它与 Redis 两种治理哲学的分水岭。
2. **拆分 monolith**：早期 dockerd 是个大单体，2016-2017 拆出 containerd（运行时）、runc（OCI 参考实现）——分层之后，K8s 取用、Redpanda 式的"重写一层"都成为可能。工具链可以换内核、外壳不变，这条规律在平台层再次生效。
3. **K8s 瘦身与减负**：移除 dockershim（1.24，2022）是给"只认标准接口、不认特定实现"还债；内置 Auto Scaling 与 Helm/Operator 的成熟，是在还"YAML 手工运维"的债——复杂度是 K8s 永远还不完的那笔，k3s/Nomad 的存在本身就是这笔债的利息。

## 五、三个必要词汇

- **镜像与容器**：镜像是只读的分层快照（层可缓存、可推拉分发），容器是镜像的一个运行实例——类与实例的关系。理解了"分发单位是镜像不是代码"，CI/CD 的形态就自然懂了。
- **声明式 API**：Deployment 里写"我要 3 个副本、用这个镜像"，不写任何步骤。K8s 负责把现实搬去符合期望。与 SQL 同一个灵魂：**说要什么，不说怎么做**——这个手法贯穿本系列（SQL 的查询、React 的 UI=f(state)、K8s 的 YAML）。
- **控制循环（Reconcile）**：K8s 的一切组件都在跑同一个小死循环：观测现状 → 与期望比对 → 修正差距。"你手删 Pod 它自动拉起来"不是魔法，是这个循环在干活。声明式 API 之所以能成立，背后全是它。

## 六、工程化：一个应用怎么容器化并跑起来

平台口径的工程化，主角是"从代码到集群"这条路：

```text
docker build -t myapp:1 .        → 按 Dockerfile 打镜像(分层缓存:依赖层不变就不重打)
docker run -d -p 8080:8080 myapp:1 → 本地起一个容器验证
docker push 仓库/myapp:1          → 镜像进仓库(分发单位是镜像,不是代码)
kubectl apply -f deploy.yaml      → 把"期望状态"提交给集群(replicas: 3)
kubectl get pods / logs / describe → 观测现实与期望的差距(排障三件套)
```

三个关键认知：

1. **镜像里要有运行所需的一切**（基础镜像+运行时+依赖+代码），所以换一台机器不需要"装环境"——这一条消灭了三十年的"环境文档"。代价是镜像要管好：用小基础镜像（alpine/slim）、多阶段构建、别把密钥打进去。
2. **K8s 只认声明**。改状态的标准动作是改 YAML 再 `apply`，不是上服务器手改。手动删掉的 Pod 会自己回来——这不是 bug，是控制循环在纠正你。想在生产环境"临时改一下"，先想清楚它会不会被调和回去。
3. **两级验证是标准流程**：`docker run` 单机跑通 → `kubectl apply` 进集群。本仓库的站点就是活例子：Astro 构建出静态产物（Next.js 篇的"纯静态可退"），CI 里打包推送，Pages 平台伺服——容器化与托管平台是同一条"环境打包"思路的不同完成度。

AI 验收三连：`docker build` 成功且二次构建命中缓存；`docker run` 后 curl 端口通；`apply` 后 `get pods` 全部 Running，删掉一个 Pod 观察到自动重建。

## 七、因果链小结

```text
环境地狱+虚拟机太重,内核的 namespace/cgroups 沉睡多年    → Docker(2013,镜像=可分发的环境)
容器多了没人管:调度/自愈/扩缩容                        → K8s(2014,Borg 经验+声明式 API),三年编排大战登基
生意与标准分家:Docker 捐 containerd、OCI 定格式         → 容器成公器(2015-2017),docker 做界面,containerd 做内核
复杂度是还不完的债:YAML 山、概念税                     → Helm/Operator/k3s(2019-),K8s 成为云的操作系统
```

## FAQ

约定：这里的问答随实际疑问追加，每条回答控制在几句话内；问题来自真实使用中的困惑，不预设。

**Q1：容器和虚拟机到底差在哪？**
容器是共享宿主内核的隔离进程，虚拟机是 Hypervisor 上的完整Guest OS。秒级 vs 分钟级、MB vs GB。代价是隔离弱一档（内核是共享的），安全敏感的多租户场景常常容器外面再垫一层 VM——云厂商都这么干。

**Q2：K8s 都移除 Docker 了，我还要装 Docker 吗？**
要分清两层：K8s 移除的是 dockershim（通过 Docker 间接用容器的那条旧路），不是 docker 工具。开发机上 Docker（Desktop）仍是事实标准；生产集群里跑的是 containerd——**docker 是界面，containerd 是引擎**，开发者无感。

**Q3：小项目有必要上 K8s 吗？**
没有。单机或三五台机器，docker compose 就是终点；K8s 买的是"多节点调度、故障自愈、声明式扩缩"这些规模化能力，复杂度是真实的价格。中间态有 k3s（单二进制轻量 K8s）。判断标准：运维的人比运行的节点更金贵时，再上。

**Q4：Pod 和容器什么关系？**
Pod 是 K8s 的最小调度单位，里面一个或多个容器共享网络与存储。为什么不直接调度容器？因为有些进程天生要一起死活（应用+日志收集 sidecar），Pod 给它们一个"同生共死"的宿舍。

**Q5：为什么我删了 Pod 它又起来了？**
Deployment 里声明着"replicas: 3"，控制循环发现现实（2 个）与期望（3 个）不符，就补一个。想真正减员：改声明再 apply。这是特性不是 bug——K8s 的世界里，声明才是事实。

**Q6：Docker 和 K8s 跟 Go 什么关系？**
Docker 与 K8s 的核心都是 Go 写的——当年 Go 还年轻，两家用自身成功给 Go 盖了"云原生官方语言"的章（Go 篇的帝国就是这么一砖一瓦砌的）。Go 的静态编译单二进制，也正好满足"分发一个自包含可执行文件"的运维审美。
