# Redis 演进路线

一句话版：**MySQL 扛不住毫秒级的实时读写，memcached 又只会存字符串、丢了就丢了；Redis 干脆把整副数据结构搬进内存，让操作在服务器端原子执行，再顺手落盘——从一块"缓存补丁"长成了后端事实上的内存数据层。**

## 一、memcached 留下的空位（2009）

Web 2.0 把网站变成了应用：排行榜、计数器、最新动态、会话保持，全是高频小读写。这类负载打在磁盘数据库上是灾难——一次随机读就是几毫秒的磁盘寻道，热点行还要锁排队。通行解法是 2003 年 LiveJournal 造的 **memcached**：一块内存里的 key-value 缓存，把热数据挡在数据库前面。

但 memcached 做得很"薄"，三件事不管：

1. **value 只是不透明字符串**：计数靠 `incr` 还行，可排行榜（按分数排序）、最新列表（只保前 100 条）、共同关注（集合交集）全都得把整份数据拉回应用进程，算完再塞回去——网络来回搬运，并发下还得自己处理竞态；
2. **不持久化**：进程一重启，缓存全空，流量瞬间砸回数据库；
3. **无复制**：单机一块内存，挂了就没了。

2009 年，意大利程序员 Salvatore Sanfilippo（antirez）在给自己的实时网站分析工具 LLOOGG 做后端时，被"MySQL + memcached"这套组合反复折磨，干脆自己写了一个服务器，取名 **REmote DIctionary Server**。分水岭一句话：**memcached 是把"数据库的查询结果"放进内存，Redis 是把"数据结构本身"放进内存**——

| 数据结构 | 一句话用途（都是服务器端原子操作） |
|------|------|
| String | 缓存对象、计数器（INCR 一条命令自增） |
| Hash | 对象按字段存取（会话、用户资料，改一个字段不必整取整存） |
| List | 双端队列（最新动态、简单任务队列） |
| Set | 去重与交并（标签、共同关注） |
| ZSet（有序集合） | 按分数排名（排行榜、延迟队列） |
| Stream（5.0，2018 补） | 持久化消息队列 |

命令直接对结构做原子操作：`ZINCRBY` 一条命令完成"某人得分加一并更新排名"，`LPUSH` + `LTRIM` 两条命令保住"最新 100 条"。再配上快照持久化（RDB）——数据在内存，但落了盘，重启能找回。**它不只是更快的缓存，是能承载数据的内存层。**

## 二、从单机到集群，从工具到标配（2010-2015）

移动互联网爆发，Redis 从"选型之一"变成"后端默认配置"——应用 + MySQL + Redis 三件套：会话放它、缓存放它、队列放它、排行榜放它、限流靠它计数、抢购靠它减库存。但单机版两个死结摆在台面上：

1. **单点故障**：主库一挂，全站缓存瞬间雪崩，数据库直接被流量拍死；
2. **容量与吞吐天花板**：单机内存有限，写再多也只有一个进程在执行。

Redis 的答案是三块积木，逐级往上搭：

- **主从复制**（很早就有）：一主多从，读水平扩展，从库兼做热备——但主挂了要人肉切换；
- **哨兵 Sentinel**（2012 年随 2.6 引入）：哨兵进程盯着主库，挂了自动把从库提上来——高可用有了，容量却还是一台机的量；
- **Redis Cluster**（3.0，2015）：官方分片。数据切成 **16384 个哈希槽**分散到多个主节点，每主再挂从；**去中心化**——没有代理层，客户端直连任意节点，节点间用 gossip 协议自协商，主挂了自动选从补位。

Cluster 是官方答案，但代价明码标价：多键操作要求键落在同一槽（跨槽得用 hash tag 把相关键硬排进同一节点），运维复杂度陡增。所以很长一段时间，业界流行"客户端分片或代理（Twemproxy、Codis）+ 哨兵"的自选组合，Cluster 慢慢才成主流。这节尾声值得记一笔生态事实：2013 年起 AWS ElastiCache 支持 Redis，此后全托管成为各家云厂商标配——Redis 和 Go 篇的 Docker 一样，赶上了云原生这班车，帝国就此定型：**它不再是一个工具，而是后端基础设施的默认层。**

## 三、平台化与许可风波（2016-2025）

事实标准做成之后，两个问题接踵而至：数据库竞争进入"多模"时代（MongoDB 管文档、Elasticsearch 管全文、向量数据库管相似度），Redis 要回答"还能管什么"；养它的公司（Redis Labs，后更名 Redis）要回答"怎么赚钱"。两问撞在一起，就是近十年的主线。

**1. 从数据库到平台。** 4.0（2017）开放 Modules API，Redis 变成可插拔的底座：RediSearch 补全文检索，RedisJSON 补 JSON 文档，RedisGraph、RedisTimeSeries 各补一块。2022 年打包成 **Redis Stack** 发行（模块全家桶 + 图形界面 RedisInsight）。最关键的一块补在 AI 时代：向量检索——先靠 RediSearch 模块，8.0（2025）干脆内建 **Vector Sets** 数据结构。呼应 Python 篇的生态帝国：LLM 应用的记忆与检索层，Redis 也在场。

**2. 许可证走了一个来回。** 这是本系列至今最戏剧的一段：

- 2018 年起，商业化模块（RediSearch 等）先后改用 Commons Clause、RSAL——云厂商拿开源版免费托管赚钱、原作者拿不到分成的老矛盾；
- **2024 年 3 月，核心 Redis 宣布从 7.4 起改 RSALv2 + SSPL 双许可**，告别沿用十五年的 BSD——按 OSI 定义，Redis 不再是开源软件；
- 几乎同时，AWS、Google 等发起 fork：**Valkey**，交给 Linux 基金会，从最后的 BSD 版本（7.2.4）出发——与当年 Elasticsearch 改许可、AWS 分叉出 OpenSearch 同款剧本；
- **2025 年 5 月，Redis 8 把 AGPLv3 加入许可选项**，回归开源阵营，还给 Valkey 用户准备了迁移文档。

教训一句话：**"开源"不是恒定属性，是社区与商业的动态平衡**——免费午餐被云厂商规模化到一定程度，规则就会被重新谈判；而 fork 是社区最后的制衡，Valkey 的存在反而促成了 Redis 的回归。同期还冒出 KeyDB、Dragonfly 等 C++ 多线程挑战者（2019 / 2022），它们证明了单线程不是性能上限、是设计取舍——这就接到下一节。

## 四、还债：单线程神话的代价（2020-2022）

2009 年"命令单线程执行"的决定，是 Redis 最著名也最被误读的设计：**一次只执行一条命令，天然原子、免锁**（上一个十年里，多线程程序的锁 bug 是日常），加上内存操作与 IO 多路复用（epoll），单线程跑出十万级 QPS。但红利有边界——**网络收发与协议解析先于命令执行成为瓶颈**，多核机器上其余核心在围观。还债分三笔：

1. **6.0（2020）引入多线程 I/O**（需配置开启）：读网络、写网络、解析协议并行做，**命令执行仍然单线程**——原子性承诺一个字不改，客户端命令一个字不变。又一个"外壳不变，换内核"（同 Next.js 篇的 Turbopack）。
2. **安全补课（ACL）**：此前十余年只有一个全局密码，谁验证通过谁就是超级用户；默认无密码又暴露公网的 Redis 被写 crontab 挖矿，是安全事件常客。6.0 引入 ACL：按用户分配可执行的命令与可访问的键。
3. **7.0（2022）三件套**：Functions 取代裸 EVAL Lua 脚本（函数有名字、可管理、可复制，不再是散落的脚本字符串）；multi-part AOF（增量 + 基线，告别重写期间的内存与磁盘双峰值）；Sharded Pub/Sub。

## 五、三个必要词汇

- **数据结构服务器**：Redis 的自我定位不是 cache，是 data structure server。value 是带类型的数据结构，操作在服务器端原子执行——这是它与 memcached 的分界线，也是它越过"缓存"长成内存数据层的根。判断一个场景该不该用 Redis，先看操作能不能下沉到服务器端。
- **RDB 与 AOF**：内存里的数据怎么活过重启的两条路。RDB 是定时全量快照（文件小、恢复快，丢最近几分钟）；AOF 是追加每条写命令（更完整、文件大、恢复慢）。7.0 起默认可混合：AOF 里嵌 RDB 基线 + 增量命令。这一对词决定 Redis 的身份——全关是缓存，全开才敢当存储。
- **单线程命令执行**：一次只跑一条命令，天然原子免锁；代价是任何慢命令堵住全世界（`KEYS *` 扫全库、DEL 一个上百 MB 的大 key）。它依然快，靠的是内存 + epoll + "少等待"，而非"多并行"。写代码前对每条命令心里有复杂度的数，是用好 Redis 的第一课。

## 六、工程化：一个 Redis 服务怎么跑起来和正确使用

演进讲完，补实务。本篇是系列首个中间件，工程化主角从"构建一个项目"换成"跑好一个服务"：

```text
brew install redis 或 docker run -d -p 6379:6379 redis → 起服务(默认端口 6379,数据全在内存)
redis-cli ping                  → PONG(验活,"装没装好"的第一判据)
redis-cli SET session:u1 '{"cart":[]}' EX 3600 → 写入(键名习惯用冒号分层,EX=3600 秒后自动删除)
redis-cli TTL session:u1        → 3597(剩余寿命递减,过期即消失)
redis-cli INFO memory           → 体检(用了多少内存、淘汰了多少 key)
redis-cli CONFIG GET maxmemory* → 读出内存上限与淘汰策略(见认知 1)
```

三个关键认知：

1. **默认配置是"能跑"，不是"能上线"**。开箱无密码、maxmemory=0（不限内存，直到吃爆机器）、无淘汰策略。上线必配三件：认证（requirepass 或 ACL）；`maxmemory` + `maxmemory-policy`（当缓存用选 allkeys-lru：内存满了自动清最久没用的）；持久化按定位选（见认知 2）。
2. **先想清定位：缓存还是存储**。缓存——数据丢了能从 MySQL 回源，选 LRU 淘汰、可关 AOF；存储——丢了就是事故，开 RDB + AOF 混合、上主从和哨兵/Cluster。容量上限 = 内存 = 钱，这个物理约束决定 Redis 适合放"热的小数据"，不适合当大仓库。
3. **命令单线程，慢命令堵全场**。`KEYS *` 生产禁用，遍历用 SCAN 渐进分批；警惕大 key（一个几百 MB 的 value，谁读谁堵，删也用 UNLINK 异步删）；批量用 MGET / pipeline，不要 for 循环单发。

AI 验收三连：`redis-cli ping` 回 PONG；`SET` 带 `EX` 后 `TTL` 递减、过期后 `GET` 回 `(nil)`；`CONFIG GET maxmemory*` 能读出上限与淘汰策略，确认不是默认的 0（不限）。

## 七、因果链小结

```text
磁盘库扛不住实时小读写,memcached 只会存字符串    → Redis(2009,内存里的数据结构服务器+RDB 持久化)
单点故障、单机内存到顶,分片各自造轮子            → 复制/哨兵/Cluster(2010-2015),同期长成后端默认配置
多模竞争与商业模式,撞上云厂商白拿               → 平台化(Modules/Stack/向量)+ 许可风波(2024 失开源→Valkey→2025 AGPL 回归)
单线程免锁的红利,撞上网络吞吐天花板              → 6.0 多线程 I/O + ACL(2020),7.0 Functions/混合 AOF(2022)——命令外壳一个没变
```

## FAQ

约定：这里的问答随实际疑问追加，每条回答控制在几句话内；问题来自真实使用中的困惑，不预设。

**Q1：Redis 为什么这么快？**
三个词：内存、epoll（IO 多路复用，一个线程盯住所有连接）、单线程免锁。注意最后一条——快不是因为多线程并行，是"少等待"：没有锁竞争、没有上下文切换、没有磁盘寻道。6.0 的多线程 I/O 解决的是网络收发，不是命令执行。

**Q2：Redis 算数据库还是缓存？**
它两栖，配置决定身份：持久化全关、配 LRU 淘汰，它就是缓存；RDB + AOF 混合、主从副本加自动故障转移，它可以当主力存储。但物理约束摆着——数据必须在内存，容量上限就是内存和预算，所以"热的小数据放 Redis、大的冷数据放磁盘库"是常态分工（另一半见 SQL 篇）。

**Q3：为什么生产环境禁用 `KEYS *`？**
命令单线程执行，`KEYS *` 是 O(N) 全库扫描，扫的这几秒所有请求排队——等于给整个服务按暂停键。遍历用 SCAN：游标渐进分批，不堵路。同一逻辑：FLUSHALL、大 key 的 DEL（换 UNLINK）都要小心。

**Q4：缓存穿透、击穿、雪崩分别是什么？**
穿透：查根本不存在的 key，每次都打穿到数据库——缓存空值或布隆过滤器挡住。击穿：某个热点 key 恰好过期的瞬间，海量请求同时回源——互斥重建（只放一个请求去查库）或逻辑过期。雪崩：一大批 key 同一时刻失效——过期时间加随机抖动。三个词都是"缓存层失守、数据库裸承流量"的不同姿势。

**Q5：Valkey 是什么，要换吗？**
2024 年 Redis 改许可后云厂商发起的 fork（Linux 基金会托管），协议兼容、命令基本通用。2025 年 Redis 回归 AGPL 后，新选型的迁移理由已经减弱——跟着你的云托管服务与既有生态走即可。这个事件的价值在教训：开源治理要看许可文本，不能只看习惯。

**Q6：用 SET NX 抢分布式锁靠谱吗？**
`SET lock:order 随机值 NX EX 10` 是正确起点：NX 保证只有一个客户端成功，EX 保证持锁者崩溃后锁自动释放。两处必须补：值用随机数、释放时用 Lua 校验"是自己的锁才删"；业务可能超过 EX 时要有续期或让步。更严格的跨实例共识（Redlock）有争议，一般业务单实例版够用。
