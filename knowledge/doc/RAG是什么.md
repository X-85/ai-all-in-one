# RAG 是什么

RAG(Retrieval-Augmented Generation,检索增强生成)是一个**概念 / 架构模式**,不是某个具体的产品或框架。核心思想:**在大模型回答问题之前,先从外部知识库里检索相关内容,把检索结果拼进 prompt,再让模型基于这些内容生成答案**。

配套的动手学习材料见 [RAG学习路线图与实战指南](RAG学习路线图与实战指南.md)。

## 一、解决什么问题

RAG 针对大模型的三个痛点:

| 痛点 | 说明 | RAG 的应对 |
|------|------|-----------|
| 知识过时 | 训练数据有截止日期,不知道新发生的事 | 知识库随时更新,不需要重新训练 |
| 私有数据 | 模型没见过企业内部文档、个人笔记 | 私有资料入库即可被检索 |
| 幻觉 | 模型会编造看似可信的答案 | 答案限定在检索到的资料范围内 |

## 二、典型架构

RAG 落地时基本都遵循同一套两阶段流水线,每一环都可以替换不同的组件:

```text
【离线索引阶段】(提前做好,只做一次或文档更新时做)
原始文档 → 加载解析(PDF/网页/数据库) → 切分成小块(chunk)
→ 用 Embedding 模型向量化 → 存入向量数据库

【在线问答阶段】(用户每次提问时)
用户问题 → 向量化 → 在向量库中做相似度检索,取 Top-K
→ (可选)重排 rerank 精筛 → 拼进 prompt 作为上下文
→ 交给 LLM 生成答案
```

所谓"RAG 架构"就是这条流水线。理解了两个阶段,再看任何 RAG 产品或框架,本质都是在给这条流水线换零件、加零件。

## 三、常见实现框架与组件

| 层次 | 代表项目 | 特点 |
|------|---------|------|
| 编排框架 | LangChain、LlamaIndex | 提供搭建流水线的积木,灵活但要写代码 |
| 一体化平台 | Dify、RAGFlow、FastGPT、AnythingLLM | 自带 UI,拖拽配置就能搭知识库问答,开箱即用 |
| 检索框架 | Haystack | 老牌 NLP 检索管线框架 |
| 向量数据库 | Milvus、Qdrant、Chroma、pgvector、Elasticsearch | 存向量和元数据,负责相似度检索 |
| Embedding 模型 | BGE 系列(智源开源)、OpenAI text-embedding | 负责把文本变成向量 |
| 重排模型 | BGE-reranker、Cohere Rerank | 对初筛结果精排,提升准确率 |

## 四、怎么选

- 只想快速搭一个"上传文档 + 问答"的应用 → 直接用 **Dify / RAGFlow** 这类平台,不用写代码;
- 产品里要深度定制的 RAG(自定义切分策略、混合检索、多路召回)→ 用 **LangChain / LlamaIndex** 自己拼;
- 数据量大、并发高的生产场景 → 向量数据库从 Chroma 换成 **Milvus / Qdrant** 等面向生产的选型。

## 五、与相邻概念的边界

| 概念 | 与 RAG 的区别 |
|------|--------------|
| 微调(Fine-tuning) | 改的是模型本身的能力和风格;知识不易更新、成本高。让模型"会做事"用微调,给模型"喂资料"用 RAG,两者常组合 |
| 长上下文(Long Context) | 把全部资料直接塞进上下文窗口,不检索;受窗口和成本限制,资料量大时不经济,RAG 是按需取用 |
| Agent | Agent 是"会规划、会调用工具的执行者",RAG 检索可以是 Agent 众多工具中的一个 |

## 六、一句话总结

**RAG 是"先查资料再回答"这个模式的名字,各种框架和平台都是帮你把这个模式工程化的工具。**
