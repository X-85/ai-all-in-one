# RAG 问答系统质量设计:问答记录与落地方案

> 记录:2026-09-22 | 场景:钉钉 + AstrBot 的 RAG 问答知识库 | 用途:问答存档 + 次日公司推进清单

概念基础见 [RAG是什么](RAG是什么.md),学习与优化手段见 [RAG学习路线图与实战指南](RAG学习路线图与实战指南.md)(阶段 5/6 与本方案直接相关)。

## 一、背景:系统架构

```text
用户(钉钉) → 钉钉机器人 → AstrBot(消息接入层)
                              ├─ 内置 RAG 知识库(召回)
                              └─ 内置 agent 执行器(生成)
                              → 回复原路返回钉钉
```

核心关切:**如何保证回答的质量**——每个问答系统都要回答的元问题。

## 二、原始思路(2026-09-22 会话记录)

对用户消息做意图识别,分三类处理:

1. **真理类知识(定位 FAQ)**:专门维护一本"答案之书",记录各种 FAQ 问题与验证过的答案;
2. **非真理类知识(模糊)**:对问题定性,识别用户最关心的方向——想知道**原因**、**结果**还是**过程**,进行有指向性的输出;
3. **意图难识别**:先反问用户几个问题让他做选择,根据选择做意图分析,得到问题方向后再定向输出。

自我定位:构建的不是普通 FAQ 问答系统,而是 **FAQ 智能体问答系统**。

## 三、AI 评估(完整记录)

### 总体判断

方向是对的,而且摸到了关键:**问答系统的质量瓶颈通常不在检索本身,而在"问题理解 + 路由"**。RAG 路线图阶段 5 里"80% 的问题出在检索而不是生成",而检索差的一大根因正是问句没被理解透。这件事业界叫 query routing / agentic RAG,是玩具 RAG 和生产级 RAG 的分水岭。三步思路里,3.1(答案之书)和 3.3(澄清追问)基本成立;3.2(定向输出)有价值,但分类轴放错了位置。

### 值得肯定的两处

1. **答案之书(curation first)是高频问题的最优解**。验证过的标准答案直接返回,质量是确定性的、可审核的,完全绕开幻觉。生产系统普遍这么分层:FAQ 命中优先,RAG 兜底。
2. **澄清式追问是最有"智能体"味道的一环**。一次性问答系统和 agent 的本质区别,就是 agent 能自主决定"现在该答还是该问"。

### 三个商榷点

**1. "真理类 vs 非真理类"这一刀切错了位置。** 边界极模糊:"为什么报表接口慢"算事实类还是模糊类?它在知识库里有答案(事实),但用户要的是"原因"这种定向输出——两个类别互相穿透。本质是把两个正交的维度压成了一根轴,应拆开:

- **路由轴**(决定走哪条路):问题在知识库内还是库外;问题完整还是欠完整;
- **形态轴**(决定答案长什么样):用户要原因、结果还是过程——对 FAQ 和非 FAQ 都适用。

"是否可验证/是否真理"的正确用途是**治理标准**(一条答案能否沉淀进答案之书,看它是否可验证、有无时效),而不是路由标准。

**2. 路由表缺了第四条,而且可能是最重要的:超纲拒答。** "知识库里没有,我不知道,建议转人工/查 XX"不是失败,是质量功能。没有这条,所有库外问题都被硬塞进 RAG,模型在低相关性 chunk 上强行生成——这正是幻觉的主产区。(对应 Dify 实验里"故意问文档里没有的问题,观察拒答表现"。)

**3. 意图识别本身会错,且误路由是静默失败。** 用户看不到"路由错了",只看到答案不对。因此:

- FAQ 命中要走语义匹配 + 置信阈值:高置信直接回标准答案、中置信带来源回、低置信落到 RAG;
- 澄清追问一轮封顶、给编号选项(钉钉群聊里按钮交互支持有限);
- 意图分类和定向生成可合并在一次 LLM 调用里完成(先出意图标签再按模板作答),不做多级流水线——链路越长越难排查。

### 两件没提但决定成败的事

**1. 答案之书怎么长(飞轮)。** 只靠人工预先编写,书会过期、会缺、维护不动。正确姿势:RAG 对话日志 → 答得好且被反复问的问题 → 人工审核队列 → 通过后沉淀入答案之书。**书是长出来的,不是一次写成的。** 这要求每条 RAG 答案带来源引用——既是用户信任,也是审核依据。

**2. 评估闭环。** "没有评估就只能感觉变好了"(路线图阶段 6)。从钉钉真实提问里攒 50~100 条 golden set(每条标注预期路由 + 答案要点),每次改 prompt、改阈值、换 embedding 就回归跑一遍。否则"质量提升了"不可证伪。

### 定位判定

"FAQ 智能体问答系统"的定位成立,更准确的说法是:**查询路由 + agentic RAG**。智能体性来自三点:检索是工具、澄清是多轮状态、"答还是问"是自主决策。FAQ 直答这条反而最不"智能体"——它是确定性管道,而这正是它的价值。

## 四、修正后的设计蓝图

### 四条路由(粗路由起步)

| 路由 | 判定条件 | 动作 |
|------|---------|------|
| A. FAQ 直答 | 答案之书语义匹配,高置信 | 直接返回标准答案,标注"已验证" |
| B. RAG 生成 | 知识库内,问题完整 | 按原因/结果/过程模板定向生成,带来源引用 |
| C. 澄清 | 问题欠完整/意图不明 | 一轮追问,给 ≤3 个编号选项,按选择再走 A/B |
| D. 拒答 | 知识库外/超纲/敏感 | 明说不知道,给替代路径(转人工/查 XX) |

配套原则:

- 两条轴分开想:路由轴(库内/库外 × 完整/欠完整)决定走哪条;形态轴(原因/结果/过程)决定答案形状,对 A/B 都适用;
- FAQ 置信分三档:高→直答;中→答+标来源;低→落 RAG;
- 澄清一轮封顶;
- 每条 RAG 答案带来源引用。

### 答案之书飞轮

```text
RAG 对话日志 → 答得好且被反复问 → 人工审核队列 → 沉淀入书
                                                    (带验证日期/负责人/时效提示)
```

### 评估闭环

50~100 条 golden set(每条标预期路由 + 答案要点) → 每次改 prompt/阈值/embedding 回归跑 → 只认数字不认感觉。

## 五、公司推进清单(按序执行,每步有验收)

1. **拉真实问题**(30~60 min):从 AstrBot 管理台/数据库导出最近 1~2 周钉钉真实提问;没有历史就先在钉钉里造 30 条典型问题。顺手给每条标注预期路由(A/B/C/D)——这一步同时产出 **golden set v0**。
   - 验收:≥30 条,每条有预期路由标注。
2. **答案之书 v0**(60~90 min):从问题清单挑 Top 10~20 高频事实类问题,人工写验证过的答案。每条格式:**问题 / 标准答案 / 别名问法 / 验证日期 / 时效提示**。
   - 验收:10+ 条,答案有据可查(能指向文档或实测)。
3. **AstrBot 配置**(30~60 min):答案之书建为独立知识库(或 markdown 文件)带 verified 标记;主知识库保持现状;persona/system prompt 写入四路由规则与澄清行为(一轮封顶、编号选项)。
   - 验收:问一条 FAQ 能命中直答;问一条超纲问题能拒答而不是编。
4. **首轮回归**(30 min):用 golden set v0 逐条测,记录路由对不对、答案质量、幻觉案例。
   - 验收:一张"问题-预期路由-实际路由-结果"对照表。
5. **定阈值与误路由分析**(30 min):统计 FAQ 误命中/漏命中,调阈值初值(余弦相似度 0.75~0.8 起步);误路由最多的那一类,优先改对应 prompt。
6. **立飞轮**(15 min):定周期(如每周五 30 min)审核 RAG 日志,好答案沉淀入书;同时把本周新误路由案例补进 golden set。

## 六、待定决策点

- 澄清选项交互:编号列表(通用稳妥)vs 钉钉卡片按钮(体验好但依赖平台能力);
- 拒答话术与转人工路径(转给谁、怎么留痕);
- 中置信 FAQ 命中的呈现方式(直接答+标来源,还是答完附详细版本入口);
- embedding 与生成模型选型(盘点 AstrBot 当前配置,先不动,回归基线建立后再谈优化)。
