# Agent 接入大模型的方式

本文围绕 Code Agent、办公 Agent 以及类似 Claude Code、Codex、Zcode 的工具，说明它们如何接入大模型。

## 一、先区分两个概念

接入大模型时经常混淆两个维度：

- **服务形态**：模型运行在哪里，由谁提供，例如云端 API、云厂商平台、本地模型、第三方中转。
- **接口规范**：应用如何调用模型，例如厂商原生 API、OpenAI 兼容接口、Anthropic 格式接口。

因此，下面这些组合都可能存在：

```text
云端 API + 厂商原生接口
云端 API + OpenAI 兼容接口
本地模型 + OpenAI 兼容接口
第三方中转 + OpenAI 兼容接口
```

“OpenAI 兼容”描述的是接口形式，不代表模型一定由 OpenAI 提供。

## 二、常见接入方式

### 1. 模型厂商自己的云端 API

模型运行在服务商的服务器上，应用通过网络调用。例如智谱 API、MiniMax API、OpenAI API、Anthropic API 等。

```text
Agent -> 厂商云端 API -> 模型
```

云端 API 不只是给自己写 Code Agent 使用，也可以用于聊天、摘要、客服、文档分析、办公自动化和批量处理等各种应用。

如果直接使用智谱或 MiniMax 提供的 SDK 和接口规范，就是厂商的**原生 API**。原生 API 通常能最完整地使用该厂商的能力，例如特殊参数、多模态、工具调用、缓存、知识库或检索等扩展功能。

### 2. 云厂商或多模型平台

例如火山引擎、腾讯云等平台，可能同时提供自家模型、第三方模型、开源模型或面向 Coding Agent 的套餐。

```text
Agent -> 云厂商模型平台 -> 多种模型
```

从使用者角度看，这类平台像一个统一的模型入口：一个账号、一个接口地址、多个模型和统一的计费或套餐。但它们不一定是纯粹的第三方聚合平台，通常还包含云基础设施、企业权限、审计和合规能力。

### 3. 第三方聚合或中转服务

例如 AICodeMirror 一类服务，向用户提供一个接口，背后再转发到不同模型服务或账号。

```text
Agent -> 第三方中转 -> 上游模型服务
```

这类服务的便利性较高，但需要关注数据是否经过第三方、稳定性、额度来源、计费方式、隐私和服务条款。

### 4. 自部署或本地模型

模型运行在自己的服务器、内网或个人电脑上，应用通过内部 HTTP 接口调用。常见工具包括 Ollama、vLLM、SGLang、llama.cpp 等。

```text
Agent -> 内部模型服务 -> 自有 GPU 上的模型
```

优点是数据控制能力强、可以离线使用；代价是需要自己承担 GPU、部署、升级、并发、监控和故障恢复。

## 三、云端 API 与 OpenAI 兼容接口

### 云端 API 是什么

云端 API 表示模型运行在服务商服务器上，应用通过网络请求使用模型。它是一种**服务形态**，不是某一种固定接口格式。

云端 API 可以使用：

- 厂商自己的原生接口和 SDK；
- OpenAI 兼容接口；
- 其他标准或兼容协议。

### OpenAI 兼容接口是什么

OpenAI 兼容接口是一种通用调用方式。服务商按照 OpenAI 常见的请求和响应结构提供服务，这样原本支持 OpenAI SDK 的 Agent 往往只需要修改配置，就可以使用其他模型。

通常需要填写：

```text
Base URL
API Key
Model
```

配置后可能只需切换这几个值，就能在不同模型之间切换。

### 原生 API 与兼容接口的区别

| 对比项 | 厂商原生 API | OpenAI 兼容 API |
| --- | --- | --- |
| 接口设计 | 厂商自己设计 | 模仿 OpenAI 常见格式 |
| SDK | 使用厂商 SDK | 通常可以复用 OpenAI SDK |
| 接入成本 | 需要适配厂商接口 | 通常只改地址、Key 和模型名 |
| 能力完整度 | 通常最完整 | 可能只支持通用能力 |
| 厂商特色功能 | 支持最好 | 可能没有完全暴露 |
| 适用场景 | 深度使用单一厂商 | 多模型切换、快速接入 Agent |

OpenAI 兼容接口不是所有模型能力的完整标准。普通文本对话、流式输出和基础工具调用通常比较容易兼容，但复杂工具调用、思考过程、多模态、缓存、上下文长度、Token 统计和错误处理可能存在差异。

## 四、三个配置字段是什么意思

### Base URL

表示请求发送到哪个服务地址，也就是“去哪里”。例如：

```text
https://api.example.com/v1
```

客户端可能会自动拼接具体接口路径，形成：

```text
https://api.example.com/v1/chat/completions
```

### API Key

表示调用者身份和权限，也可以理解为“你是谁、额度记在哪个账户”。服务商通过它判断权限、套餐、用量和计费对象。

API Key 不应提交到 Git，也不应放在公开的前端代码中。更稳妥的结构是：

```text
前端或 Agent -> 自己的后端 -> 大模型 API
```

### Model

表示具体使用哪个模型，也就是“让谁处理请求”。模型名称必须使用服务商提供的准确标识符，不能只填界面上看到的展示名称。

三者合起来就是：

```text
Base URL：找到哪家服务
API Key：确认身份和额度
Model：选择具体模型
```

## 五、URL 中的 `/v1`、`/v2` 和接口路径

一个完整地址可能是：

```text
https://api.example.com/v1/chat/completions
```

其中：

- `https://api.example.com`：服务域名；
- `/v1`：API 版本；
- `/chat/completions`：具体功能接口。

`/chat/completions` 通常表示聊天补全接口。`/responses` 是另一种更综合的响应接口，可能更适合工具调用、多模态和复杂 Agent 工作流。两者不是简单的“旧版”和“新版”，而是不同的接口设计，具体要看 Agent 和服务商支持哪一个。

`v1` 和 `v2` 表示 API 版本，但不同厂商的定义不统一。`v2` 不一定自动代表更好，也可能意味着请求格式、认证、返回结构或支持能力发生了变化。不能仅凭版本号判断兼容性，应以服务商文档为准。

## 六、为什么需要代理层

Claude Code、Codex、Zcode 等 Agent 可能按照某个固定协议调用模型。例如 Claude Code 主要使用 Anthropic 风格的请求和响应格式，而目标模型可能只支持自己的原生格式或 OpenAI 格式。

这时可以加入代理层，例如 CCSwitch 这类工具在代理转换模式下的逻辑：

```text
Claude Code
  -> Anthropic 格式请求
  -> CCSwitch 代理层
  -> 智谱 / MiniMax 格式请求
  -> 模型服务
  -> CCSwitch 转换响应
  -> Claude Code
```

代理层可能转换：

- Base URL 和认证信息；
- 模型名称；
- `system`、`messages` 等请求字段；
- 工具调用格式；
- 思考内容和流式输出事件；
- Token 用量、错误码和错误消息。

这里更准确的说法不是“修改 SDK”，而是做**协议适配**：把一种 API 请求和响应格式转换成另一种格式。

有些切换工具只是修改 `Base URL`、`API Key` 和模型环境变量，让 Agent 直接请求一个已经支持目标协议的服务；这种情况下，转换工作由目标服务完成。只有当目标服务协议不同，才需要本地代理真正做请求和响应转换。

代理转换并不一定能做到完全一致。普通文本对话比较容易适配，但复杂 Coding Agent 场景中的工具调用、流式事件、思考过程、多模态输入、上下文缓存和错误处理都可能出现差异。

## 七、实际选择建议

```text
只使用一家模型，追求完整能力       -> 厂商原生 API / SDK
需要快速接入多个模型               -> OpenAI 兼容接口
使用已有的 Code Agent 切换模型      -> 兼容接口或协议代理层
需要统一监控、配额和故障切换        -> 自建模型网关或统一适配层
敏感数据、内网或离线使用            -> 自部署 / 本地模型
```

Coding Plan 需要单独确认是否开放通用 API、OpenAI 兼容接口或第三方 Agent 使用权限。订阅 Coding Plan 不一定等于拥有一个可以任意调用的通用 API Key，应以厂商说明为准。

## FAQ

### 1. 云端 API 是不是专门给自己写 Agent 使用的？

不是。云端 API 只是模型运行在服务商云端并通过网络调用，聊天、办公自动化、客服、文档分析和 Code Agent 都可以使用。

### 2. 一个模型厂商能不能同时提供原生 API 和 OpenAI 兼容 API？

可以，而且很常见。原生 API 用厂商自己的 SDK 和格式，兼容 API 用 OpenAI 常见格式，方便更多平台和工具接入。

### 3. OpenAI 兼容接口是不是模型由 OpenAI 提供？

不是。它只表示接口格式类似 OpenAI，背后可能是智谱、MiniMax、火山引擎、本地模型或第三方中转服务。

### 4. OpenAI 兼容接口是不是原生 API 的阉割版？

不一定。它通常能覆盖通用能力，但厂商独有功能可能只有原生 API 支持，或者兼容接口没有完整暴露。

### 5. `Base URL` 应该填完整的 `/chat/completions` 地址吗？

如果配置项叫 `Base URL`，通常填到域名加版本路径，例如 `https://api.example.com/v1`。Agent 会自动拼接具体接口路径。但不同客户端实现不同，应以服务商和 Agent 文档为准，避免重复拼接路径。

### 6. `/v1` 和 `/v2` 是模型版本吗？

通常不是，而是 API 版本。它们表示接口格式或能力可能不同，不代表模型一定升级，也不保证彼此兼容。

### 7. 为什么同一个 API Key 还要填写 Model？

API Key 只负责身份、权限和额度，Model 才决定具体调用哪个模型。一个账户通常可以访问多个模型。

### 8. Coding Plan 能不能直接拿来接入其他 Agent？

要看套餐和服务商是否明确支持 API、OpenAI 兼容接口或第三方客户端。不能简单认为“开通 Coding Plan 就等于获得通用 API Key”。

### 9. Claude Code 接入智谱或 MiniMax 时，谁负责格式转换？

如果目标服务直接支持 Claude Code 所需的 Anthropic 格式，就由目标服务处理；如果只支持其他协议，则需要 CCSwitch 这类代理层转换请求和响应。

### 10. 使用第三方中转有什么主要风险？

请求数据可能经过第三方，服务稳定性、额度来源、计费、隐私和服务条款都需要确认。生产环境和敏感代码尤其要谨慎。
