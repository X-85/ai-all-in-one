# AI 治理工程方法论

> 面向研发团队的 AI Agent 工程治理实践：从需求理解、方案设计、代码实现到验证、发布和缺陷闭环。

## 1. 核心判断

AI 带来的不只是一个更快的程序员，而是研发系统中出现了大量可以并行、快速行动、但可能失控的执行者。

因此治理重点要从“管理人”扩展为管理：

- 需求是否被正确理解
- 技术决策是否合理
- 变更是否在明确范围内
- 实现是否有可验证证据
- 缺陷是否能回到需求、代码和测试闭环

AI 时代最重要的能力不是让 AI 更快写代码，而是能够证明：

> AI 开始写代码之前，它和人理解的是同一个问题；AI 写完代码之后，有证据证明结果符合预期。

## 2. 关注点与必要性

需要重点治理的风险包括：

- 错误理解需求后高速实现
- 把隐含假设当成已确认事实
- 将大需求拆成遗漏关键路径的小任务
- 只验证“能编译”，没有验证“行为正确”
- 多轮对话后丢失上下文和决策
- 需求变化后规格、代码、测试和文档没有同步
- Bug 修复没有补充回归测试，问题反复出现

这些问题不是 AI 专属，但 AI 会显著放大它们的速度和影响范围。因此需求澄清、变更边界、验证证据和可追溯性都必须前置。

## 3. 端到端治理链

完整的证据链应当是：

```text
需求/问题
  -> 需求理解与澄清
  -> 规格与验收条件
  -> 架构决策与影响分析
  -> 可执行任务
  -> 代码变更
  -> 测试与审查证据
  -> 发布
  -> 线上反馈/缺陷
  -> 新需求或修复
```

每一步都应该能够追溯到上一步，任何一个“完成”都必须有证据，而不是只依赖 Agent 的口头报告。

## 4. 需求治理：先治理“做什么”

### 4.1 需求进入研发前的最低信息

- 要解决的用户问题
- 目标用户和使用场景
- 预期收益与优先级
- 范围及明确不做的内容
- 正常、异常和边界场景
- 验收条件
- 风险、依赖和发布约束
- 需求负责人和决策人

AI 可以帮助整理反馈、发现冲突、提出方案、拆解需求和生成场景，但不能替代人确认“这个问题是否值得解决”和“做到什么程度算完成”。

### 4.2 需求理解闸门

需求不能直接交给 Agent 实现。先要求 Agent 生成 `understanding.md`，至少包含：

```markdown
# 需求理解

## 我理解的问题
## 用户和使用场景
## 目标
## 不在范围内
## 已确认事实
## 未确认假设
## 关键问题
## 正常场景
## 异常和边界场景
## 必须保持的不变量
## 验收条件
## 如果以下答案改变，方案需要重做
```

只有在以下条件满足后，才进入方案设计：

- 没有会改变架构或范围的高风险未确认假设
- 至少有正常、异常和边界场景
- 有明确的不做范围
- 有可执行的验收条件
- 已明确哪些既有行为不能破坏
- 产品或需求负责人确认了关键问题

## 5. Grill-Me：需求反向审问机制

类似 `grill-me` 的 skill 或提示词模式很有价值。它的作用不是写代码，而是逼迫 Agent 暴露理解、假设、反例和不确定性。

### 5.1 推荐流程

#### 第一轮：重述

Agent 用自己的话说明：

- 要解决的问题
- 目标用户
- 预期行为
- 影响范围
- 暂时理解的成功标准

#### 第二轮：找漏洞

按“答案不同会导致方案不同”的优先级提问，重点覆盖：

- 产品规则
- 模块边界
- 数据模型
- 公共接口和兼容性
- 权限与安全
- 性能和容量
- 测试边界

不要一次提出几十个低价值问题，应优先解决高影响的不确定性。

#### 第三轮：反例攻击

主动检查：

- 空输入和重复操作
- 并发操作
- 超时、网络失败和部分成功
- 权限不足
- 数据存在或不存在
- 老版本数据
- 用户中途退出
- 重试和幂等性

#### 第四轮：生成验收场景

例如：

```markdown
场景：用户重复导入同一个能力
前置条件：能力已经存在
操作：再次执行导入
预期：拒绝重复导入，并给出明确提示
```

#### 第五轮：输出决策摘要

最终只保留：

```text
已确认决策
未解决问题
关键假设
需求边界
验收条件
是否可以进入设计
```

### 5.2 重要限制

AI 自己提问、自己回答，不能证明需求已被正确理解。可靠流程是：

```text
AI 重述
  -> AI 列出假设和疑问
  -> 人确认关键决策
  -> AI 生成验收场景
  -> 人确认场景
  -> 进入设计和实现
```

## 6. 方案与架构治理：治理“怎么做”

中大型变更建议使用一个变更包，至少包含：

```text
proposal.md   为什么做、范围、不做什么
requirements  需求、规则和验收场景
design.md     模块边界、接口、数据流和兼容性
tasks.md      可独立完成的实现任务
verification  测试、检查和验收结果
```

架构审查重点：

- 是否违反模块边界
- 是否引入不必要的依赖
- 是否破坏已有接口或数据
- 是否有迁移、兼容和回滚策略
- 是否影响性能、安全和可观测性
- 是否把临时方案固化成长期架构

CodeGraph 适合帮助 Agent 查询调用关系、依赖和变更影响，但不能替代架构决策。

## 7. 任务与代码治理：治理“如何改”

每个 Agent 任务应包含执行契约：

```text
目标：
允许修改的目录：
禁止修改的目录：
前置依赖：
完成条件：
必须运行的命令：
发现公共接口变化时的停止条件：
输出格式：
```

任务设计原则：

- 一个任务只解决一个行为变化
- 尽量限定在一个模块或一个垂直切片
- 每个任务都有可执行的完成条件
- 代码、测试和文档一起变更
- 发现需要扩大范围时暂停并报告
- 高风险变更不得由 Agent 自动合并
- 每次执行记录修改内容、验证内容和未验证内容

## 8. 质量治理：完成不等于代码能编译

建议设置四道质量门：

### 8.1 需求门

- 目标、范围和不做项清晰
- 有正常、异常和边界场景
- 验收条件可执行

### 8.2 设计门

- 模块边界和影响范围明确
- 接口、数据、兼容和回滚方案明确
- 安全、性能和可观测性风险已评估

### 8.3 代码门

- 格式化和静态检查通过
- 单元测试通过
- 错误处理和资源释放合理
- 依赖和安全检查通过
- 变更范围符合任务契约

### 8.4 行为门

- 集成测试通过
- 关键 UI 流程通过 Playwright 或真实操作验证
- 必要时做截图和视觉回归
- 关键场景有人验收
- 发布后有监控和回滚路径

## 9. Bug 治理：缺陷必须回到证据链

Bug 不能只是聊天中的“帮我修一下”。至少记录：

```text
Bug ID
严重等级
影响范围
复现步骤
实际结果与期望结果
环境和版本
日志、截图或测试证据
关联需求、变更和提交
修复验证方式
是否补充回归测试
```

关闭 Bug 的条件应是：

```text
Bug
  -> 可复现
  -> 根因明确
  -> 修复完成
  -> 回归测试通过
  -> 相关验收场景更新
  -> 发布版本可追溯
```

如果 Bug 暴露的是需求理解错误，除了修代码，还应更新规格、验收条件、回归测试和相关架构决策。

## 10. 工具分工

| 工具或系统 | 主要职责 | 不应承担的职责 |
| --- | --- | --- |
| Issue Tracker | 需求、Bug、优先级、负责人 | 详细技术设计的唯一来源 |
| Grill / requirements-grill | 暴露假设、澄清需求、生成反例 | 自行决定产品范围 |
| OpenSpec | 规格、设计、变更包和任务计划 | 线上任务状态的唯一来源 |
| CodeGraph | 代码理解、依赖和影响分析 | 替代架构决策 |
| Trellis | 任务依赖、执行状态和会话恢复 | 替代需求管理 |
| Codex/其他 Agent | 实现、测试、诊断和文档 | 未经授权扩大范围 |
| Git 与 CI | 变更隔离、审查和自动化证据 | 判断产品价值 |
| Playwright/Screenshot | UI 行为和视觉验证 | 替代业务验收 |
| 日志与 Sentry | 发布后反馈和诊断 | 代替测试 |

推荐的主数据归属：

- Issue Tracker：需求和 Bug 的主记录
- OpenSpec：某次变更的规格和设计记录
- Trellis：任务执行和依赖状态
- Git/CI：代码变更和验证证据

不要让多个工具同时维护同一份独立状态。

## 11. 角色职责

### 产品经理

负责“做什么”：

- 问题和用户价值
- 目标与优先级
- 范围和不做项
- 成功指标和验收条件

### 架构师

负责“怎么做以及影响什么”：

- 模块边界
- 数据和接口变化
- 兼容、迁移和回滚
- 安全、性能和可观测性

### 开发者

负责“如何可靠地改”：

- 任务边界
- 实现质量
- 测试和验证
- 代码审查
- 技术债务和维护成本

AI 可以参与三类工作，但不能把三类责任混为“AI 已经决定”。

## 12. 衡量治理效果

不要只统计 AI 生成了多少代码。建议关注：

- 需求到发布的周期
- 需求澄清后返工率
- 首次验证通过率
- PR 返工次数
- 关键路径测试覆盖率
- 线上缺陷逃逸率
- AI 变更人工回滚比例
- Bug 平均修复时间
- 需求、代码、测试之间的可追溯率

可以给需求做简单质量评分，每项 0 到 2 分：

| 维度 | 判断问题 |
| --- | --- |
| 问题清晰度 | 是否知道解决什么问题 |
| 用户清晰度 | 是否知道谁受益 |
| 范围清晰度 | 是否知道做什么和不做什么 |
| 行为清晰度 | 是否有正常、异常、边界场景 |
| 约束清晰度 | 是否知道兼容、安全、性能要求 |
| 验收清晰度 | 是否能写出可执行验证 |

总分过低时不进入实现阶段。涉及数据、安全、公共 API 的需求，即使分数足够，也需要人工审查。

## 13. 在 Elwright 中的落地建议

Elwright 已经具备较好的基础：

- `docs/features/`：长期行为和架构文档
- `docs/work/active/`：当前变更计划
- `plan/checklist/verification`：执行和验证
- `ROADMAP.md`：路线和状态
- `AGENTS.md`：Agent 工作约束

建议演进为：

```text
需求进入
  -> understanding.md
  -> Grill 追问和确认
  -> OpenSpec proposal/spec/design
  -> CodeGraph 影响分析
  -> Trellis 任务拆解和执行
  -> Codex 实现
  -> 测试 / Playwright / 安全检查
  -> verification.md
  -> 发布和 Bug 反馈
```

不建议一开始同时引入三套新的状态系统。更稳妥的顺序是：

1. 先把现有 `docs/work/active/` 规范成统一变更包。
2. 增加 `understanding.md` 和需求 Grill 阶段。
3. 用 OpenSpec 的 proposal/spec/design/tasks 思路补齐需求和设计。
4. 只有跨会话、长周期或并行任务失控时，再引入 Trellis。
5. 只有跨模块影响分析成为瓶颈时，再引入 CodeGraph。
6. 用 CI、Playwright、安全检查和验证报告建立完成证据。

## 14. 最小可行治理流程

对于个人项目或小团队，可以先只执行以下流程：

```text
1. 需求进入 Issue
2. Agent 生成 understanding.md
3. 人确认关键问题、范围和验收条件
4. Agent 生成 design.md 和 tasks.md
5. 人审查高风险设计
6. Agent 按小任务实现
7. 每个任务执行规定的测试命令
8. 生成 verification.md
9. 合并前检查需求、代码、测试和文档是否可追溯
10. Bug 必须补回归测试并更新相关场景
```

这套流程的目标不是增加文档数量，而是让每一次 AI 变更都具备：

```text
有来源、有范围、有决策、有负责人、
有代码、有测试、有审查、有回滚路径。
```
