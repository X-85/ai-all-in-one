# AI 治理工程方法论：问答原话

> 以下内容按本次对话原文整理。正文保留问题与回答的原有表述，仅增加标题和分隔线，便于作为 FAQ 查阅。

## 问题一：CodeGraph、Trellis、OpenSpec 是做什么的？

### 用户

codegraph ，trellis ，openspec这三个软件都是干嘛用的

### Codex

如果你说的是 AI 编程圈最近常见的这三个工具，它们分别解决不同问题：

| 工具 | 主要用途 | 一句话理解 |
|---|---|---|
| **CodeGraph** | 建立本地代码语义图，分析符号、调用关系、依赖和跨文件影响，并通过 MCP 提供给 Codex/Claude/Cursor | 让 AI 更准确地“读懂已有代码” |
| **Trellis** | 把项目拆成 Project → Epic → Feature → Task，管理依赖、进度、任务认领和多会话衔接 | 让 AI 按任务、有秩序地持续开发 |
| **OpenSpec** | 规范驱动开发，先生成 proposal、requirements、design、tasks，再执行和归档 | 让 AI “先把要做什么说清楚，再写代码” |

具体来说：

**CodeGraph**

它不是普通的代码可视化工具，而是面向 AI coding agent 的本地代码智能层。它会索引代码，生成代码图，再通过 MCP 让 AI 查询：

- 某个函数被谁调用
- 修改一个模块可能影响什么
- 某个 API、类型或业务流程的完整关系
- 哪些测试、文件和调用链可能需要同步修改

常见项目是 [colbymchenry/codegraph](https://github.com/colbymchenry/codegraph)，支持 Codex、Claude Code、Cursor 等。

**Trellis**

这里有几个同名项目。AI 编程语境中最常见的是 [Task Trellis MCP](https://github.com/langadventurellc/task-trellis-mcp)：

- 把需求拆成层级任务
- 处理任务依赖
- 记录进行中、已完成和待处理状态
- 记录每个任务改过哪些文件
- 支持跨多次 AI 对话继续工作

它更像“给 AI coding agent 用的项目管理器”，而不是 Jira 的普通替代品。

另外还有一个 [Trellis Workflow Enhancer](https://github.com/lei1024/trellis-workflow-enhancer)，它主要是增强已有 Trellis 工作流，通过 hooks、验证和技能路由来改善执行过程。若你看到的是这个，功能会偏“工作流编排”而不是任务管理。

**OpenSpec**

[OpenSpec](https://openspec.dev/) 是 spec-driven development 工具。它通常按这样的流程工作：

```text
/opsx:explore
    -> /opsx:propose
    -> review proposal / specs / design / tasks
    -> /opsx:apply
    -> /opsx:verify
    -> /opsx:archive
```

它会在项目中维护类似：

```text
openspec/
  specs/
  changes/
    add-dark-mode/
      proposal.md
      design.md
      tasks.md
```

核心价值是把“需求、设计、验收条件和实现任务”从聊天上下文中提取出来，变成可审查、可提交、可持续更新的 Markdown 文档。

对你的 Elwright，三者可以这样组合：

```text
CodeGraph：先理解 Rust/Vue/Tauri 现有结构
OpenSpec：定义要增加的功能和验收条件
Trellis：拆分任务、安排依赖、持续跟踪执行
Codex：逐项实现并运行测试
```

我的判断是：

- 小改动：直接用 Codex，没必要三个都上。
- 中大型功能：**OpenSpec + Trellis** 很有价值。
- 老项目、跨模块修改、担心 AI 漏改调用方：再加 **CodeGraph**。
- Elwright 目前已经有 `docs/features/`、`docs/work/active/`、`ROADMAP.md` 和维护协议，所以 OpenSpec/Trellis 会和现有文档体系产生一定重叠，最好先选一个作为主任务系统，不要两套状态同时维护。

## 问题二：如何使用 AI 治理工程？

### 用户

我需要一套治理ai agent写的工程的工具或者方法论，这套方法论面向研发，从研发收到需求，使用ai把需求拆解为小需求，然后做计划，再去实现，在对实现的验证。包括对需求的管理，对代码开发的管理，对代码质量的管理，对bug的管理等，我借助上面的工具可以做到一部分，但不能做到完整的管理，ai带来了效率，但也引来了变化，关于如何在变化中使用ai或者应运而生的新工具来治理工程，从资深产品经理，资深架构师以及资深开发的角度给出你的理解

### Codex

我的核心判断是：AI 带来的不是“多一个程序员”，而是研发系统中出现了大量可以并行、快速行动、但容易失控的执行者。因此治理重点要从“管理人”转向“管理需求、决策、变更和证据”。

不能只靠 OpenSpec、Trellis 或 CodeGraph。它们分别解决规范、任务和代码上下文问题，但完整治理需要一条可追踪的证据链：

```text
需求
  -> 规格与验收条件
  -> 架构决策
  -> 实现任务
  -> 代码变更
  -> 测试与审查证据
  -> 发布
  -> 线上反馈/缺陷
  -> 新需求或修复
```

每一环都必须能追溯到上一环。

## 一、从产品经理角度：先治理“做什么”

需求不能直接交给 AI。需求进入研发前，至少应明确：

- 要解决的用户问题
- 预期收益和优先级
- 范围与明确不做的内容
- 用户场景和验收条件
- 风险、依赖和发布约束
- 谁对结果负责

AI 可以帮助：

- 整理访谈、Issue、反馈
- 发现需求冲突和遗漏
- 生成多个方案
- 把大需求拆成用户可验证的小需求
- 生成验收场景和边界条件

但产品负责人必须确认：“这个问题值得解决”和“做到什么程度算完成”。AI 不应该自行决定产品范围。

建议把需求分成三类：

1. 探索：还不知道该怎么做。
2. 规格：目标、范围和验收条件已经明确。
3. 交付：可以拆成开发任务。

OpenSpec 适合管理第二类，不能代替产品优先级管理。

## 二、从架构师角度：治理“怎么做以及影响什么”

每个中大型变更都应该有一个变更包，至少包含：

```text
proposal.md   为什么做、范围、不做什么
requirements  可验证的需求和场景
design.md     模块边界、接口、数据流、兼容性
tasks.md      可独立完成的小任务
verification  测试、检查和验收结果
```

架构师重点审查：

- 是否违反模块边界
- 是否引入不必要的依赖
- 是否破坏已有接口
- 是否有迁移、回滚和兼容策略
- 是否影响安全、性能和可观测性
- 是否把临时方案写成了长期架构

CodeGraph 的价值在这里：帮助 AI 查询调用关系、影响范围和依赖，而不是让 AI 凭搜索结果猜代码结构。

Trellis 的价值在于执行层：任务依赖、任务认领、进度和多会话恢复。它不应该成为需求和架构决策的唯一存储地。

## 三、从开发者角度：治理“AI 如何改代码”

每个 AI 任务都应该有明确的执行契约：

```text
目标：
允许修改的目录：
禁止修改的目录：
前置依赖：
完成条件：
必须运行的命令：
失败时停止条件：
输出格式：
```

例如：

```text
只修改 src-tauri/src/core/invoke.rs 及其测试。
不得修改注册表格式。
完成条件是 cargo test 全部通过，并新增离线降级测试。
如果发现需要修改公共接口，停止并报告，不自行扩大范围。
```

AI 任务应尽量满足：

- 一个任务只解决一个行为变化
- 单次变更控制在一个模块或一个垂直切片内
- 每个任务都有可执行的完成条件
- 代码、测试和文档一起提交
- AI 不直接合并高风险变更
- 每次执行都记录改了什么、验证了什么、未验证什么

“AI 生成了多少代码”不是有效指标。更有价值的是：

- 需求到发布的周期
- 首次验证通过率
- PR 返工次数
- 测试覆盖的关键路径
- 线上缺陷逃逸率
- AI 修改后被人工回滚的比例
- 需求变更造成的返工成本

## 四、质量治理：完成不等于代码能编译

建议把质量分成四道门：

### 需求门

- 验收条件是否明确
- 是否有反例和异常场景
- 是否定义了不做的范围

### 设计门

- 架构边界是否清晰
- 影响范围是否评估
- 是否有兼容和回滚方案

### 代码门

- 格式化、静态检查、单元测试
- API 和错误处理检查
- 安全检查
- 依赖和资源检查

### 行为门

- 集成测试
- Playwright 或真实 UI 流程
- 关键场景人工验收
- 发布后监控和回滚验证

只有“证据齐全”才能进入 Done，而不是 AI 说“已完成”。

## 五、Bug 管理：Bug 是需求偏差，不是聊天里的临时任务

每个 Bug 至少记录：

```text
Bug ID
严重等级
影响范围
复现步骤
实际结果
期望结果
环境和版本
日志、截图或测试证据
关联需求/变更/提交
修复验证方式
是否需要补充回归测试
```

AI 很适合做：

- 从日志和 Issue 归纳复现条件
- 定位可能的调用链
- 生成最小复现
- 提出修复方案
- 补回归测试
- 检查相似问题

但 Bug 关闭必须有人或自动化证据确认，不能以“代码已修改”作为关闭标准。

## 六、这三个工具如何组合

我会这样分工：

| 工具 | 负责 |
|---|---|
| Issue Tracker | 需求、Bug、优先级、责任人 |
| OpenSpec | 需求规格、设计、任务计划和变更记录 |
| Trellis | 任务执行、依赖、进度和会话恢复 |
| CodeGraph | 代码理解、影响分析和上下文查询 |
| Codex/其他 Agent | 实现、测试、文档和诊断 |
| Git + CI | 变更隔离、审查和自动化证据 |
| Playwright/Screenshot | UI 行为和视觉验证 |
| Sentry/日志系统 | 发布后的问题反馈 |

不要让 OpenSpec、Trellis 和 Issue Tracker 都维护一份独立状态。建议：

- Issue Tracker 是需求和 Bug 的主记录
- OpenSpec 是某次变更的规格记录
- Trellis 是执行计划和任务状态
- Git/CI 是实现与验证证据

## 七、从三个角色看，必须补充的治理点

### 产品经理：治理“做什么”

产品侧要防止 AI 把模糊愿望直接变成技术任务。

必须明确：

- 问题，而不是解决方案
- 目标，而不是功能数量
- 用户价值，而不是代码产出
- 优先级和不做范围
- 成功指标
- 验收场景

AI 可以辅助拆解，但产品负责人必须确认范围和优先级。

### 架构师：治理“怎么做”

架构侧必须关注：

- 模块边界
- 数据和接口变化
- 兼容性
- 迁移和回滚
- 性能
- 安全
- 可观测性
- 长期维护成本

CodeGraph 可以帮助 AI 做影响分析，但不能替代架构决策。

### 开发者：治理“如何改”

开发任务需要明确执行契约：

```text
目标：
允许修改的目录：
禁止修改的目录：
前置依赖：
完成条件：
必须执行的测试：
发现公共接口变化时如何处理：
```

AI 不应获得无限制的“自由修改整个仓库”权限。任务越小，验证越可靠，回滚越容易。

## 八、对 Elwright 的建议

你现在的文档体系已经有很好的基础：

- `docs/features/` 管长期行为
- `docs/work/active/` 管当前变更
- `plan/checklist/verification` 管执行和验证
- `ROADMAP.md` 管路线
- `AGENTS.md` 管 Agent 工作约束

我不建议马上引入三套新的状态系统。更适合的演进是：

```text
需求进入
  -> understanding.md
  -> Grill 追问和确认
  -> OpenSpec proposal/spec/design
  -> CodeGraph 影响分析
  -> Trellis 任务拆解和执行
  -> Codex 实现
  -> 测试 / Playwright / 安全检查
  -> verification.md
  -> 发布和 Bug 反馈
```

最值得优先实现的不是 CodeGraph 或 Trellis，而是一个项目级的 `requirements-grill` skill，以及一份统一的需求理解模板。

因为如果需求错了：

- OpenSpec 会把错误需求写得更正式
- Trellis 会把错误需求拆得更细
- CodeGraph 会让 AI 更高效地修改错误的位置
- Codex 会更快地完成错误的实现

AI 时代最重要的能力不是“让 AI 更快写代码”，而是：

> 在 AI 开始写代码之前，能够证明它和人理解的是同一个问题。

## 问题三：我关心什么？是否有 Grill-Me 类工具？

### 用户

你说的有道理，从我的问题中分析我关心的是什么，这些关心是否必要，除了你刚才的回答还有没有其他补充？
比如是否有类似grill-me类似skill或者工具可以帮我们检查需求是否理解透，这样才可以指导ai更好的管理需求，开发代码

### Codex

你真正关心的核心不是“有哪些 AI 工具”，而是：

> 如何确保 AI 在理解正确的问题上高效工作，并且每一步都留下可检查、可追责、可回滚的证据。

这个关心非常必要。AI 最大的风险不是写不出代码，而是：

- 错误理解需求后高速实现
- 把隐含假设当成事实
- 拆解出看似合理、实际遗漏关键路径的任务
- 修改代码后只验证“能编译”，没有验证“行为正确”
- 多轮对话后丢失上下文和决策
- 需求变了，但规格、代码、测试和文档没有同步变化

所以你需要治理的不是单纯的 Agent，而是四件事：

```text
理解是否正确
决策是否合理
执行是否受控
结果是否有证据
```

## “Grill Me”解决什么问题

类似 `grill-me` 的东西是有价值的，但它通常不是一个统一标准的软件，而是一种“反向审问需求”的 skill 或提示词模式。

它的职责不是直接规划和写代码，而是先逼 AI 和需求提出者回答：

- 你到底要解决什么问题？
- 谁会使用？
- 什么情况不应该触发？
- 哪些内容明确不在范围内？
- 成功和失败分别是什么？
- 有哪些异常、边界和冲突场景？
- 哪些假设尚未确认？
- 如果这个假设错了，设计会不会完全改变？
- 现有系统中哪些行为不能被破坏？
- 这个需求是否真的值得实现？

这是一个重要的前置闸门。

但要注意：AI 自己提问、自己回答，不能证明需求已经理解正确。真正有效的是：

```text
AI 重述
  -> AI 列出假设和疑问
  -> 人确认关键决策
  -> AI 生成验收场景
  -> 人确认场景
  -> 才允许进入设计和实现
```

## 我建议你建立一个“需求理解门”

每个需求进入开发前，强制生成一个 `understanding.md`：

```markdown
# 需求理解

## 我理解的问题
...

## 用户和使用场景
...

## 目标
...

## 不在范围内
...

## 已确认事实
...

## 未确认假设
...

## 关键问题
1. ...
2. ...

## 正常场景
...

## 异常和边界场景
...

## 不变量
哪些已有行为必须保持不变？

## 验收条件
...

## 如果以下答案发生变化，方案需要重做
...
```

AI 只有在以下条件满足后，才能开始设计：

- 没有高风险的未确认假设
- 至少有一个正常场景和多个异常场景
- 有明确的不做范围
- 有可执行的验收条件
- 已明确哪些既有行为不能破坏
- 人确认过关键问题

这比让 AI 直接输出“需求分析和开发计划”可靠得多。

## 一个实用的 `requirements-grill` 流程

你可以把它做成 Codex skill，工作方式类似：

```text
$requirements-grill
```

它不直接改代码，只做需求澄清：

### 第一轮：重述

AI 用自己的话说明：

- 要解决的问题
- 目标用户
- 预期行为
- 影响范围
- 暂时理解的成功标准

### 第二轮：找漏洞

AI 按风险排序提出问题：

- 产品规则不明确的地方
- 会影响架构选择的地方
- 会影响数据模型的地方
- 会影响兼容性的地方
- 会影响安全和权限的地方
- 会影响测试边界的地方

不要让它一次问几十个问题，而是优先问“答案不同会导致方案不同”的问题。

### 第三轮：反例攻击

要求 AI 主动构造：

- 空输入
- 重复操作
- 并发操作
- 超时和网络失败
- 权限不足
- 数据已存在
- 数据不存在
- 老版本数据
- 用户中途退出
- 部分成功、部分失败

### 第四轮：验收场景

输出类似：

```gherkin
Given ...
When ...
Then ...
```

或者普通 Markdown：

```markdown
场景：用户重复导入同一个能力
前置条件：能力已经存在
操作：再次执行导入
预期：拒绝重复导入，并提示已存在
```

### 第五轮：生成决策摘要

最终只输出：

```text
已确认决策
未解决问题
关键假设
需求边界
验收条件
可以进入设计 / 不能进入设计
```

这份结果随后交给 OpenSpec，而不是让 OpenSpec 从原始聊天中重新猜需求。

## 三个工具在这条链中的位置

可以这样组合：

```text
Grill / requirements-grill
    负责确认“我们是不是理解了同一个问题”

OpenSpec
    负责把理解固化为规格、设计和变更包

CodeGraph
    负责确认“现有代码中哪些地方会受影响”

Trellis
    负责把变更拆成可执行任务并持续跟踪

Codex
    负责实现、测试和诊断

CI / Playwright / 安全检查
    负责产生验证证据
```

OpenSpec 自带的 explore/propose 流程已经覆盖了一部分需求澄清，但如果你特别重视“反向审问”和“暴露假设”，最好在它前面增加独立的 Grill 阶段。

## 从三个角色看，必须补充的治理点

### 产品经理：治理“做什么”

产品侧要防止 AI 把模糊愿望直接变成技术任务。

必须明确：

- 问题，而不是解决方案
- 目标，而不是功能数量
- 用户价值，而不是代码产出
- 优先级和不做范围
- 成功指标
- 验收场景

AI 可以辅助拆解，但产品负责人必须确认范围和优先级。

### 架构师：治理“怎么做”

架构侧必须关注：

- 模块边界
- 数据和接口变化
- 兼容性
- 迁移和回滚
- 性能
- 安全
- 可观测性
- 长期维护成本

CodeGraph 可以帮助 AI 做影响分析，但不能替代架构决策。

### 开发者：治理“如何改”

开发任务需要明确执行契约：

```text
目标：
允许修改的目录：
禁止修改的目录：
前置依赖：
完成条件：
必须执行的测试：
发现公共接口变化时如何处理：
```

AI 不应获得无限制的“自由修改整个仓库”权限。任务越小，验证越可靠，回滚越容易。

## 还需要增加一个“需求质量评分”

可以用一个简单评分控制是否进入开发：

| 维度 | 问题 |
|---|---|
| 问题清晰度 | 是否知道解决什么问题 |
| 用户清晰度 | 是否知道谁受益 |
| 范围清晰度 | 是否知道做什么和不做什么 |
| 行为清晰度 | 是否有正常、异常、边界场景 |
| 约束清晰度 | 是否知道兼容、安全、性能要求 |
| 验收清晰度 | 是否能写出可执行验证 |

每项 0 到 2 分。总分低于 8 分，不进入实现阶段；涉及数据、安全、公共 API 的需求，即使分数够，也必须人工审查。

这不是为了制造官僚流程，而是为了把时间花在最便宜的阶段：需求澄清。错误需求在代码阶段才被发现，成本会高很多。

## Bug 也应该回到这条证据链

Bug 不应只是“修一下这个问题”，而应关联：

```text
Bug
  -> 复现步骤
  -> 受影响的验收场景
  -> 根因
  -> 修复变更
  -> 回归测试
  -> 发布版本
```

如果一个 Bug 暴露出需求理解错误，就不能只补代码，还应更新：

- 原始规格
- 验收条件
- 回归测试
- 相关架构决策
- Agent 的规则或检查清单

否则 AI 会在下一个功能中重复犯同类错误。

## 对 Elwright 的建议

你现在的文档体系已经有很好的基础：

- `docs/features/` 管长期行为
- `docs/work/active/` 管当前变更
- `plan/checklist/verification` 管执行和验证
- `ROADMAP.md` 管路线
- `AGENTS.md` 管 Agent 工作约束

我不建议马上引入三套新的状态系统。更适合的演进是：

```text
需求进入
  -> understanding.md
  -> Grill 追问和确认
  -> OpenSpec proposal/spec/design
  -> CodeGraph 影响分析
  -> Trellis 任务拆解和执行
  -> Codex 实现
  -> 测试 / Playwright / 安全检查
  -> verification.md
  -> 发布和 Bug 反馈
```

最值得优先实现的不是 CodeGraph 或 Trellis，而是一个项目级的 `requirements-grill` skill，以及一份统一的需求理解模板。

因为如果需求错了：

- OpenSpec 会把错误需求写得更正式
- Trellis 会把错误需求拆得更细
- CodeGraph 会让 AI 更高效地修改错误的位置
- Codex 会更快地完成错误的实现

AI 时代最重要的能力不是“让 AI 更快写代码”，而是：

> 在 AI 开始写代码之前，能够证明它和人理解的是同一个问题。
