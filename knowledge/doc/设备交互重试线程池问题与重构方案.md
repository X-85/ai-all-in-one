## 1. 任务目标一句话

把「设备交互失败后阻塞式无限重试」的线程池用法，重构为**基于 `ScheduledExecutorService` 的非阻塞调度重试**，使重试等待不再占用工作线程，10 个线程稳定服务 20 个设备。

## 2. 业务背景与现状

### 业务场景

- 系统需要与 **20 个设备**交互（读写/指令下发）。
- 交互失败时**每 2 秒重试一次**，一直失败就一直重试。
- 运行环境：**JDK 8 和 JDK 17**（两套环境都在用，代码需同时兼容，只能用 JDK 8 及以下的 API 与语法）。

### 当前实现（口头描述，待验证）

- 用 `ExecutorService` 线程池，池大小 **10**，20 个设备各提交一个任务。
- 每个任务内部是阻塞式重试循环，形如：

```java
// 现状的典型形态（反面示例，改造对象）
while (true) {
    try {
        interact(device);
        break;                 // 成功退出（或成功后也不退出，待确认）
    } catch (Exception e) {
        Thread.sleep(2000);    // ← 问题核心：sleep 期间线程被白白占用
    }
}
```

## 3. 问题分析：为什么这样会把线程池"锁死"

线程池适合**短任务**；上面这种写法把"无限期的等待"塞进了任务体里：

1. 前 10 个设备占满 10 个线程，后 10 个设备在队列里永远得不到执行；
2. 更糟：如果占住线程的恰好是故障设备，它们会**无限期持有线程**（sleep 2 秒→重试→再 sleep，永不返回），连正常设备都被饿死；
3. sleep 的 2 秒里线程什么都没干，却一直被占着——问题的本质不是"线程不够多"，而是**等待不该占线程**。

## 4. 约束与已否决的备选方案（不要重新讨论）

| 备选方案 | 结论 | 原因 |
|---|---|---|
| 虚拟线程（`newVirtualThreadPerTaskExecutor`） | ❌ 否决 | 需要 JDK 21+，当前只有 8 和 17。可作为未来统一到 21+ 之后的演进方向，本次不做 |
| NIO 多路复用 / Netty（一/几个线程管所有连接） | ❌ 否决 | 20 个设备规模收益低、复杂度高（要自己处理非阻塞读写、粘包拆包）；若设备是串口或厂商 SDK 本身阻塞式，NIO 根本套不上。设备数到几百、长连接高并发时再考虑 |
| **`ScheduledExecutorService` 调度重试** | ✅ **采用** | Java 5 就有，8/17 通吃；把"等 2 秒"交给调度器的延迟队列，任务只做一次交互就还线程 |

## 5. 目标方案

### 5.1 核心思想

- 一次任务 = 一次交互尝试（必须带超时），做完立刻结束、归还线程；
- "2 秒后再试"由 `ScheduledExecutorService` 的延迟队列承担，**等待零线程成本**；
- 任务内部必须捕获所有异常：交互失败 → 记日志 → 正常返回，等待调度器下次触发。

### 5.2 模式一：周期轮询（成功失败都持续交互）

适用于"一直定期和设备交互"的语义：

```java
ScheduledExecutorService scheduler = Executors.newScheduledThreadPool(10);
Map<String, ScheduledFuture<?>> tasks = new ConcurrentHashMap<>();

void start(Device device) {
    ScheduledFuture<?> f = scheduler.scheduleWithFixedDelay(
            () -> runOnce(device),
            0,              // 立即执行第一次
            2, TimeUnit.SECONDS);  // 上一次任务【结束后】再等 2 秒执行下一次
    tasks.put(device.getId(), f);
}

void runOnce(Device device) {
    try {
        interactOnce(device);      // 只做一次，内部必须有 connect/read 超时
    } catch (Exception e) {
        // 千万不能往外抛！抛出会导致该任务后续调度被静默终止
        log.warn("设备 {} 交互失败，2秒后自动重试", device.getId(), e);
    }
}

void stop(Device device) {
    ScheduledFuture<?> f = tasks.remove(device.getId());
    if (f != null) f.cancel(false);
}
```

要点：

- `scheduleWithFixedDelay`：同一设备的两次执行**天然串行、绝不并发**，无需加锁；间隔从上次任务结束算起（若交互耗时 1 秒，实际节奏约 3 秒一次。若业务严格要求"每 2 秒一次"的固定节奏，改用 `scheduleAtFixedRate`，同样不会同任务并发）。
- 池大小：交互变成短任务后，10 个线程带 20 个设备绰绰有余。

### 5.3 模式二：失败重试直到成功（成功即停）

适用于"重试只是为了成功一次"的语义（与口头描述"失败就重试，一直失败一直重试"更吻合）：

```java
void attempt(Device device) {
    scheduler.execute(() -> {
        try {
            interactOnce(device);
            // 成功，自然结束，不再调度
        } catch (Exception e) {
            log.warn("设备 {} 交互失败，2秒后重试", device.getId(), e);
            scheduler.schedule(() -> attempt(device), 2, TimeUnit.SECONDS); // 失败才续期
        }
    });
}
```

要点：

- 同一设备天然串行（下一次调度发生在上一次失败之后）；
- 重试次数无上限 = 无限重试，符合现有需求；若将来要加上限/退避，在 `attempt` 里加计数即可。

**两个模式选哪个，取决于「待确认清单」第 4 项的业务语义。**

### 5.4 `interactOnce` 的要求（无论哪个模式）

- 只做**一次**交互：连接（带 connect 超时）→ 读写（带 read/write 超时）→ 释放；
- 不允许内部有循环重试、不允许 `Thread.sleep`；
- 超时必不可少：没有超时，一个卡死的设备依然会永久占住一个线程，10 个卡死设备照样吃光线程池，调度器也救不了。

## 7. 验收标准

1. **故障隔离**：制造若干设备持续失败，其余正常设备的交互不受影响，线程池不会满（可用日志或 jstack 线程 dump 验证：故障期间无线程长期 BLOCKED/TIMED_WAITING 在 sleep 上堆积）；
2. **同一设备不并发交互**；
3. **任务抛异常不会终止后续重试**（故意让某次交互抛异常，观察 2 秒后仍会再次触发）；
4. 所有设备调用均有**显式超时**，逐一列出超时值；
5. 代码在 **JDK 8 语法/API 级别编译通过**（不得使用 Java 9+ API，例如 `CompletableFuture.delayedExecutor` 是 9+ 的，禁用）；
6. 应用关闭时任务可被优雅停止，无泄漏线程。

## 9. 已知坑位速查（实现时逐条自查）

- **调度任务往外抛异常 → 后续调度静默终止**。`scheduleWithFixedDelay/AtFixedRate` 的任务必须把所有异常吞在任务体内，这是最经典的坑。
- **老式阻塞 IO 不响应中断**：`cancel(true)` 的中断对阻塞中的 socket 读通常无效，不要依赖中断来打断交互；靠超时让任务自行结束。
- **不要在调度任务里做重度后处理**：如果"设备返回值的处理"很重，把处理扔到单独的 worker 线程池，别占用交互调度线程（这也是"交互"与"返回处理"分离的正确姿势——不需要为此上 NIO）。
- **fixedDelay 的间隔从上次任务结束起算**，不是严格每 2 秒；节奏敏感时用 `fixedRate`。
- **线程池大小**：交互均为短任务后 10 足够；若单次交互超时上限 > 2 秒，最坏情况下 20 个设备同时交互会短暂排队，属正常，可按需微调池大小或缩短超时。

## 10. 演进方向（本次不做，仅备忘）

- 统一到 JDK 21+ 后：可改用虚拟线程（`Executors.newVirtualThreadPerTaskExecutor()`），阻塞式重试写法即可直接使用，届时本方案的调度器可逐步替换；
- 设备规模增长到数百台、或改成长连接高并发模型时：再评估 Netty/NIO 多路复用（一组 eventLoop 线程各管一批连接 + 独立 worker 池做业务处理）。
