# Plan Review Skill

审查用户对 AI 提出的方案 / plan 的理解是否有偏差。通过结构化对比，让潜在的误解、遗漏、概念混淆在执行前暴露出来。

## 何时触发

用户在以下场景主动调用 `/plan-review`：

- 刚拿到 AI 给出的一份完整方案（实现路径、学习计划、业务流程、架构设计等），准备动手前
- 担心自己把方案里的概念、步骤、范围、风险理解错了
- 想要第二意见验证自己"读懂了"

不适用于：纯代码 review、纯 bug 调试、需要外部信息才能判断的研究类问题。

## 输入要求

用户必须提供 **两段文本**：

1. **AI 原始方案**：从 AI 那里完整复制过来的原文（不要先做总结，要原文）
2. **用户复述**：用户自己用 3–5 条 bullet 写出的理解版本（用自己的话，不是抄原文）

如果用户只给了其中一段，先礼貌要求补齐，不要凭一半信息硬做判断。

## 工作流

严格按以下 4 步执行，**不要跳步**：

### Step 1 — 拆解原方案
把 AI 原始方案拆成「关键点清单」，每条一个独立的事实/动作/概念，编号列出。这是后面比对的基准。

格式：
```
[原方案关键点]
1. <关键事实/动作/概念>
2. <关键事实/动作/概念>
...
```

### Step 2 — 解析用户复述
把用户的复述拆成「用户理解清单」，同样编号列出。注意：**保留用户原话中的用词**，不要替换成"标准术语"，因为用词偏差本身就是信号。

格式：
```
[用户理解清单]
1. <用户原话或最小改写>
2. <用户原话或最小改写>
...
```

### Step 3 — 逐条对照
对每个用户理解项，找它在原方案中的对应关键点，给出判断：

- ✅ **一致**：意思和原方案相符，无歧义
- ⚠️ **偏差**：意思有偏差，**必须明确指出正确版本是什么**
- ❓ **需澄清**：用户理解有歧义 / 原方案本身就模糊 → 反问澄清
- ➕ **盲点**：用户遗漏了原方案里的关键点 → 单列在「盲点清单」

格式见 `references/review-format.md`。

### Step 4 — 总结评分
给出：

1. **理解准确度评分**：0–100 分（基于偏差项数量和严重程度）
2. **关键盲点 Top 3**：从「盲点清单」里挑最可能影响执行的前 3 项
3. **建议下一步**：要么"理解到位，可以执行" / 要么"先和 AI 再确认 X / Y / Z"

## 输出格式

完整示例见 `references/review-format.md`。核心结构：

```
## Plan Review 结果

### 1. 原方案关键点
...

### 2. 你的理解清单
...

### 3. 逐条对照
| # | 你的理解 | 对应原方案 | 判定 | 说明 |
|---|---------|-----------|------|------|

### 4. 盲点清单（你遗漏的）
...

### 5. 总结
- 准确度评分：XX / 100
- 关键盲点 Top 3：...
- 建议下一步：...
```

## 行为准则

- **不要替用户做决策**：review 的目的是暴露偏差，不是给出"应该怎么改"的方案
- **不要美化偏差**：发现误解就直说，不要用"你的理解也很有道理"这种话糊弄
- **不要过度发散**：只对比用户提供的两段文本，不要引入用户没问到的新方案维度
- **不确定就标 ❓**：宁可反问也不要硬判，特别是原方案本身就含糊的地方
- **保留用户原话用词**：用户写"那个 token 缓存的东西"就照搬，不要改成"Token Cache"，用词偏差本身就是信号

## 反例

- ❌ 只贴用户的复述就开始 review → 必须要求补原方案
- � 把用户的复述和原方案混在一起读 → 必须先拆成两份清单再对照
- ❌ 给出"建议你这样做"的实施建议 → 这是越界，告诉用户偏差就够了
- ❌ 跳过总结评分直接结束 → 必须给出评分和下一步建议
