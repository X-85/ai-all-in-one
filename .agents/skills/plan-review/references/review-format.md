# Review 输出格式参考

完整输出模板，模型应该严格按此结构生成 review 结果。

---

## 完整模板

```markdown
## Plan Review 结果

### 1. 原方案关键点
把 AI 原始方案拆成 5–10 条独立的关键事实/动作/概念。优先拆解：
- 核心动作（要做什么）
- 关键约束（必须在什么条件下做）
- 隐含假设（默认成立的前提）
- 风险/副作用（需要规避的点）

示例：
1. 用 Redis 做缓存层
2. 缓存 key 用 user_id + resource_id 拼接
3. TTL 设为 5 分钟
4. 缓存更新采用「先写库，再删缓存」策略
5. 假设 QPS < 1000，单实例 Redis 足够

### 2. 你的理解清单
把用户复述拆成编号 bullet，**保留用户原话用词**。

示例：
1. 用 Redis 缓存用户数据
2. key 直接拼 user_id
3. 5 分钟过期
4. 写完数据库再清理缓存

### 3. 逐条对照
用表格逐条对比，⚠️ 项必须给出正确版本：

| # | 你的理解 | 对应原方案 | 判定 | 说明 |
|---|---------|-----------|------|------|
| 1 | 用 Redis 缓存用户数据 | 用 Redis 做缓存层 | ✅ 一致 | 表述等价 |
| 2 | key 直接拼 user_id | key 用 user_id + resource_id 拼接 | ⚠️ 偏差 | 你遗漏了 resource_id，实际是 user_id:resource_id 双段拼接。单拼 user_id 会导致不同资源类型互相覆盖缓存 |
| 3 | 5 分钟过期 | TTL 设为 5 分钟 | ✅ 一致 | — |
| 4 | 写完数据库再清理缓存 | 「先写库，再删缓存」策略 | ✅ 一致 | — |

### 4. 盲点清单（你遗漏的）
用户复述里完全没有提到的关键点。单列出来：

- **原方案 #5**：假设 QPS < 1000 — 你没提这个前提，如果实际 QPS 超过这个值，单实例 Redis 会成为瓶颈
- **原方案 #4 中的策略含义**：原方案的「先写库，再删缓存」是为了避免「先删缓存再写库」期间的脏读，你理解里没体现这个动机，可能执行时改错顺序

### 5. 总结
- **理解准确度评分**：82 / 100
- **关键盲点 Top 3**：
  1. 遗漏 resource_id，导致缓存 key 设计有误（严重）
  2. 不知道 QPS < 1000 这个前置假设（中等）
  3. 没理解「先写库再删缓存」的动机（轻微）
- **建议下一步**：先和 AI 确认 (a) cache key 拼接规则 (b) 当前业务 QPS 是否在 1000 以内，再动手写代码。
```

## 评分参考

| 评分 | 含义 |
|------|------|
| 90–100 | 理解到位，可执行 |
| 75–89 | 基本到位，有 1–2 个非关键偏差，建议补确认 |
| 60–74 | 有明显偏差，必须补确认才能执行 |
| < 60 | 偏差较多或关键概念混淆，建议重新读原方案 |

不要给 100 分除非逐条对照全部 ✅ 且无盲点。

## 常见偏差类型速查

模型在 review 时重点关注以下偏差：

- **概念混淆**：OAuth ≠ SSO ≠ JWT；进程 ≠ 线程 ≠ 协程
- **顺序颠倒**：执行步骤搞反（如「先删缓存后写库」 vs 「先写库后删缓存」）
- **范围溢出**：把 A 模块的方案套到 B 模块上
- **条件遗漏**：原方案说「在 X 情况下用 Y」，用户理解成「无脑用 Y」
- **副作用盲区**：方案里有「注意 Z 风险」，用户完全没提
- **术语歧义**：用户用错词（如把"幂等"理解成"线程安全"）
