# LLM 基础认知 · 上下文工程(延伸篇)

> 层:原理层(延伸篇)| 主题:上下文工程解决什么问题 / 它从哪来 / 六族通用方案 / 本人实践对照
> 版本:学习版——问题→背景→方案三段主线,每节落到工程取舍;原理依据见 [生成机制(上)](LLM基础认知-生成机制(上).md) [生成机制(下)](LLM基础认知-生成机制(下).md)

一句话版:**上下文是模型推理时唯一的工作台,而容量、注意力、成本三样都有限——上下文工程就是设计"什么信息、以什么形式、在什么时机进入这个工作台"的系统方法;提示词工程是它的子集,RAG、记忆、压缩、隔离都是它的分支。**

使用说明:本文是原理层延伸篇首篇(用户点题展开,见补充资料登记机制),定位是"原理层→工程层的桥"——前两节讲为什么,第三节讲怎么办,第四节把本人一年实战翻译成这个框架的语言。面试自检标准:六族方案每族能说出一个自己的实例或失效场景。

## 一、它解决什么问题

**是什么**:上下文(context)= 推理那一刻模型能看到的全部信息——system prompt、对话历史、工具定义、工具返回、检索片段、注入的记忆。模型没有"上下文之外的世界":参数里没有、上下文里也没有的,它就不知道(表现为瞎编或该拒答不拒答)。上下文工程(context engineering)就是对这条信息流的系统设计。

**三个硬约束**(原理层分别讲过,这里汇总成一张账):

| 约束 | 原理依据 | 工程含义 |
|------|---------|---------|
| 容量有限 | 窗口是常数(几千~百万 token) | 任务所需信息可以无限增长,装不下就是装不下 |
| 注意力有限 | lost in the middle:塞进去 ≠ 用上 | 信息越多,单位信息分到的注意力越稀 |
| token 有价 | 注意力计算量随长度平方级增长 | 长上下文同时伤质量、延迟、账单 |

**agent 时代把矛盾放大了四倍**:

1. **多轮堆积**:agent 一个任务几十轮,每轮的思考、工具调用、工具返回全留在上下文里滚动前进
2. **工具输出又长又脏**:一次搜索、一个 API 响应动辄几千 token,信号密度远低于人写的指令
3. **错误滚雪球**:早期的误解留在上下文里,后续生成会把它当事实继续引用——上下文被自己污染(社区称为 context rot)
4. **任务本身在长**:从"问一句答一句"到"读一个仓库改一处代码",所需状态远超任何窗口

**核心命题**:不是"塞得更多",而是"喂得更准"——在有限预算内,让对下一个生成步骤最有用的信息以最高信号密度出现在窗口里。衡量指标是**信号密度:同样 token 预算下,窗口里有效信息的占比**。

**例子(可直接讲,约 1 分钟)**
编码 agent 干活干到一半,开始重复读同一个文件、忘掉一小时前的约定——不是模型"变笨了",是上下文里堆了几十万 token 的工具输出,早期指令分到的注意力被稀释光了。所以 Claude Code 有 /compact(把长会话压缩成任务简报重开),有 sub-agent(派子任务去独立窗口里干,只把结论带回来)。这些产品功能的存在本身,就是这个问题真实存在的最好证据。

## 二、背景:从提示词工程到上下文工程

**演化动因:优化对象变了。**

- **2023 前后·提示词工程(prompt engineering)**:主流形态是单轮调用。优化对象是一段静态指令的措辞——角色设定、few-shot 示例、格式要求、思维链触发词。指令约等于上下文的全部,所以"写好一段话"就够用
- **agent 时代**:指令只占上下文的一小块,大头是动态流进来的一切——检索命中了什么、历史留了什么、工具返回了什么、记忆读回了什么。写好一段话不再够用,要设计的是一条**信息流水线**
- **2025 年术语出圈**(概念级):Karpathy 公开表达过大意"别过度强调提示词工程,它只是上下文工程的一个子集";Anthropic 的 agent 博文给的定义大意是**构建动态系统,在正确的时机、以正确的格式,把正确的信息和工具交给模型**。此后"上下文工程是新的提示词工程"成为行业共识口径

**为什么值得单独命名**(面试的讲点):它把一堆看似无关的技术收拢到同一个问题下——RAG、记忆系统、会话压缩、子 agent 隔离、prompt 缓存,全是"管理进入窗口的信息流"的不同侧面。能讲出这句收拢的话,和只会背 RAG 定义,是两个段位。

**常见误区**

- "上下文工程 = 高级提示词工程"——提示词只管窗口里那段静态指令;上下文工程管整条动态信息流,包括丢什么、隔离什么
- "信息越全越好"——无关信息是负资产:稀释注意力、花真金白银、还可能误导生成

## 三、通用解决方案:六族

按"信息怎么进出窗口"整理。每族记三样:思路、代表技术、失效与代价。

### 1. 按需加载(just-in-time):用到才取

- **思路**:不预塞,用时取——用"选择性"换预算
- **代表**:RAG 管线(检索→rerank→组装);agent 主动检索(grep 查目录,而不是整库读入);渐进式披露(先给目录/摘要,要细节再读全文)
- **失效与代价**:检索错 = 上下文错,上游失效直接传导下游;多一跳延迟。**RAG 的质量问题就是这一族的固有风险**
- **位置策略同族**:lost in the middle 的直接应用——rerank 完最相关片段放前面,关键约束头尾各放一次

### 2. 压缩(compaction):摘要换空间

- **思路**:旧信息不舍得丢又占地方 → 压成高密度版本
- **代表**:长对话滚动摘要;工具原始输出截断/结构化(只留字段不留全文);Claude Code 的 /compact
- **失效与代价**:压缩必有损——丢掉的信息恰是后面要用的,就得回读(缺页代价);摘要质量本身依赖模型,可能摘错重点
- **变体**:结构化输出算"预压缩"——让工具直接返回结构化字段,而不是给人读的自然语言长文

### 3. 隔离(isolation):脏活不进主窗口

- **思路**:大量低信号操作(全库搜索、长文档抽取)放到独立上下文里干,主上下文只收回结论——污染不扩散
- **代表**:sub-agent 模式(主 agent 派活,子 agent 带自己的干净窗口去干,只返回结果);并行任务的上下文分叉
- **失效与代价**:子 agent 看不到主上下文的隐性信息,派活时任务描述必须自包含;多一层调度开销;**隔离不彻底会互相踩**(本人实例:两个并行会话共用同一工作区改同一文件,互相覆盖——见 [工作流agent实践](工作流agent实践.md) 第四节)

### 4. 记忆外置(externalized memory):窗口是内存,文件是磁盘

- **思路**:会话结束窗口就清零;跨会话、跨任务的状态放外部,按需读回
- **代表**:短时记忆(会话内状态摘要、检查点);长时记忆(记忆文件、数据库、知识库)。本仓库的台账模式就是长时记忆:问题/事件/决策三件套落盘,新会话先读台账,零口令接续
- **失效与代价**:读什么、何时读要设计(引导索引 = 仓库地图 AGENTS.md);记忆会过期,要有更新与淘汰机制;读回也占预算——本质是把"记住一切"换成"知道去哪查"

### 5. 结构化与位置(写入侧基本功)

- **思路**:同样进窗口的信息,形式和位置决定利用率
- **代表**:system prompt 放开头(位置先验);指令与示例精简;输出格式约束(结构化输出);工具定义瘦身
- **定位**:这是最接近提示词工程的部分——**提示词工程是上下文工程的子集**,对应六族中这一族

### 6. 缓存(prompt caching):成本侧的上下文工程

- **思路**:前缀相同的部分复用 KV 计算——稳定内容(system prompt、工具定义)放前面不动,动态内容放后面追加
- **意义**:成本与延迟的大杠杆;也是"system prompt 放前面"的第二个理由(第一个是注意力先验)
- **归属**:不改变窗口内容,改变的是同样内容的价格——接质量层的成本与延迟话题

```text
方案地图(按信息流向)
  进什么   → ①按需加载(RAG/主动检索/渐进披露)+ ④记忆外置的读取
  留多少   → ②压缩(滚动摘要/工具输出瘦身)+ ③隔离(子 agent 只收回结论)
  什么形式 → ⑤结构化与位置(头尾先验/字段化/指令精简)
  什么价位 → ⑥缓存(前缀稳定,复用计算)
```

## 四、实践对照:一年实战翻译成上下文工程的语言

本人实践里六族全部有真实实例(这也是"用过六个 agent"的正确打开方式——用框架讲,不罗列工具名):

| 本人实践 | 对应族 | 一句话 |
|---------|-------|--------|
| session 台账(问题/事件/决策三件套,跨会话接续) | ④记忆外置 | 窗口是易失内存,台账是磁盘 |
| AGENTS.md 仓库地图(必读文件+流程+坑) | ④记忆外置+⑤结构化 | 新会话冷启动的引导索引 |
| AstrBot 方案的渐进式加载(先给 Skill 目录,要用再读全文) | ①按需加载 | 索引先行,正文按需 |
| FAQ 系统 rerank 后最相关片段放 prompt 最前 | ⑤位置策略 | lost in the middle 的直接应用 |
| 澄清追问一轮封顶 | ②压缩(预算控制) | 不让低效轮次无限膨胀 |
| 并行会话撞文件(互相覆盖 chapters.ts) | ③隔离失败 | 隔离不彻底的反面教材 |
| Claude Code 的 /compact 与 sub-agent 使用体感 | ②③ | 产品级实现的使用者视角 |
| 六工具横评的"上下文管理"维度 | 全景 | 各家做六族的差异化对比 |

**面试话术(1 分钟,可直接讲)**
上下文工程我的理解是:模型的全部工作状态就是当前上下文,但容量、注意力、成本三样都有限,所以问题从"把指令写好"变成"设计一条信息流水线"——什么信息、什么形式、什么时机进窗口。我在自己的工作流里全套实践过:session 台账是记忆外置,AGENTS.md 仓库地图是冷启动引导,渐进式加载是按需取用;公司 RAG 系统里 rerank 后的片段排序是位置策略。判断一个方案好不好,我看信号密度——同样 token 预算下,窗口里有效信息的占比是升了还是降了。

## 五、常见误区与面试自检

**误区**

- "窗口都百万 token 了,上下文工程会过时"——容量涨,任务复杂度涨得更快;注意力稀释与成本问题不随容量消失(lost in the middle 在长窗口下依然成立)
- "上下文工程是提示词工程的换皮"——前者管动态信息流(含丢什么、隔离什么),后者只管静态指令这一族
- "多塞点总没错"——无关信息稀释注意力还要付费,三个约束一个都没绕过

**自检三问**(答不顺的就是没消化)

1. 什么是上下文工程?和提示词工程、RAG 各是什么关系?(前者管流水线,后者管静态指令;RAG 是知识注入分支)
2. 你的 agent 长任务怎么不失忆不跑偏?(记忆外置+压缩+按需加载,各带一个自己的实例)
3. 窗口越来越大,为什么还要 RAG?(注意力质量、平方级成本、知识常变要溯源——容量只是三约束之一)

## 小结

```text
上下文 = 模型推理时唯一的工作台(参数外的一切都要从这里进)
三约束:容量有限 + 注意力有限(lost in the middle)+ token 有价
agent 时代四放大:多轮堆积 / 工具输出脏长 / 错误滚雪球(context rot)/ 任务变长
        ↓
上下文工程 = 设计信息流水线:进什么 / 留多少 / 什么形式 / 什么价位
六族:①按需加载 ②压缩 ③隔离 ④记忆外置 ⑤结构化位置 ⑥缓存
判据:信号密度——同预算下窗口内有效信息占比(↑好)
```

## FAQ

**Q:上下文工程和 RAG 到底什么关系,面试怎么说?**
RAG 是上下文工程在"外部知识注入"分支上的具体实现。上下文工程是更大的框架:除了取什么(RAG),还管留多少(压缩)、在哪干(隔离)、存哪里(记忆)、什么形式(结构化)、多少钱(缓存)。面试讲清关系比背定义加分。

**Q:长上下文模型(整库塞入)会淘汰 RAG 和上下文工程吗?**
容量只是三约束之一。注意力稀释(塞进去 ≠ 用上)、平方级成本、知识更新与溯源需求,都不随窗口变大消失。小库静态场景可以试长上下文;库大、常更新、要溯源的生产系统仍是 RAG 主场(同 [生成机制(下)](LLM基础认知-生成机制(下).md) FAQ 第一问)。

**Q:面试官问"你做过上下文工程吗",没做过专职岗位怎么答?**
不背定义,直接摆实例:台账=记忆外置、仓库地图=冷启动引导、渐进式加载=按需取用、rerank 排序=位置策略、并行撞文件=隔离失败教训。上下文工程本是实践先于术语的领域,自己的工作流就是案例。
