# LLM 基础认知 · 生成机制(上)

> 层:原理层 | 系列位置:生成机制上篇 | 主题:token 化 / 下一 token 预测与幻觉 / 采样参数
> 版本:学习版——机制段展开 + 每主题一个可讲 1 分钟的例子;延伸深挖点见 [LLM基础认知-补充资料](LLM基础认知-补充资料.md)

一句话版:**LLM 不是在"回答问题",而是在"续写文本"——它把世界切成 token,用概率猜下一个 token,采样参数决定猜得多稳。这三件事解释了大半 LLM 工程现象。**

使用说明:每主题四段(是什么 → 机制 → 工程推论 → 常见误区)是速览层,面试前 5 分钟过一遍;"例子"块是讲稿素材,练到能脱稿讲。面试自检标准:每段工程推论能讲出至少两条。

## 一、token 化与上下文窗口

**是什么**:模型看不到字,只看 token。token 是文本的碎片(子词单元),上下文窗口是模型一次能处理的 token 总预算。

**机制**

- 分词器是**统计学出来的**:拿海量语料从字符开始,把最常见的相邻组合反复合并进词表。结果是高频词一个 token 装下,生僻组合拆成多块。示意(精确切分以具体模型的官方 tokenizer 为准):
    - 英文 `internationalization`(20 个字母)≈ `inter` + `national` + `ization` 三块
    - 中文"知识库"常见 1~2 个 token;生僻字如"饕餮"多半落到字节级,一个字节一块
    - 数字也是坑:`1234567` 怎么切因模型而异——这是模型算术不稳的一环
- 上下文窗口是**输入与输出共享**的预算。以一次 RAG 问答记账:

| 组成 | 量级(token) |
|---|---|
| system prompt(角色+规则) | ~500 |
| 检索回来的资料 | ~3000 |
| 对话历史 | ~2000 |
| 本轮问题 | ~100 |
| 输出预留(生成也扣预算) | ~1000 |

    合计约 6600。看似远小于 128k,但**成本、延迟、限制全按这笔账算**——上下文管理的本质就是管这笔账。

- 模型处理的是 token 序列,不是字符序列——"strawberry 里有几个 r"翻车的根源:它没看到一个个字母,看到的是几个碎片编号。

**例子(可直接讲,约 1 分钟)**
面试官问"为什么模型数不清字母",我这样答:模型看到的世界和人不一样。人看 `strawberry` 是 10 个字母,模型看到的是 3 个左右的 token 编号——像透过毛玻璃看字,它能认出这是"草莓",但要数字母,得先把毛玻璃里的碎片还原成字母,这不是它的原生操作。所以字符级精确任务(计数、精确匹配、字符操作)我的做法是外挂代码,一行 `len()` 比任何提示词技巧都稳。

**工程推论**

1. **计费、延迟、长度限制全部按 token 算**。做成本估算的第一步就是估 token 量;给业务方报价前先算清一次问答大概烧多少
2. **长文档必须切片**——不只是塞不下,塞下了效果也会劣化(lost in the middle,下篇展开)。RAG 的存在一半就是上下文预算逼出来的
3. **上下文要当内存管理**:上面那张记账表就是管理对象——system prompt 是固定开销,对话历史越滚越大,检索结果波动最大,输出别忘预留
4. **精确计数、字符级操作不要指望模型**,外挂代码执行

**常见误区**

- "上下文窗口 128k,塞 100k 没问题"——能塞 ≠ 好用,长上下文的中段遗忘是常态
- 拿字数估 token(中文尤其失真,可能差一倍)

## 二、下一 token 预测与幻觉

**是什么**:LLM 的全部工作 = 给定前文,算出下一个 token 的概率分布,挑一个接上,循环往复,直到挑出停止符。

**机制**

- **知识是"压缩"进参数的,不是"存表"里的**。训练把海量语料的统计规律压进千亿参数;生成时没有任何"查数据库"动作,每一步都在算"这样的前文后面,语料里最常接什么"
- **为什么不知道还答得理直气壮**:训练目标只奖励"像好答案的文本"——结构工整、术语正确、语气自信,从不惩罚"编造但流畅"。对模型来说,"根据财报,营收为 1.2 亿元"和"我不知道"都是合法续写,选哪个取决于哪种模式在分布里更强;而语料里自信的陈述远多于坦白的说"不知道",所以缺知识时它天然滑向"编得像"
- **生成即上下文(滚雪球)**:第 100 个 token 生成时,前 99 个已成为它的条件。一旦开头编了个数字,后文会围绕它自洽展开,极少自我推翻——"推翻前文"意味着承认前面写得像坏答案,与训练方向相抵。用户若基于那个数字追问,它会顺着继续编,一条道走到黑
- 同样的输入可以有不同输出,因为"挑"这一步有随机性——引出主题三

**例子(可直接讲,约 1 分钟)**
问模型"介绍一下林语堂的弟弟林语森"(我虚构的人物),它多半会给出像模像样的生平:生卒年、著作、文风。落点:这不是模型"撒谎",是它在执行本职——续写最像传记的文本;在语料分布里,"介绍一个人"后面跟生平远比跟"查无此人"常见。所以我的 RAG 系统里,库外问题走超纲拒答路由,不给它"自信续写"的机会;要事实,就把事实放进上下文(RAG),让续写有据可依。

**工程推论**

1. **对抗幻觉靠系统设计,不靠祈祷**:RAG 把事实放进上下文;要求引用来源;超纲问题拒答而不是硬答(四路由里的超纲拒答,本质就是承认这条机制)
2. **温度调到 0 也消灭不了幻觉**——随机性只是放大器,根子在生成机制
3. **模型嘴上的"我不确定"不可信**(道歉文本同样是续写产物);工程上要的置信度得靠外部手段:多次采样看一致性、看检索命中质量
4. **长任务里早期错误会滚雪球**——所以 agent 工作流要在关键节点设置验收确认,别让它带着错往前跑

**常见误区**

- "升级更大的模型就没幻觉了"——更大模型幻觉率更低,但机制不变,场景越专业越不能裸奔
- "它能道歉/能说不知道,说明有自知之明"——那是两种都被训练鼓励过的续写方向,不代表真实的内部置信度

## 三、采样参数

**是什么**:每步生成都有一个概率分布,采样参数决定"从分布里怎么挑"。

**机制**

- **分布长什么样**:以"今天天气真"为例,下一步候选可能是——好(40%)、不错(20%)、糟(10%)、冷(5%)……后面几百个候选各占不到 1%。所有候选概率加起来等于 1
- **temperature 是给分布重新分配权重**:T<1 把高概率的推得更高(削峰),T→0 逼近"只选第一名";T>1 把分布摊平,冷门候选机会变大。注意:它**不改变候选集合,只改变挑法**
- **top-p(核采样)是直接改候选集合**:按概率从高到低累加,只保留累计到 p(如 0.9)的候选,其余踢出牌桌——那几百个不到 1% 的"今天天气真离谱"就永远选不到,无论温度多高。top-k 同理,固定取前 k 个
- 为什么默认参数够用:现代 API 的默认值是厂商调过的;采样参数是**稳定性旋钮,不是能力旋钮**

**例子(可直接讲,约 1 分钟)**
温度像点菜时的冒险程度:不改变菜单,只改变你敢不敢点冷门菜。T=0.2 是"就点招牌菜",每次几乎一样;T=1.2 是"来点惊喜",冷门菜也敢上。所以"调高温度让它更聪明"是错觉——菜单(模型能力)没变,只是敢点了。真正想要新菜,要么改菜单(把知识放进上下文,即 RAG),要么换厨师(换模型)。

**工程推论**

1. **默认参数覆盖多数场景**。要动的典型场合:结构化输出、代码、事实问答 → 调低;文案创意、头脑风暴 → 调高
2. **"完全一致的输出"不要写进验收标准**:温度 0 也只是接近确定,浮点并行等工程因素仍可能带来差异
3. **调参顺序:先 prompt 后参数**。输出不稳定时,先检查 prompt 是不是本身允许多种合理解读(问题模糊、缺少格式约束),再动温度
4. 做 RAG 时把参数记录进评测配置——换参数前后的结果不可直接比较,这是评测报告的一个必填项

**常见误区**

- "调高温度让它更聪明"——不会,只会更随机;创造力来自模型能力 + 好的引导,不是来自随机性
- "温度 0 = 确定性"——接近,但不保证

## 小结

```text
文本 → [token 化] → token 序列(模型眼中的世界,一切计费/限制的计量单位)
     → [下一 token 预测] → 概率分布(没有查证动作 → 幻觉是固有的;
                            生成即上下文 → 错误会滚雪球)
     → [采样] → 挑一个接上(温度/top-p 控制稳不稳,不控制会不会;
                            输出天然带随机性)
```

三件事合起来,就解释了大半日常工程现象:为什么按 token 计费、为什么要切片、为什么会一本正经胡说、为什么同样的问题两次回答不一样、为什么温度调 0 还是偶尔翻车。

## FAQ

**Q:温度设 0,为什么每次输出还是可能不一样?**
温度 0 只是"几乎总挑最高概率",但浮点运算的并行顺序、批处理布局等工程因素会引入微小差异;个别概率接近的 token 上,这点差异就够翻盘。所以工程上写"近似确定",别承诺逐字一致。

**Q:"strawberry 里有几个 r"这个梗说明了什么?**
它说明模型看世界的方式和人不一样:人看到字母序列,模型看到 token 序列。字符级精确任务(计数、精确匹配、字符操作)要用代码工具兜底,这不是模型笨,是"视网膜"不同。面试讲这个例子时,落点放在"所以我会在工作流里把这类任务外挂"——从原理落到工程,才是加分答案。
