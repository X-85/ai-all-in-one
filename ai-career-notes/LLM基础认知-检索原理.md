# LLM 基础认知 · 检索原理

> 层:原理层 | 系列位置:检索原理篇(原理层收尾) | 主题:embedding / 向量检索与失效模式 / rerank 与两段式 / chunking
> 版本:学习版——机制段展开 + 每主题一个可讲 1 分钟的例子;延伸深挖点见 [LLM基础认知-补充资料](LLM基础认知-补充资料.md)

一句话版:**RAG 管线的每个设计都是被检索的物理规律逼出来的——语义能被算(embedding),但算得快就糙(ANN/top-k),所以先召回再精排(rerank);而入口质量的一半在切法(chunking)。**

使用说明:每主题四段(是什么 → 机制 → 工程推论 → 常见误区)是速览层;"例子"块是讲稿素材。面试自检标准:每段工程推论能讲出至少两条。入门视角与学习路线见仓库既有文档 [RAG是什么](../knowledge/doc/RAG是什么.md)、[RAG学习路线图与实战指南](../knowledge/doc/RAG学习路线图与实战指南.md),本篇讲"为什么"。

## 一、embedding:语义变几何

**是什么**:embedding 模型把一段文字变成一个高维向量(几百到几千维的数字列表),语义相近的文字,向量距离也近。"相似度 = 距离"是整个向量检索的地基。

**机制**

- **怎么训出来的**:对比学习——同一语义的不同表述(问题与答案、同义改写)被拉近,无关内容被推远。训练语料决定它"懂哪类语义",所以通用 embedding 换到黑话/术语密集的场景可能拉胯(概念级,细节在补充资料)
- **相似度怎么算**:常用余弦相似度(向量夹角),取值约 [-1, 1],越接近 1 越相关。**0.7 之类的阈值不是普适常数**——分数量纲依模型而定,必须用自己的数据校准
- **维度的直觉**:模型把语义摊到几百个维度上,单个维度没有人类可读的含义,但整体几何结构承载了"意思有多近"
- **关键的不对称**:向量距离近保证"语义近",**不保证"答案对"**——两个几乎一样的问题可以有完全不同的答案("如何重置 A 系统密码"和"如何重置 B 系统密码"),几何上挨着,内容上无关。这是后面失效模式的总根源

**例子(可直接讲,约 1 分钟)**
"登录不上去了"和"无法访问账户"——字面零重叠(没有共同关键词),关键词检索基本失联;但 embedding 距离很近,一查就中。落点:这就是 FAQ 问答选向量检索而非关键词检索的根本原因——**用户永远不用文档里的词提问**。反过来,字面像而语义异的 case 是它的失效区,这就是下一节的主角。

**工程推论**

1. embedding 选型是独立决策(与生成模型分开选),看它在**自己语料**上的召回表现,不看通用榜单
2. 相似度阈值必须用自己的数据校准;不同模型之间分数不直接可比
3. embedding 也有知识截止——新术语、新产品名可能落不进正确语义区,库要能增量补
4. 语料特殊(黑话/中英混杂)时评测先行,别默认通用模型够用

**常见误区**

- "相似度高 = 答案对"——embedding 只保证语义近;检索类 bad case 一半是"语义近但不对"
- 拿 A 模型调好的阈值直接用在 B 模型上

## 二、向量检索与失效模式

**是什么**:库大了不可能每问都与全库逐条比相似度,所以用 ANN(近似最近邻)索引——用"几乎找到最近邻"换"快几个数量级"。top-k = 每次取最相似的前 k 条。

**机制**

- **ANN 的取舍**:HNSW/IVF 这类索引把向量空间建图分簇,查询只探一部分空间——快,但可能漏掉真正的最近邻(召回率 < 100%,可调;细节在补充资料)
- **top-k 的结构性两难**:k 调大,金块更可能在内,但噪声同涨(挤占上下文预算、干扰生成);k 调小,干净但漏检。**这不是能调没的参数矛盾,是结构矛盾**——所以才需要下一节的 rerank 分层化解
- **失效模式清单**(原理层的重点,bad case 排查地图):
    1. **专有名词/精确串**:向量擅长"意思",弱在"精确"。错误码 `ERR-1001` 和 `ERR-1002` 向量几乎重合,答案完全不同
    2. **否定语义**:"如何关闭 X"和"如何开启 X"只差一个动词,几何位置几乎重叠——embedding 对否定不敏感是老毛病
    3. **多跳问题**:答案要组合两条知识("用 A 的角色能否访问 B"),库里没有直接答案,单次 top-k 最多中一半
    4. **问题-答案形态差**:用户问句 vs 文档陈述句,若 embedding 对齐弱,距离被拉远
    5. **粒度不匹配**:问细节,库里只有概述(或反之)——命中了"主题对但粒度错"的块

**例子(可直接讲,约 1 分钟)**
用户问"怎么开通权限 X",系统检索回来"怎么关闭权限 X"的文档——两句 95% 的词相同,只差一个动词,向量距离近得很自然。落点:所以我的管线里,带精确标识(错误码、功能名)的查询走关键词命中那条路,向量检索只兜"模糊表达"——**单一向量检索不是完备方案,混合检索才是**。这一条踩过的人才懂,面试里讲出来就是实战味。

**工程推论**

1. **bad case 排查第一动作**:翻 top-k 原文,先判"检索命中没有",再看生成——一半以上的"答错"其实是"没检对"
2. 失效模式反推方案:专名 → 混合检索(BM25);否定类 → 查询改写/意图路由;多跳 → 拆问题或多轮检索
3. top-k 与相似度阈值是"漏检 vs 噪声"的配比旋钮,用评测数据说话,不拍脑袋
4. ANN 召回率是隐藏参数,库小先别焦虑,几十万块以上再关心

**常见误区**

- "向量检索更高级,全面替代关键词"——互补,不是替代
- "top-5 没检到就加大到 top-50"——噪声同涨;先判断失效模式属于哪类再动手

## 三、rerank 与两段式管线

**是什么**:生产级检索管线标准形态是两段——**召回**(embedding 从全库粗筛出 top 几十)+ **精排**(rerank 模型对候选逐条细算,重排后取前几)。

**机制**

- **召回为什么糙**:embedding 是"双塔"结构——问题和文档**分别**编码成向量再比距离。文档可以离线预编码(所以快,查询时只算一次),但各自压缩成一个点,**细节在压缩里丢了**
- **精排为什么准**:rerank 是"交叉编码"——问题与文档**拼在一起**过模型,逐 token 交互,直接输出相关分。细节全在,但每对都要现场算(无法预编码),慢且贵
- **两段式是算力的必然分工**:用便宜的召回从十万条捞出 50 条,再用贵的精排从 50 条选 5 条——"海选 + 复试"
- rerank 与 embedding、生成模型是**三种不同的模型**,各选各的,不存在谁附赠谁

**例子(可直接讲,约 1 分钟)**
招聘类比:HR 按简历关键词一秒筛一千份(召回,快而糙),筛出 50 份交给面试官逐一面谈(精排,慢而准),最后发 5 个 offer。没有人让面试官直接面一千个人——时间和钱都不允许。RAG 管线完全同构:embedding 当 HR,reranker 当面试官。落点:我的 FAQ 系统就是召回 top-30、精排取 top-5,而且精排完按分数把最相关的放 prompt 最前——这一步接的是生成机制(下)的 lost in the middle。

**工程推论**

1. 两段各自的 K 独立调:召回段 k 放宽(给精排足够候选),精排段收紧(只留精华)
2. "检索不准"的第一处方通常是加 rerank——成本可控、不动存量库,先试它再谈换 embedding
3. 别跳过 rerank 直接换更大 embedding——双塔的糙是结构性的,换大模型只是缓解,补不了"压缩丢细节"
4. 精排后的组装顺序接上篇:分数最高的块放上下文最前面

**常见误区**

- "一个 embedding 包打天下"——结构决定它只能干粗活
- "embedding、rerank、生成选一家全家桶"——三种模型三个选型,各自评测

## 四、chunking:入口决定一半

**是什么**:文档入库前要切块,块是检索的最小单元。**切法直接决定检索的粒度和上下文的完整性**——很多"检索不准"的病根不在检索器,在切法。

**机制**

- **矛盾的本体**:块大 → 语义完整(答案自带语境)但向量被稀释(一块讲五件事,向量哪件都不像,还费预算);块小 → 向量聚焦但语义残缺("参见上表"没了表)。**这是取舍,不是待调优的参数**
- **切法光谱**:固定长度(简单,易切断语义)→ 按结构切(标题/段落,Markdown 天然有结构)→ 语义切(模型找边界,贵)。FAQ 场景有特解:**一问一答天然一块**——FAQ 库的 chunking 退化成了"整理问答对",这是 FAQ 形态对 RAG 的先天优势
- **元数据是块的另一半**:来源、标题路径、更新时间、verified 标记——检索过滤、答案溯源、新旧淘汰都靠它
- **重叠切法(overlap)**:相邻块重叠一段,缓解"切断",代价是存储与检索冗余——折中手段,不是免死金牌

**例子(可直接讲,约 1 分钟)**
同一个退货政策文档两种切法:按 500 字盲切,"7 天可退"和"食品类除外"被切进两个块——用户问"零食能退吗",检索命中前者,答案漏了"除外",一本正经地答错。按标题和 QA 对切,一条政策自带完整语境,问题消失。落点:我的库里 FAQ 一问一答一块、挂元数据(类别/来源/verified),文档按标题层级切——**切法跟着内容形态走,没有万能参数**。这个例子还能顺带讲清:为什么 bad case 要先看块内容,再看检索器。

**工程推论**

1. 切法跟着内容形态走:QA 库按问答对,说明书按标题层级,自由文本再考虑语义切
2. 改 chunking = 全库重嵌入,是成本动作——评测数据支持后再动
3. bad case 里"主题对但答案缺半句"的,先怀疑切法,再怀疑检索器
4. 每块带元数据,为溯源、过滤、答案之书的 verified 机制留好接口

**常见误区**

- "chunk 大小有个公认最佳值(比如 512)"——脱离内容形态谈参数没有意义
- "切完就完了"——元数据是 chunking 的另一半

## 小结

```text
语义可计算(对比学习训出 embedding) → 字面无关、语义近的能查中(向量检索的存在理由)
                                  ↘ 但几何近 ≠ 答案对(专名/否定/多跳/形态/粒度五类失效)
                                     → 失效模式反推方案(混合检索/改写/拆问题)
规模要快(ANN)+ top-k 两难 → 召回快而糙(双塔分别压缩)+ 精排慢而准(交叉编码逐 token 交互)
                          → 两段式是算力分工的必然
块是检索的入口 → 语义完整 vs 向量聚焦的固有取舍 → 切法跟内容形态;元数据是另一半
串回生成机制篇:检索喂的是上下文 → 注意力偏头尾,精排后最相关放最前;上下文有预算,只取精华
```

至此原理层三篇齐:模型怎么生成(上)、边界与来历(下)、检索为什么是解药(本篇)。RAG 的每一步——切片、混合检索、rerank、排序组装——现在都能回答"为什么",这正是一线使用者和应用工程师的分界线。工程层的《RAG系统设计复盘》将用同一套骨架复盘自己的系统。

## FAQ

**Q:为什么不用最强的 embedding 一步到位,非要两段?**
双塔为了快必须把文档压缩成一个向量,糙是结构性的,换再大的模型也只是缓解;交叉编码准是因为逐 token 交互,但每对都要现场算。一步到位等于让面试官直接面一千个候选人——钱和延迟都不允许。两段式是算力分工,不是技术妥协。

**Q:我的 FAQ 库就几十条,也要 rerank 吗?**
几十条可以暴力精排(甚至全量塞上下文)——管线规模跟着库长,别过度设计。但注意:库小不等于没失效模式,否定语义、专名混检这些问题不因库小消失,该上的混合检索和查询改写还是要上。规模缩的是工程,不是原理。
