# AI 应用工程岗技能地图(主干)

> 目标岗位:AI 应用工程岗 | 切入点:一年多 agent 实战经验 | 时间线:2026-09 → 2027 年年后

一句话定位:**把"多用过几个 agent"升级为"能设计、能解释、能证明的 AI 应用工程能力",以一年多实战经验为素材,四层框架补齐,年前完成证据化,年后投递。**

本文是本专题的主干文档(总目录+总框架),各层细节由后续子文档展开(见第六节)。

## 一、为什么做这个专题

一年多里密集使用过 codex、pi coding agent、codebuddy、zcode、zed、claude code 六个编码 agent,工作上在做 FAQ 问答 RAG 知识库(钉钉 + AstrBot),还用 AI 辅助产出过产品能力文档与公司试点方案。但直接拿这些去面试,呈现出来只是"多会使用几个 agent"——工具使用经验贬值很快,一年前会用编码 agent 是加分项,现在越来越多人都会。

真实的处境是:**手里的素材比想象的多,缺的是两样东西——体系化(散落的经验变成能讲的知识)和证据化(脑子里会的东西变成可展示的作品与指标)。** 本专题就是干这两件事。

## 二、目标岗位画像:AI 应用工程岗

明确锚定 **AI 应用工程岗**(又称 AI 应用工程师 / Agent 工程师 / AI 解决方案工程师),不追算法/研究岗——后者要数学功底与论文/训练经验,几个月补不出来,硬追只会两头落空。

这个岗位做的事:用 LLM 能力构建生产级应用——RAG 问答、agent 工作流、工具集成、评测与监控、成本与延迟优化。面试考察的不是背概念,而是三条:

| 考察维度 | 面试官的问题形态 | 对应本地图 |
|---------|----------------|-----------|
| 决策链 | "为什么这么设计?还有什么别的方案?" | 原理层+工程层 |
| 失效认知 | "系统为什么会答错?你怎么发现和修的?" | 原理层+质量层 |
| 证据 | "拿什么证明它好用?" | 证据层(差异化重点) |

## 三、切入点:一年 agent 实战的正确打开方式

切入点的认知转换:**从"使用者"变成"能解释和评估的人"。**

- "用过 6 个 agent"没有说服力;"能讲清楚 agent 什么时候该用、什么时候不该用、常见失败模式是什么、怎么设计防错"才有说服力。
- 六个工具的真正价值是**横评视角**——多数人只深度用过一两个,同时用过六个的人反而能看出设计取舍(交互形态、权限模型、上下文管理、MCP/工具生态、适用场景各有不同)。横评认知要主动整理成文,不整理就只是"都开过会员"。
- 失败经验是金矿:本仓库台账里全是真实踩坑(文件名 `#` 被 URL 当锚点、Astro slug 大小写 404、CI 产物 409……),这些故事化之后就是面试里"我有实战经验"的证据。**没有失败故事的候选人,面试官会怀疑他没真做过。**

典型面试题自检(现在答不顺的,就是要补的):

1. 你用过这么多 agent,它们的核心区别是什么?各自适合什么场景?
2. 什么任务不该交给 agent?你怎么判断边界?
3. agent 改你的代码,你怎么防止它改坏?(权限、验收、回滚)
4. 你的 RAG 系统为什么会答错?举一个你修过的真实 bad case。
5. 拿什么证明你的 RAG 比直接问大模型好?

## 四、四层框架(主体)

比例上重下轻,证据层与实践素材是主力:

```text
┌──────────────────────────────────────────────┐
│ 证据层 30%   作品集 / 量化指标 / 开源贡献 / 输出 │  ← 差异化
├──────────────────────────────────────────────┤
│ 工程层 30%   RAG 全链路 / agent 编排 / 工作流   │
├──────────────────────────────────────────────┤
│ 质量层 20%   evals / 可观测 / 成本与延迟        │  ← 市场稀缺
├──────────────────────────────────────────────┤
│ 原理层 20%   到"能做工程决策"的深度             │
└──────────────────────────────────────────────┘
```

### 4.3 质量层(20%):市场最缺的一环,重点补

会用 agent 的人很多,能把"我觉得好"变成"指标证明好"的人很少——这是性价比最高的差异化。

- [ ] golden set 构建:50~100 条真实问题+标准答案(Q7 方案里已有设计)
- [ ] 回归评测:每次改动跑一遍,指标不倒退才算改完
- [ ] LLM-as-judge:用模型评模型,知道它的偏差与校准方法
- [ ] 可观测:日志留痕、bad case 收集渠道、线上问题回放
- [ ] 成本与延迟:缓存、模型分级路由(简单问题小模型)、token 账单怎么算

已有基础:Q7 的评估闭环设计已写进落地方案,评测报告模板 v0 已建(2026-10-02,数据回流即填);缺的是在公司项目里真正跑起来。
产出:一份带真实数字的评测报告(准确率/误路由率/延迟/成本)。

## FAQ

**Q:要不要补数学(线代/概率)或学微调?**
应用岗面试极少考推导。微调了解概念与适用场景即可(什么时候该微调、什么时候 RAG/提示词就够了,反而常考)。时间应投给 evals 和作品。

**Q:要不要考个 AI 证书?**
作品>证书。这个仓库+带指标的 RAG 系统的说服力远高于证书,且时间只有一份。

**Q:六个 agent 要都写进简历吗?**
不罗列工具名。写成横评认知:"深度使用过六个主流编码 agent,能按任务特征选型并设计防错工作流",面试再展开。

**Q:现在最该做的一件事是什么?**
把公司 RAG 项目的 golden set 跑起来。它同时喂饱质量层(评测报告)和证据层(量化指标),是四层的交汇点。
