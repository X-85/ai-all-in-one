一句话版:**上篇讲模型的脾气(怎么生成),本篇讲它的身板——能装多少上下文、天生做不好什么、推理模型多花的钱买了什么、它是怎么练出来的、版图上怎么选。**

## 一、上下文与注意力(lost in the middle)

**是什么**:上下文窗口虽大,但注意力不是均匀洒的——开头和结尾被充分利用,中段容易被忽略。这个现象叫 lost in the middle(2023 年同名论文)。

**机制**

- 注意力的本质:生成每个 token 时,模型对上下文里所有 token 算一遍相关性权重,决定"此刻最该看哪里"——但这个"看"有位置偏差
- 偏差从训练来:语料里重要信息多在开头(指令、标题)和结尾(近期对话、结论),模型学到了头尾加权的先验
- 实验形态:把能回答问题的关键事实放在长文档的不同位置测答对率,曲线呈 U 型——首尾高,中段明显下滑
- 长上下文还贵:注意力计算量随长度平方级增长(概念级),推理时要缓存的历史也线性变长——**长上下文不只影响质量,还影响延迟和成本**

**例子(可直接讲,约 1 分钟)**
lost in the middle 的实验:同一份资料、同一个问题,唯一变量是"包含答案的那句话"放在第几个位置——放头尾答对率高,埋在中段,答对率掉一半。落点:所以我的 RAG 管线里,rerank 打完分不是直接扔给模型,而是把最相关的片段排在 prompt 最前面——"检索"解决找得到,"排序"解决被看见。这是知道原理才会想到的细节。

**工程推论**

1. **检索结果的摆放有讲究**:最相关片段放前面(或首尾),别让金块埋中段
2. **RAG 是"花小钱办大事"的机制级合理性**:与其整篇塞入赌注意力,不如只检索最相关的几千 token——省预算,还避开中段遗忘
3. system prompt 放开头有道理(指令位置先验);关键约束可以开头结尾各放一次
4. "超长窗口整库塞入"≠ 检索,选型时拿自己的数据测,别信宣传页

**常见误区**

- "窗口大 = 记性好"——窗口是容量,不是注意力质量
- "都塞进去了它就该知道"——塞进去 ≠ 用上

## 二、能力边界与工具外挂

**是什么**:有些任务模型**机制性地**做不好,提示词救不了。识别边界、给模型外挂工具,是应用工程师的日常决策。

**机制**

逐 token 概率生成这个机制,天然决定四类弱项:

1. **精确性**:计数、算术、严格约束满足——每个 token 都是"大概率的下一个",精确从来不是它的目标函数
2. **事实性**:训练截止后的新知识、私有知识不在参数里(上篇:知识是压缩进去的,压缩有截止日期)
3. **一致性**:长输出容易前后不一,而且自洽地错(滚雪球)
4. **长流程**:几百步的任务没有外部状态就容易漂

最危险的组合:模型**校准差**(不擅长知道自己不知道)+ 输出流畅——流畅会掩盖无能。

**例子(可直接讲,约 1 分钟)**
"9.11 和 9.9 哪个大"这类翻车:token 化之后版本号语义和数值语义打架,模型凭分布直觉作答。工程化的对照:让模型直接算订单总价,几行乘加法错误率可观;让模型生成一段 Python 去执行,零误差。落点:我系统里凡是数字运算,模型只负责"把需求翻译成代码",从不亲自算——它当调度员,不当计算器。

**工程推论**

1. **弱项清单反过来就是工具清单**:算术 → 代码执行;新事实 → 检索;严格格式 → 结构化输出+校验重试;长流程 → 外部状态+检查点
2. **agent 的机制级本质**:LLM 当调度大脑,精确执行交给工具——工具调用不是附加功能,是对能力边界的正解
3. 面试常考"什么时候不该用 agent":任务模型一步就能做好,外挂纯属增加失败面
4. 边界识别靠实证:拿 golden set 测,不要靠猜

**常见误区**

- "prompt 再改改总能救"——提示词救表述性弱项,救不了机制性弱项
- "模型变强这些问题就没了"——弱项在收窄但没消失,工程决策看当下边界

## 三、推理模型(reasoning models)

**是什么**:回答前先生成一段长内部思考(thinking),再给最终答案的一类模型——o 系列、DeepSeek-R1、各家 thinking 模式是代表。

**机制**

- 回顾上篇:每个 token 就是一次前向计算。普通模型"直觉式"一步作答,复杂问题一步登天容易踩空
- 推理模型把**草稿纸内化**:先在上下文里写推理过程,中间结论落成文字,再基于它继续推——"生成即上下文"这次是优点(草稿会自我强化,这次强化的是对的路径)
- 训练上主要靠强化学习:奖励最终答对的推理路径,模型自己学出"先想再答"的行为(概念级,细节在补充资料)
- **代价**:thinking 也是 token,按量计费、拉长延迟;简单问题上属于花钱买等待

**例子(可直接讲,约 1 分钟)**
同一道题:给三条产品线的原始营收数据,问哪条增长最快。普通模型直觉作答,比大小容易错;推理模型先列式、再逐步算,正确率明显高——但延迟可能多数十秒、费用数倍。落点:所以我的路由是分级的——FAQ 直答不走推理,数据分析类问题才升级推理模型。"每类问题一个价位",这是成本工程的 core 思想。

**工程推论**

1. **选型判据**:多步推理/数学/复杂分析 → 值得;翻译/摘要/格式转换/简单 FAQ → 不值
2. **模型分级路由**是成本工程主战场:简单任务便宜模型,复杂任务才上推理(接质量层)
3. thinking budget 是成本旋钮,不是越长越好
4. 对 RAG 的含义:推理模型提升"答案综合",**救不了"检索命中"**——别指望换模型治检索病

**常见误区**

- "推理模型全面更强,默认用它"——对简单任务是纯浪费
- "thinking 文本可以直接展示给用户当解释"——它不一定忠实于模型真实的决策过程,当参考可以,当解释承诺不行

## 四、训练概念级:模型怎么来的 & 微调 vs RAG

**是什么**:两个阶段——**预训练**(海量文本学会续写)+ **后训练**(教它当助手)。到概念级为止,数学细节不进面试话术。

**机制**

- **预训练**:万亿 token 级语料,自监督学"下一个 token",语言、世界知识、部分推理能力都在这一步进参数。极贵,只有大厂玩
- **后训练**:先 SFT 监督微调(人写问答示例,教格式与助手行为),再偏好对齐 RLHF/RFT(人类对回答排序,教"哪个更好");DPO 等是简化变体(细节在补充资料)
- 微调(继续 SFT)改的是**行为与分布**:输出风格、格式、领域语言习惯;参数更新意味着知识一变就得重训
- **微调 vs RAG 的决策轴:知识 vs 能力**——知识(常变、要溯源、要权限)放外部用 RAG;能力/风格(稳定)可进参数用微调
- 顺带两个词:蒸馏(大模型教小模型)、量化(参数压缩)——"小模型也能干活"的背后

**例子(可直接讲,约 1 分钟)**
面试标准题:"老板要求模型学会公司术语、回答用公司口径——微调还是 RAG?"我先把需求拆两半:术语和口径是**稳定的说话方式**,微调擅长;但术语对应的事实(价格、参数、政策)**常变**,是 RAG 的主场。真实答案常常是"都要":微调管怎么说话,RAG 管说什么。这个"拆需求再选工具"的答法,比直接站队更能证明工程判断力。

**工程推论**

1. **默认顺序:prompt → RAG → 微调**,每一步解决上一步解决不了的;成本递增、灵活性递减
2. 企业落地最常见的坑:**拿微调当知识灌注用**——知识一更新就得重训,这是把 RAG 的活派给微调
3. "微调了就不用写 prompt 了"是错的:微调改善起点,prompt 决定上限附近的表现
4. 排期口径:微调是训练任务(数据工程+评测+迭代),不是一次性配置

**常见误区**

- "微调 = 灌知识"——最常见误解;知识更新是 RAG 的主场
- "RAG 是微调的替代品"——解决的是不同问题,常常互补

## 五、多模态与模型格局

**是什么**:多模态 = 模型不止读文本,还能看图(截图/图表/照片)、听音频;格局 = 2026 年的模型版图:闭源旗舰、开源权重、大小分级、通用与特化。

**机制**

- **图像怎么进来**:视觉编码器把图切成小块(patch),每块变成一个"视觉 token",与文本 token 拼进同一个上下文——所以**图也占 token 预算**,一张图几百到上千 token(量级,依分辨率与模型而定;细节在补充资料)
- 语音同理,走特征化前端或专门的音频通路
- **版图认知(不背参数,记分工)**:闭源旗舰(能力上限)、开源权重(可私有化,与闭源差距在缩小)、小模型(便宜快,承接简单任务)、推理模型(贵而强)、嵌入与 rerank 模型(RAG 专件)
- 选型逻辑:按任务选价位——直接接工程层的成本路由

**例子(可直接讲,约 1 分钟)**
钉钉群里用户甩一张报错截图问"怎么办":纯文本 RAG 答不了。我的分层做法:多模态模型先做**感知**——把截图转成结构化描述(错误码、组件名、时间),再拿这描述走文本 RAG 检索知识库。一句话总结:"多模态做感知,RAG 做知识"——各干各的强项,而不是找一个全能模型硬吞。

**工程推论**

1. 多模态 RAG 场景判断:截图问答、图表理解、工单带图;记得图像 token 也计费也占预算
2. 选型三问:要能力上限还是要私有化?调用量多大成本多敏感?延迟要求多少?
3. **模型可替换性设计**:API 封装层别绑死单一厂商——模型是快变量,架构要能换
4. 嵌入 / rerank / 生成模型分开选型,各有最优解,不迷信一家全家桶

**常见误区**

- "多模态 = 更聪明"——通道变多而已,推理能力另算
- "旗舰一定最好"——对批量简单任务是成本灾难

## 小结

```text
窗口虽大 → 注意力偏头尾(lost in the middle) → 检索+排序是刚需(RAG 的机制级合理性)
生成机制 → 四类机制性弱项(精确/事实/一致/长流程) → 工具外挂(agent 的本质)
直觉式作答易错 → 推理模型(思考=在上下文打草稿,生成即上下文的正向利用)
                              → 按任务复杂度分级路由
预训练+后训练 → 知识在参数(会过期) vs 行为在参数(稳定)
              → 知识用 RAG、行为用微调,顺序 prompt → RAG → 微调
图像切块成 token → 与文本同池同预算 → 多模态也是预算问题;格局=按任务选价位
```

至此上下两篇合起来,模型的"脾气与身板"齐了:怎么生成(上)、边界与来历(下)。下一篇《检索原理》回答:针对这些机制,RAG 为什么是对症的解药。

## FAQ

**Q:RAG 和超长上下文(整库直接塞进去)到底选哪个?**
机制层答案:长上下文有注意力偏置(塞进去 ≠ 用上)和平方级成本;检索是"选择性注意"的工程实现。小知识库(几百页)可以试长上下文,库大、知识常更新、答案要溯源的,必走 RAG。

**Q:公司说想"训练一个自己的大模型",怎么理解这个诉求?**
绝大多数"自训大模型"的真实诉求是两条:回答符合公司口径(行为)+ 知道公司知识(知识)。前者小规模 SFT 可做,后者 RAG 是正解;从零预训练不是应用工程岗该接的活。把模糊诉求翻译成 prompt/RAG/微调的组合方案,正是 AI 应用工程师的价值所在。
