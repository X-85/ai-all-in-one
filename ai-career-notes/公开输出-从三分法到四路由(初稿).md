在公司钉钉群里,我们需要一个 FAQ 问答机器人。技术栈很朴素:钉钉机器人接入 AstrBot,自建知识库,原路回复。需求只有两个字:**答得准**。

这篇文章不讲部署、不讲调参,只讲路由层设计被推翻重来的一次演进——从三分法到四路由。它是一次真实的设计失误与修正,我觉得比"我做了个 RAG 系统"更值得写。

## 一、第一版:三分法

初版的路由设计按"答案可不可验证"把所有提问分成三类:

- **真理类**:有唯一标准答案的事实问题 → 直接回答
- **非真理类**:需要解释、比较、推理的问题 → 走 RAG 生成
- **意图不明**:问题没问清楚 → 追问

直觉上很顺:有标准答案的走标准答案,没有的让模型发挥,听不懂的先问清楚。跑起来头几天也过得去。

然后坏事了。有些问题**两头都沾**:"报表接口为什么慢"——它既是库内有文档的事实,答案又必须是一段成因解释。按三分法它该进哪类?操作层面我们开始手工打补丁:这类先归非真理类,那类再归真理类,类目越打越多,bad case 却越来越难归因——因为你已经说不清一条 case 错在哪个环节。

## 二、被推翻的那个下午

复盘时,问题的真正根因被点破了:

**"是否可验证"是答案的治理属性,"库里有没有、问题全不全"是检索的物理属性——这是两根正交的轴,我把它们压成了一根。**

两根轴压成一根,必然互相穿透:"报表接口为什么慢"就是一个穿透点(库内事实 × 原因形态)。修补类目解决不了穿透,就像给歪了的坐标系加刻度。

这次学到的东西,后来我把它当成分类设计的铁律:**先检验轴,再修补类目。轴歪了,类目越修越乱;轴正交了,类目自然各归其位。**

## 三、四路由

重新设计后,系统拆成两根轴:

- **路由轴**:库内/库外 × 问题完整/欠完整 —— 决定走哪条路
- **形态轴**:原因/结果/过程 —— 决定答案长什么形状(对生成类回答都适用)

路由轴落地成四条路由:

| 路由 | 判定条件 | 动作 |
|------|---------|------|
| **A. FAQ 直答** | 高频事实问题,语义匹配高置信 | 直接返回人工维护的标准答案,标注"已验证" |
| **B. RAG 生成** | 库内、问题完整 | 按原因/结果/过程模板定向生成,带来源引用 |
| **C. 澄清** | 问题欠完整、意图不明 | 一轮追问,给 ≤3 个编号选项,按选择再走 A/B |
| **D. 拒答** | 库外/超纲/敏感 | 明说"不知道",给替代路径(转人工/查哪里) |

配合一个独立维护的**答案之书**:高频事实问题人工写成标准条目——问题 / 标准答案 / 别名问法 / 验证日期 / 时效提示,带 verified 标记独立成库。A 路由直答就出这本书。

## 四、四个反直觉的设计决策

### 1. "我不知道"是质量功能,不是失败

知识库外的问题,初版会被硬塞进 RAG 生成——模型在低相关性的片段上强行编答案,这是幻觉的最高发区。第四条路由(拒答)就是冲它去的:库外/超纲,明说不知道,并给替代路径。

对抗幻觉最硬的手段,不是更聪明的提示词,是**不给模型编的机会**。

### 2. 能不经过生成的答案,就是最确定的答案

A 路由直答完全绕开生成环节:答案是人写的、可审核、可复现。有人问"不走模型,不怕匹配错吗"?匹配错的风险由置信分层兜着:高置信直答,中置信答案带来源让人判断,低置信落入 RAG 生成——**不在一个阈值上赌全部**。

### 3. 澄清一轮封顶

意图不明时,多轮澄清理论上"更准",实际上是对话版的滚雪球:第一轮的误解在后续轮次里自我强化,而且群聊场景里用户的耐心就一两句。所以我们定死:澄清**只问一轮**,选项 ≤3 个、带编号,选完立刻回答案。同理,意图识别和答案生成合并为一次模型调用,不做多级流水线——链路每加一环,排查难度翻一倍。

### 4. 书是长出来的,不是一次写成的

答案之书 v0 只人工写 Top 高频问题,之后靠飞轮:每周审核一次 RAG 日志,把"答得好且被反复问"的问答对送人工审核,通过后沉淀入书(带验证日期和负责人)。知识库不是交付物,是运营出来的资产。

## 五、还没做的事

诚实起见,这部分必须写:这套设计目前的状态是**已定稿、待实测**。

- **golden set 还没建完**:50~100 条真实问题、每条标注预期路由,这是评测的地基
- **首轮回归还没跑**:所有"设计正确"的断言,要等"预期路由 vs 实际路由"的对照表出来才算数 `[待回填:路由准确率]`
- **已知未封的洞**:专名类(`ERR-1001` vs `ERR-1002`)和否定类("开通" vs "关闭")的查询,单靠向量检索必然翻车——golden set 里会单列这两类,命中差就上关键词混合检索

评测思路先立个 flag 在这:每条 case 标预期路由,回归时对照实际路由,误路由按方向分类归档(A 误成 B、B 误成 D、C 过度触发……),每类对应一个明确的修正动作。数字出来后我会回来更新这篇文章。

## 写在最后

这次演进留给我四条原则,它们比四路由本身更可迁移:

1. **轴要正交**——分类出问题,先查轴,再修类目
2. **确定性优先**——能走管道的不过模型的手
3. **短链路**——每多一环调用,就多一倍排查面
4. **把"不知道"当功能设计**——系统的诚实边界,就是用户信任的起点

RAG 系统的难点从来不是"接上大模型",而是回答"它什么时候不可信,以及你拿什么证明它可信"。四路由是我的答案的第一版,等评测数据回来,再写第二版。
