# 工作流 agent 实践

> 层:工程层 | 系列位置:工程层第三篇 | 主题:用 agent 干成事的方法论 | 与横评分工:横评管"选哪个工具",本篇管"选定后怎么用好"

一句话版:**一年多实战沉淀的工作流方法论——把"人机协作"当系统来设计:上下文喂对(仓库地图)、验收前置、危险操作受控、增量确认、待确认显式化、过程留痕。工具换来换去,这些不变。**

## 一、工作流全景清单

一年多来用 AI agent 干的事,按产出形态分五类:

| # | 类别 | 代表产出 | 主体工作流 |
|---|------|---------|-----------|
| 1 | 知识生产 | 语言演进系列 20 篇、本求职专题 | 模板 + AGENTS.md 流程 + 台账接续,长文档生产线 |
| 2 | 文档工程 | 产品能力文档(AI 初稿 + 负责人审核) | 资料包 → AI 提取事实 → 人确认 → 生成初稿 → 评审 |
| 3 | 工作流移交 | ZCode-MCP 公司试点手册 | 把工作流写成"可移交文档":占位符 + 铁律 + 验收 |
| 4 | agent 系统设计 | 钉钉日志智能分析方案、FAQ 问答系统(另见复盘) | 受控工具 + 分层编排 + 安全边界 |
| 5 | 会话管理 | session 台账 | AI 记忆外置,跨会话接续 |

[待回填:还有没有别的类别(运维排查、数据分析、日常杂活…)]

## 二、代表案例复盘

### 案例 1:语言演进系列——长文档生产线

**问题**:20 篇结构严格一致的因果链长文,多会话产出,怎么保证不走样、不重复劳动?

**做法**:三件套——①**模板**(decisions.md:不变件+按类型可变件,九段式骨架);②**AGENTS.md 流程**(必读文件→六步产出→注意事项,新会话零口令接续);③**台账**(进度、踩坑、编号,跨会话记忆)。

**效果**:20 篇全按同一模板产出,任何新会话说"写 X 演进路线"即可开工;踩坑(如 C# 文件名锚点坑)沉淀进决策,不二犯。

### 案例 2:产品能力文档——"审核初稿"取代"从零写作"

**问题**:能力文档从零写耗时,负责人拖延;不熟悉的能力无从下笔。

**做法**:把写作拆成人机分工流水线——AI 整理资料生成初稿 → 负责人确认事实、补经验 → 评审发布。两个关键设计:①**先理解再写作**(先让 AI 提取事实、区分能力/特性/支持项、列出冲突缺口,人确认高风险项后再生成);②**模板三原则**:"AI 容易生成、负责人容易审核、后续容易维护"——不为完整堆字段。

**效果**:负责人的任务从"从零写"变成"审核初稿",启动成本骤降 [待回填:试点实测的审核耗时对比]。

### 案例 3:ZCode-MCP 试点手册——工作流的移交

**问题**:在公司(Windows、网络受限)落地"AI 巡页面 + 生成配置文档",而执行者不是自己。

**做法**:把工作流写成自包含文档:占位符表(测试地址/账号/仓库)、给 agent 的执行铁律(标出处/留空不编/危险操作只截图)、安装三路线按网络状况选、分阶段提示词与验收标准、故障排查表、90 分钟时间表。

**关键点**:这是"元工作流"——工作流本身被文档化到**可以交给别人(或未来某个会话)执行**。个人技能变成可复制资产的分界线。

### 案例 4:钉钉日志智能分析——agent 系统的设计纪律

**问题**:钉钉收日志 → AstrBot 分析 → 回钉钉,怎么设计才不失控?

**做法**(方案全文见知识库,此处抽设计决策):

- **三层递进分析**:direct LLM → Skill+模块文档 → 受控源码工具;**证据不足才升级**——最贵的能力(源码分析)由置信度触发,不由用户触发。和 FAQ 系统的"FAQ 直答→RAG 兜底"、推理模型分级是同一个思想:**按需花钱**
- **受控工具,不给 shell**:语义化工具(`read_source_file`/`search_source`/`get_git_blame`)+ 白名单命令 + 只读 + 路径边界 + 工具调用次数上限(8~12 次)——不给 LLM 无限制的执行权
- **MCP 的克制**:明确"MCP 是工具接入协议,不是必须替换的执行器";列了五条触发条件(隔离部署/跨语言/多实例共享…),不满足就不引入,避免嵌套两套 Agent Loop
- **安全默认**:日志按不可信输入处理(脱敏、防提示注入)、trace_id 全链路、超时可取消

**效果**:方案文档本身就是"agent 系统设计纪律"的展示品 [待回填:落地进度与实测]。

## 三、通用模式提炼(方法论核心)

从四个案例+一年使用中提炼,每条注明原理依据(接原理层)与实践出处:

1. **上下文喂对:仓库地图(AGENTS.md / SKILL.md)**
   AI 产出质量的上限是上下文质量。先花 30 分钟写"地图"(规则、流程、必读文件、坑),之后每次开工都省 30 分钟解释。AstrBot 方案还给了进阶版:**渐进式加载**——先给目录(Skill 名称+描述),要用再读全文,正对应上下文预算管理(生成机制·上·一)。
2. **验收前置**
   把"什么算做完"写进开工前:演进系列每篇有验收三连,试点手册每阶段有验收标准,日志方案有统一 JSON 结构。没有验收的生成是开盲盒——也呼应"评测闭环"(质量层)。
3. **危险操作受控**
   巡览"只截图不点击"、源码工具"只读+白名单+路径边界"、生产配置先备份。机制依据:能力边界(生成机制·下·二)——不考验模型的自制力,用工程边界兜住。
4. **增量确认**
   先理解再写作(提取事实→人确认→生成)、长文档按节产出、澄清一轮封顶(FAQ 系统)。机制依据:滚雪球(生成机制·上·二)——错误在早期拦截成本最低。
5. **待确认显式化,不编造**
   能力文档模板单列"待确认问题"章节,"资料不足标记待确认,不能让 AI 根据常识猜测产品事实";本专题的 `[待回填:xxx]` 同构。机制依据:幻觉是固有属性——与其事后鉴别,不如结构上不给它编的位置。
6. **过程留痕**
   session 台账(问题/事件/决策三件套)、trace_id、"问题-预期-实际"对照表。AI 的记忆外置到文件,跨会话、可审计;踩坑和 bad case 都是资产。
7. **按需花钱:分级与升级触发**
   FAQ 直答→RAG、direct→docs→code、普通模型→推理模型:同一思想的三次应用——便宜的能力先上,贵的能力由证据/置信度触发。
8. **移交设计**
   占位符+铁律+分阶段+排查表(试点手册)。检验一个工作流是否真成型:把它写成文档,别人能否零口令执行。

## 四、防错设计与边界

**什么时候不用 agent**(接能力边界,面试高频):

- 任务一步就能做对、验证比执行还快 → 直接做,agent 纯增失败面
- 高风险不可逆操作(删库、对外发布)→ agent 只做只读侦查,决策与执行留给人
- 需要为结果负责的判断(拍板、签字)→ agent 供证据,人拍板

**权限边界的层次**(从松到紧):全开放 shell(仅限沙箱/一次性环境)→ 命令白名单 → 语义化受控工具(日志方案的选择)→ 纯只读侦查(巡览)。按场景选档,默认从紧。

**真实踩坑与修正**(失败模式清单的种子,面试可讲):

- **并行会话撞文件**:两个会话同时改 chapters.ts/首页,写入互相覆盖——修正:动笔前重读台账+文件现状,增量改动后重试
- **台账编号撞号**:并行轮各自记了"第6次处理"——修正:补记时核对编号并注明
- **静默失败**:Astro 遇 `#` 文件名页面静默缺失,不报错——修正:产出后主动验收(构建页数/死链检查),不信任"没报错=没问题"

共同教训:**agent 的错误大多不是"能力不够",而是"边界没设好、验收没做实"**——防错设计在人不在模型。

## 五、FAQ

**Q:这些工作流和"会用 Claude Code/ZCode"的区别是什么?面试怎么讲?**
会用工具是知道油门刹车;工作流是有路线图的驾驶——可移交(写成手册别人能执行)、可复现(模板+流程,产出一致)、可审计(台账+trace,每步可溯)。一句话:"我不挑工具,六个都开过;我沉淀的是不管工具怎么换都成立的工作流。"

**Q:agent 把文件改坏了怎么办?**
三层兜底:git(可回滚)、验收(构建+死链检查,改完就验)、边界(受控工具/只读侦查,从源头少改坏)。真实案例:并行会话撞文件靠"重读现状+增量重试"化解——错误处理本身也是工作流的一部分。
